## ServerClock (clock-skew correction)  [risk: low]
- purpose: Make the 45s presence freshness window survive wrong device clocks.
- files: E:\LDR\mobile\lib\core\services\server_clock.dart; fed from presence_service.dart:200-207.
- tables: none (derives offset from presence.updated_at returned by the upsert).
- transport: neither.
- how it works: Every presence upsert returns the server-stamped updated_at. ServerClock.observe() takes the device time captured just before the request, computes the round-trip midpoint (NTP-style), and stores serverNow - deviceNow as a static offset. Until the first heartbeat lands, offset is zero and the app is back on the device clock. The offset is a process-global static with no drift re-estimation beyond the 2s hysteresis.
- scale reason: Correctly designed and free (rides an existing round-trip). The residual lastSeenText bug affects display text only, not delivery.

- how it works: Each of the four tables has an AFTER INSERT trigger that calls net.http_post to the SAME edge function with {kind, record} (fcm_push.sql posts a bare row for backwards compatibility). reach-notify resolves the recipient — explicit callee_id for calls, otherwise `profiles where couple_id = X and id != from_user limit 1` — mints a Google OAuth2 access token by RS256-signing a service-account JWT and exchanging it at oauth2.googleapis.com, then POSTs to fcm/v1/projects/{id}/messages:send. Payload is data-only (type, from_name, couple_id, + one id key per kind) with android.priority=high and ttl 30s for reach/care/call, 86400s for message. On 404/UNREGISTERED/NOT_FOUND it nulls the recipient's fcm_token; it always returns 200 so pg_net never retry-storms. The client re-registers its token on every app resume (main.dart:286) specifically to self-heal a token the function nulled. The background isolate re-inits Firebase, builds a local notification wearing the current disguise style (title/body/icon carry NO sender name or content, visibility secret), and stashes the tap in a ValueNotifier (pendingReach/pendingCall) that AppShell drains in a post-frame callback.
- weaknesses: 1) profiles.fcm_token is a SINGLE column — one device per user; signing in on a second device silently steals push from the first, and there is no per-device token table. 2) getAccessToken() runs on EVERY invocation — an RSA sign plus a Google token round-trip per push, with no caching, so a message push is 3 sequential network hops before FCM even sees it. 3) The message trigger fires on every messages INSERT with no check of whether the recipient is online or already has the chat open; the client silently discards it in _onForeground (fcm_service.dart:139-146), so a large fraction of pushes are pure waste. 4) pg_net is fire-and-forget: the trigger cannot see failures, and the only diagnosis is reading net._http_response (documented in message_push.sql:39-44). No retry, no dead-letter, no dedupe. 5) The recipient query uses limit(1) with no ordering — a couple with a stray third profile is nondeterministic. 6) FSI permission for the background isolate is read from a SharedPreferences cache ('fsi_can_use') that only the foreground can refresh.
- scale reason: This is the hard ceiling. Every chat message triggers one synchronous pg_net enqueue plus one edge-function invocation that performs an RSA signature and a Google OAuth exchange before sending — per message, per couple, with no token cache, no batching, and no suppression for online recipients. At thousands of users chatting this is edge-function invocations and Google token-endpoint calls scaling linearly with total message volume, and pg_net's single fire-and-forget queue plus an unbounded net._http_response table sits directly in the write path of the busiest table in the app.
