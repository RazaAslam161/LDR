# Android push notification reliability for time-critical events: FCM semantics, Doze/App Standby, force-stop and OEM kill behaviour, delivery observability, and privacy-preserving wake-ups — benchmarked against Signal/Telegram and mapped onto Flutter + Supabase (free tier)

## Mechanism
## The core mechanism top-tier apps converge on

**Push is a doorbell, not a mailbox.** Signal's server (open source, verifiable) sends a **data-only** FCM message whose entire payload is one key — `"newMessageAlert"` — with an **empty/placeholder value**. No sender, no ciphertext, no counter. `AndroidConfig.Priority.HIGH` when the `urgent` flag is set, otherwise `NORMAL`. TTL defaults to `Duration.ofDays(28)`. **No collapse key.** On `UNREGISTERED` the result carries an `unregistered` flag and the token is dropped. (DOCUMENTED — `Signal-Server/.../push/FcmSender.java`.)

The client is where the engineering is. `FcmReceiveService` reads **only** `getMessageId()`, `getSentTime()`, `getPriority()`, `getOriginalPriority()`, and a handful of non-message data keys (`challenge`, `rateLimitChallenge`, `verificationCodeRequested`). It logs *both* priorities and the computed delay + server time offset — i.e. every push is a delivery-latency probe. It branches on `getPriority() == RemoteMessage.PRIORITY_HIGH`: high → `startForegroundService()`; not high → background service on API < 26, **nothing at all** on API ≥ 26 (because starting an FGS after a priority downgrade throws `ForegroundServiceStartNotAllowedException`). (DOCUMENTED — `Signal-Android/.../gcm/FcmReceiveService.java`.)

`FcmFetchManager` then does the actual work, and its stated goals are exactly the two that matter: *"Ensure some service is active for the duration of the fetch and processing stages"* and *"Do not make unnecessary network requests."* Concretely (DOCUMENTED — `FcmFetchManager.kt`):
- `WebSocketDrainer.blockUntilDrainedAndProcessed()` pulls messages over the app's **own authenticated websocket** — FCM never carries content.
- Drain timeout: **5 minutes** normally, **2 minutes** on censored networks.
- A `SerialMonoLifoExecutor` (single-flight, 1 running + 1 queued, newest wins) **coalesces** a burst of pushes into one fetch. This is the idempotence mechanism: N pushes → 1 drain.
- On failure it schedules a retry via system `JobScheduler` (API 26+) or `MessageFetchJob`.
- If a **high-priority** fetch times out, it posts a deliberately content-free user notification: *"You may have new messages."* That is the fallback of last resort — tell the user something arrived rather than silently lose it.

So the shape is: **content-free high-priority data push → wake → foreground service → authenticated pull over your own transport → local notification built on-device → server-side queue is the source of truth, push is only a hint.** Every mainstream privacy-focused messenger converges on this. Telegram adds a second leg — it keeps its own connection alive when it can, and the FOSS build (no Play Services at all) is forced to run a permanent foreground-service notification because *"one can't use Google's push messaging in a FOSS app"* (DOCUMENTED — Telegram-FOSS `Notifications.md`).

## The FCM semantics that force this design

**Message types and who gets woken** (DOCUMENTED — firebase.google.com/docs/cloud-messaging/android/receive-messages):

| App state | notification-only | data-only | both |
|---|---|---|---|
| Foreground | `onMessageReceived` | `onMessageReceived` | `onMessageReceived` |
| Background | **system tray; `onMessageReceived` NOT called** | **`onMessageReceived` called** | tray + data into launcher Activity extras; `onMessageReceived` NOT called |

Consequence: **only a data-only payload gives you code execution when the app is backgrounded/killed.** If you need to decrypt, look up a disguise, choose a channel, or ring a call — data-only is the *only* option. Notification-only means the OS draws whatever you sent, in the clear, and your process never runs.

Second consequence, usually missed: **`notification` messages are always collapsible and ignore `collapse_key`** (DOCUMENTED — collapsible-message-types). You cannot make a notification message non-collapsible.

**Execution window.** `onMessageReceived` has *"a short execution window"*; the docs' own sample says *"For long-running tasks (10 seconds or more) use WorkManager"*. Firebase's 2025 post adds that high-priority messages get *"slightly more time... than normal priority ones"* and warns against async network calls that outlive the callback. FlutterFire is blunter: *"If tasks run for longer than 30 seconds, the device may automatically kill the process."* (DOCUMENTED.)

**Priority.** Normal = *"delivered immediately when the device is not sleeping... When the device is in Doze mode, delivery may be delayed."* High = *"FCM attempts to deliver high priority messages immediately, allowing FCM to wake a sleeping device... and to run some limited processing."* In Doze the system *"delivers the message and gives the app temporary access to network services and partial wakelocks, then returns the device or app to the idle state."* (DOCUMENTED — message-priority, doze-standby.)

**Priority quota — the Android 13 pivot.** On API ≤ 32 the standby bucket capped daily high-priority messages; over cap → downgraded to normal. **From Android 13, the standby bucket no longer determines high-priority FCM quota**; instead the system *"downgrades high-priority messages if an app consistently sends them without resulting in a notification."* (DOCUMENTED — appstandby, power-details.) The downgrade is not cosmetic: a downgraded message **cannot start a foreground service** and the attempt throws `ForegroundServiceStartNotAllowedException` (DOCUMENTED — restrictions-bg-start). This is why Signal checks `getPriority()` before `startForegroundService()`. **Every high-priority push must end in a user-visible notification, or you burn the mechanism you need for calls.**

**TTL.** Default and max = **2,419,200s (28 days)**. `ttl=0` is now-or-never — *"messages that can't be delivered immediately are discarded"*, never stored, *"provides the best latency."* A low-priority message to a Dozing device *"is stored by FCM until the device is out of Doze."* (DOCUMENTED — setting-message-lifespan.)

**Collapse and the 100-message cliff.** FCM stores **exactly 4 distinct collapse keys per device**; exceed it and *"FCM only keeps four collapse keys, with no determining factor on which keys are kept."* For non-collapsible messages the limit is **100 pending per app instance** — and when it's hit, ***all* stored messages are discarded** and the device gets a special message that surfaces as `onDeletedMessages()`, whose documented contract is *"perform a full sync with your app server."* (DOCUMENTED — collapsible-message-types, receive-messages, firebase.blog 2024.)

**Rate limits** (DOCUMENTED — throttling-and-quotas): 600k messages/min per project (429 `RESOURCE_EXHAUSTED`); **240 messages/min and 5,000/hour to a single device**; collapsible messages throttled to a **burst of 20 per app per device, refilling 1 every 3 minutes**.

## Doze, App Standby, and what an exemption actually buys

Doze suspends network, ignores wakelocks, defers `setExact()`/`setWindow()` alarms, skips Wi-Fi scans, sync adapters, and **JobScheduler — therefore WorkManager too**. Maintenance windows get rarer over time; **Google publishes no interval numbers**. `setAndAllowWhileIdle()`/`setExactAndAllowWhileIdle()` *"can[not] fire alarms more than once per nine minutes, per app."* (DOCUMENTED — doze-standby.)

Per-bucket quotas (DOCUMENTED — power-details):

| Bucket | Regular jobs | Expedited jobs | Alarms | Network |
|---|---|---|---|---|
| Active | 20 min / rolling 60 min | 30 min / 24h | unlimited | ok |
| Working set | 10 min / rolling 4h | 15 min / 24h | 10/hour | ok |
| Frequent | 10 min / rolling 12h | 10 min / 24h | 2/hour | ok |
| Rare | 10 min / rolling 24h | 10 min / 24h | 1/hour | **disabled** |
| Restricted | 1×/day, 10 min | 5 min / 24h | 1/day | **disabled** |

Restricted entry: **8 days** of no interaction on Android 13+ (45 days on 12/12L), or excessive broadcasts/bindings in 24h. Note the trap: in Rare/Restricted, **network is off** — a data-only push that wakes you into a bucket with no network gets you a running process that cannot fetch anything. High-priority FCM's *"temporary access to network services"* is the escape hatch, and it is the only one.

Battery-optimization exemption gives network + `PARTIAL_WAKE_LOCK` during Doze/Standby — and **nothing else**: *"the app's jobs and syncs are deferred... and its regular AlarmManager alarms don't fire."* Google's own acceptable-use table lists **"Real-time messaging app using FCM high priority" as NOT acceptable** ("Use FCM instead"), and Play policy prohibits requesting it *"unless the core function of the app is adversely affected."* (DOCUMENTED — doze-standby.)

## Force-stop: the hard wall

`FLAG_STOPPED` means **nothing in the app runs automatically, including its broadcast receivers**, until the user launches it directly or indirectly (share sheet, widget, live wallpaper). Android 15 tightened this further: *"the system cancels all pending intents when the app enters the stopped state"*, widgets are disabled, `ACTION_BOOT_COMPLETED` is redelivered when the app leaves stopped state so it can re-register, and `ApplicationStartInfo.wasForceStopped()` lets you detect it after the fact. (DOCUMENTED — developer.android.com/about/versions/15/behavior-changes-all.)

Firebase names **"App force-stopped"** as one of seven message outcomes: *"Device restricts app; FCM cannot deliver after retry failures."* FlutterFire states it plainly: *"On Android, if the user force quits the app from device settings, it must be manually reopened again for messages to start working."* (DOCUMENTED.)

**There is no workaround. None. Not high priority, not a foreground service, not a battery whitelist.** The message is queued (up to TTL / 28 days / the 100-message cap) and delivered when the user next opens the app. Every claimed fix is either a lie or an OEM-specific autostart toggle the *user* must flip.

## OEM behaviour, and the one lever Google gave you

The catalogue at dontkillmyapp.com ranks Huawei / Xiaomi / OnePlus / Samsung at the worst tier (5/5), Oppo/Meizu/Asus at 4, Vivo/realme/Motorola at 3, with AOSP/Google, Nokia/HMD and HTC clean. Specifics (DOCUMENTED as a catalogue; each is a user-facing setting, not an API):
- **Xiaomi/MIUI/HyperOS** — Security app → Permissions → **Autostart**; MIUI 14 promotes it to a real app permission ("Background autostart"); Battery → App Battery Saver → **No restriction**; drag-down **lock in recents**; a hidden "MIUI optimization" developer toggle that *"can break the background tasks."*
- **Samsung** — *"Put unused apps to sleep"*, **default 3 days**; **Sleeping apps / Deep sleeping apps / Never sleeping apps** lists (Android 11+); adaptive battery *"significantly more aggressive than stock."* Verdict: ***"No known solution on dev end."***
- **Vivo/Funtouch/OriginOS** — More settings → Applications → **Autostart**; Battery → **High background power consumption**; lock in taskbar.
- **Oppo/ColorOS** — startup manager + floating-app list in `com.coloros.safecenter`; **"Allow Auto Start-up"**; "smart restriction" pauses background services when the app is closed; background services killed **on screen-off** on some models. *"No known solution on the dev end."*
- **Huawei/EMUI** — **Protected apps**; App launch → disable "Manage all automatically" and enable every per-app toggle; **PowerGenie** *"kills all apps that are not on its whitelist"* with **no way to add your own** (removal needs `adb shell pm uninstall -k --user 0 com.huawei.powergenie`).

Google's counter-move is **CDD §3.5.1 "Application Restriction"** (renamed from "Background Restriction"). If an OEM's proprietary mechanism is **more restrictive than the Rare App Standby Bucket**, then (DOCUMENTED — android.googlesource.com CDD diff):
- **[C-1-1] MUST** provide user affordance where the user can see the list of restricted apps
- **[C-1-5] MUST** inform users when restrictions are applied automatically, **within 24 hours**
- **[C-1-6] MUST** return `true` for **`ActivityManager.isBackgroundRestricted()`** when the restricted app calls it

**That last one is the single portable programmatic signal you have.** (INFERRED, but it follows directly: the CDD makes it a compatibility requirement, so a CTS-passing MIUI/ColorOS/One UI build must report it.) Combine it with `UsageStatsManager.getAppStandbyBucket()`, `PowerManager.isIgnoringBatteryOptimizations()`, and `NotificationManagerCompat.areNotificationsEnabled()` and you can *detect* a doomed device and tell the user, which is exactly what WhatsApp/Signal/Telegram do via in-app help screens. Nobody has found a way to *fix* it from code — the honest, universal answer is a targeted, per-OEM onboarding screen.

## Observability

**FCM BigQuery export** — one row per message with `message_id`, `instance_id`, `event`, `analytics_label`, `message_type`, `sdk_platform`, `app_name`, `priority`, `ttl`, `topic`, `collapse_key`; events include `MESSAGE_ACCEPTED`, `MESSAGE_DELIVERED`, and rejection classes (`MISSING_REGISTRATIONS`, `UNAUTHORIZED_REGISTRATION`, `INVALID_PARAMETERS`, `PAYLOAD_TOO_LARGE`, `AUTHENTICATION_ERROR`). Initial propagation **up to 48 hours**; daily sync starts **4:00 AM Pacific**. (DOCUMENTED — understand-delivery.)

**FCM Data API (aggregated)** — **7 days** of history, **delayed up to 5 days**, per app/date/analytics-label. Mutually exclusive outcomes delivered / pending / dropped, with dropped reasons device-inactive, too-many-pending, TTL-expired. Also `deliveredNoDelay`, `delayedDeviceOffline`, `delayedMessageThrottled`, and — critically — **`priorityLowered`**, the percentage downgraded HIGH→NORMAL. Analytics labels: **max 100 unique/day, 50 chars**. Console reports lag **up to 24 hours**. Sampled, not complete. (DOCUMENTED.)

Neither tells you whether the *user saw* anything. That is why Signal instruments the client: log `messageId`, `sentTime`, computed delay, `priority` **and** `originalPriority` on every receipt. Top-tier apps close the loop with a **client ack** back to their own backend, giving true end-to-end delivery/latency per message — FCM's own data cannot provide this.

## Privacy-preserving wake-up

The pattern is fixed:
1. **Data-only, high priority, payload = opaque id + type only.** Signal ships literally one key with an empty value. Google, your CDN, and anyone reading FCM logs learn "a Signal push happened", nothing more.
2. **Build the notification on-device** in the background handler after decrypting/fetching locally.
3. **Lock screen redaction** via `setVisibility()`: `VISIBILITY_PRIVATE` shows icon + title only and pairs with `setPublicVersion()` for a redacted stand-in (docs' example: *"You have 3 new text messages"*); `VISIBILITY_SECRET` shows nothing on the lock screen at all. The user/channel setting always wins. (DOCUMENTED — build-notification.)
4. Three platform traps that silently break this:
   - **Android 13 POST_NOTIFICATIONS**: *"If your app creates its first notification channel when it is running in the background, which the FCM SDK does when receiving an FCM notification, Android won't allow the notification to be displayed and won't prompt the user... any notifications received before your app is opened and the user accepts the permission will be lost."* → **create channels at first foreground launch.**
   - **Android 12 notification trampolines**: you cannot `startActivity()` from a Service or BroadcastReceiver on notification tap — the system blocks it. Use a `PendingIntent` straight to the Activity.
   - **Android 14 USE_FULL_SCREEN_INTENT**: Play **revokes it at install** for apps that aren't calling/alarm apps. Check `NotificationManager#canUseFullScreenIntent()` and route users to `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`. (DOCUMENTED.)

## Invariants
- Push is a hint, never the payload. The server-side queue (Postgres row + monotonic cursor) is the sole source of truth; a lost, collapsed, TTL-expired or force-stop-dropped push costs latency, never data. Signal's design makes this structural: the FCM payload literally cannot carry a message.
- Every high-priority message terminates in a user-visible notification. This is the precondition that keeps the high-priority mechanism working: Android 13+ downgrades HIGH→NORMAL for apps that don't, and a downgraded message cannot start a foreground service (ForegroundServiceStartNotAllowedException).
- The client checks RemoteMessage.getPriority() before doing anything that requires high-priority privileges. Priority is a runtime property of the received message, not of what you sent.
- Fetches are single-flight and coalescing. Signal's SerialMonoLifoExecutor allows 1 running + 1 queued, newest wins — N pushes collapse into ≤2 drains, so redelivery and duplicate pushes are idempotent by construction.
- Content-free push payload => the transport carries no secrets, so FCM/Google/logs/lock screen leak nothing regardless of device state or notification settings. Privacy is a property of the payload, not of the notification config.
- onDeletedMessages() triggers a full server sync. The 100-pending cap discards ALL stored messages at once, so a gap is guaranteed detectable only if the client treats that callback as 'resync from cursor'.
- Token lifecycle is self-healing: UNREGISTERED/404 from FCM nulls the stored token server-side, and the client re-registers on every foreground/resume. Any token the server holds was valid at last app open.
- TTL encodes the semantic deadline of the event, not a guess. ttl=0 for 'worthless if late' (ring now), long TTL for 'must eventually arrive' (a message). A short TTL on durable content is data loss.
- Collapse keys are assigned per logical event stream, and never more than 4 distinct keys per device — exceeding it makes eviction arbitrary and unpredictable.
- Notification channels are created on first foreground launch, before any push can arrive, so the Android 13 permission-prompt trap cannot swallow the first notification.

## Failure modes designed for
- Device in Doze: normal-priority messages are batched to maintenance windows whose intervals Google does not publish and which lengthen over time; jobs, syncs, WorkManager and regular alarms don't run at all.
- App in the Rare or Restricted standby bucket: network access is DISABLED, so a woken process cannot fetch. Only high-priority FCM's temporary network grant escapes it. Restricted entry after 8 days of no interaction (Android 13+).
- High-priority quota exhaustion / automatic downgrade: on API ≤32 the standby bucket capped daily high-priority messages; on Android 13+ FCM downgrades apps whose high-priority pushes don't produce notifications. Downgrade silently removes the ability to start a foreground service.
- User force-stops the app (or an OEM ROM force-stops it on swipe-away): nothing in the app runs, receivers included, until manual relaunch. Android 15 additionally cancels all pending intents and disables widgets. Unrecoverable from code.
- 100 non-collapsible messages pending: ALL are discarded at once, not just the overflow — handled by treating onDeletedMessages() as a resync trigger.
- Only 4 collapse keys stored per device, with undefined eviction beyond that.
- Collapsible-message throttling: burst of 20 per app per device, refill 1 every 3 minutes — a chatty collapse key starves the others.
- Per-device rate limit: 240 messages/min, 5,000/hour — a retry storm or a group blast self-throttles.
- Stale tokens: FCM classifies a device inactive after roughly 4 weeks without delivery; Firebase reports apps that neglect token hygiene seeing ~15% of messages dropped for inactive devices.
- Notification delivered but never displayed: POST_NOTIFICATIONS ungranted, notification channel disabled, or the channel created in the background on Android 13 (message silently lost, no prompt until next app open).
- Priority downgrade breaking foreground-service start on a call — Signal branches on getPriority() and degrades gracefully rather than crashing.
- Fetch itself failing or timing out after a successful wake — Signal caps the websocket drain (5 min, 2 min on censored networks), reschedules via JobScheduler, and on high-priority timeout posts a content-free 'You may have new messages.'
- No Play Services at all (FOSS/de-Googled/China) — Telegram's FOSS build falls back to a permanent foreground-service notification because FCM is unavailable.
- OEM battery managers killing the process or blocking autostart: Huawei PowerGenie has a hardcoded whitelist apps cannot join; Samsung sleeps unused apps after 3 days by default; MIUI/ColorOS/Funtouch require per-app autostart toggles.
- Android 12 notification trampoline block (tap does nothing) and Android 14 full-screen-intent revocation at install (incoming-call UI silently downgrades to a normal notification).

## Applicability to Supabase
## What already matches the top-tier pattern in E:\LDR

`E:\LDR\supabase\functions\reach-notify\index.ts` and `E:\LDR\mobile\lib\core\services\fcm_service.dart` already get the two hardest decisions right:

- **Data-only + `priority: "high"`.** The comment at the top of `index.ts` gives the correct reason ("notification-only messages are drawn by the OS and won't reliably wake the screen on our channel") — and it is also the *only* way `firebaseMessagingBackgroundHandler` runs when the app is backgrounded, and the only way the disguise stays on-device. Same shape as Signal.
- **Token self-healing.** `FcmService.registerToken()` re-saves on every resume, and the edge function nulls `profiles.fcm_token` on `UNREGISTERED`/404. That is exactly Signal's `unregistered` flag. Keep it.
- **`type: 'message'` shows nothing in the foreground** because realtime already delivered it. Correct de-dup instinct.

## What is materially wrong or missing

**1. There is no retry. At all.** `index.ts` returns HTTP 200 on every FCM failure — the comment says *"200 so the webhook doesn't retry-storm"*. That converts a transient FCM `UNAVAILABLE`/`INTERNAL`/429, an OAuth token-exchange blip, or an edge-function cold-start timeout into **permanent silent loss of a call or a message**. Top-tier retries with backoff on retryable classes only. Fix: an `outbox` table (`id, user_id, kind, payload, attempts, next_attempt_at, state, last_error`) written in the same transaction as the domain row; the edge function drains it; retryable errors (429, 5xx, network) reschedule with exponential backoff; non-retryable (`UNREGISTERED`, `INVALID_ARGUMENT`) mark dead and clear the token. This is the single highest-value change and it needs a component that does not exist yet.

**2. `ttl: "30s"` on `reach` and `care` is data loss by design.** For `call`, 30s is defensible — a stale ring is worse than none (that's `ttl=0` reasoning). For a *Reach* or a care nudge it means: partner's phone is in a tunnel for 31 seconds → the nudge is discarded by FCM and never mentioned again. The `message` kind already got fixed to `86400s`; the same reasoning applies to `reach`/`care`. Use `ttl: "0s"` for `call` (documented "now or never", best latency, never stored) and a real TTL for everything else.

**3. No collapse keys.** Two calls in a row queue as two non-collapsible messages. Set `collapse_key` per logical stream — `"call:<couple_id>"`, `"msg:<couple_id>"` — so the newest supersedes the stale. Budget: **max 4 distinct keys per device**, and collapsible messages are throttled to **20 burst / 1 per 3 min refill**, so do not key per-message-id.

**4. `profiles.fcm_token` is a single column.** One token per user means a second device silently steals pushes from the first, and one device's `UNREGISTERED` nulls the token for all of them. Move to `device_tokens(user_id, token, platform, last_seen_at, created_at)` with a unique index on `token`; fan out to all rows; delete the row on `UNREGISTERED`.

**5. No delivery observability whatsoever.** Nothing records that a push was attempted, accepted by FCM, or acted on by the device. Minimum viable, entirely within the free tier: persist the FCM response `name` (message id) per outbox row, and have the Flutter background handler POST a one-row ack (`message_id`, `received_at`, `RemoteMessage.sentTime`, `RemoteMessage.priority`, `originalPriority`) — that gives you real end-to-end latency and, from `originalPriority != priority`, a direct read on whether Android is downgrading you. FCM's own BigQuery export needs the **Blaze** plan (Spark only gets the BigQuery sandbox), and the aggregated Data API is **7 days, lagging up to 5 days** — useless for debugging "my partner's phone didn't ring 20 minutes ago." Ship the client ack.

**6. `onDeletedMessages` is not handled anywhere.** With the 100-pending cap discarding *everything*, the only correct response is a resync-from-cursor. `firebase_messaging` exposes `onDeletedMessages` on some platforms unreliably — the durable substitute is what a couples app should have anyway: **a monotonic per-couple cursor and a catch-up fetch on every foreground**, which makes the entire class of push loss (force-stop, TTL expiry, collapse, 100-cap, Doze) recoverable on next app open. Some of this exists ("the catch-up fetch covers a dropped socket") — make it universal and cursor-based, not best-effort.

**7. Ordering: webhook vs. transaction.** A Supabase Database Webhook fires after the insert; if the function is cold or errors, nothing retries. `pg_net` from a trigger has the same problem plus known silent-failure reports. The outbox in (1) is what makes push delivery a *consequence of the committed row* rather than a side effect that may or may not happen.

**8. Foreground-service start on high priority.** `AndroidManifest.xml` already declares `USE_FULL_SCREEN_INTENT`, `WAKE_LOCK`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE_*`. Two checks to add: guard any FGS start behind `RemoteMessage.priority == PRIORITY_HIGH` (Signal's exact branch) to avoid `ForegroundServiceStartNotAllowedException` after a downgrade; and check `NotificationManager#canUseFullScreenIntent()` on Android 14+ — **Play revokes that permission at install for apps it doesn't classify as calling/alarm apps**, and a privately-distributed disguised app is a strong candidate for revocation. There is already an `FsiPermission` cache in the code; make the call path degrade to a high-importance notification with a `PendingIntent` when FSI is unavailable, and never `startActivity()` from the receiver (Android 12 trampoline block).

**9. Channel creation timing.** `FcmService.init()` creates the three channels at startup — good, that dodges the Android 13 trap where a channel first created in the background causes the notification to be dropped with no permission prompt until next open. Don't regress this.

**10. The disguise interacts with lock-screen privacy.** For a private couples app, set `setVisibility(VISIBILITY_SECRET)` on sensitive channels (nothing on the lock screen) or `VISIBILITY_PRIVATE` + `setPublicVersion()` with the disguised text. The data-only payload already ensures FCM never sees content; the lock screen is the remaining leak. Note the user can always override channel visibility.

## What does not transfer

- **A persistent websocket as the primary channel.** Signal and Telegram can afford a foreground-service-backed socket; Supabase Realtime free tier caps at **200 concurrent connections**. At 1,000 users that is oversubscribed by 5x on presence alone. Realtime must stay the *foreground* transport; FCM must stay the *background* transport. Do not attempt a Signal-style always-on socket.
- **Battery-optimization exemption as a strategy.** Google's own acceptable-use table lists "Real-time messaging app using FCM high priority" as **Not Acceptable** ("Use FCM instead"). Play policy prohibits it unless core function is affected. A private-distribution app escapes Play review, but the exemption still only buys network + partial wakelock during Doze — not jobs, not syncs, not alarms — and does nothing against force-stop or PowerGenie.
- **Any code-level fix for OEM killing.** Samsung/Oppo/Vivo/Huawei all catalogue as *"no known solution on dev end."* The transferable practice is what the big apps do: an onboarding screen that reads `PowerManager.isIgnoringBatteryOptimizations()`, `ActivityManager.isBackgroundRestricted()` (CDD §3.5.1 [C-1-6] makes this the one portable signal), `UsageStatsManager.getAppStandbyBucket()`, and `Build.MANUFACTURER`, then shows device-specific instructions and deep-links to the right settings screen. For the three phones in play — **IN2015 (OnePlus, 5/5 severity), Vivo (3/5), OnePlus 7 (5/5)** — this is not optional; OxygenOS is in the worst tier.
- **BigQuery-based delivery analytics** — Blaze plan required.

## Scale
## Where each piece breaks, and what it costs

**Supabase Realtime, free tier (DOCUMENTED — supabase.com/docs/guides/realtime/limits):** 200 concurrent connections, 100 messages/sec, 100 channel joins/sec, 100 channels per connection, 256 KB payload. Pro: 500 / 500 / 500 / 100 / 3,000 KB; Pro-without-spend-cap and Team: 10,000 concurrent, 2,500 msg/s. Errors are explicit — `too_many_connections`, `too_many_joins`, `too_many_channels`, `tenant_events` (which disconnects clients and lets supabase-js reconnect when throughput drops).

At **1,000 users / 500 couples**, if every foregrounded app holds one socket, you exceed 200 concurrent at roughly **20% simultaneous usage** — entirely plausible for a couples app at evening peak. **This is the first thing that breaks, and it breaks as user-visible "the app stopped updating."** Mitigations in order of cost: (a) close the socket on background and rely on FCM + catch-up fetch (free, and it is what you should do anyway); (b) one channel per couple rather than per-feature (channel count, not connection count, but it protects the 100-channels-per-connection ceiling); (c) Pro at $25/mo for 500 concurrent; (d) Pro without spend cap for 10,000.

The **2M realtime messages/month** budget is 66k/day. 500 couples exchanging 60 realtime events/day each = 30k/day — comfortable. Presence/typing indicators are what blow this up; they are high-frequency and low-value. Throttle or drop them before you pay.

**FCM itself does not scale-break.** It is free on Spark and Blaze, no per-message charge, no message cap. The project quota is **600k messages/minute** — four orders of magnitude above this app. The binding limits are per-device: **240/min, 5,000/hour**, and for collapsible messages **20 burst, +1 per 3 minutes**. A couples app hits these only via a bug (a retry loop, a trigger firing per-row on a bulk update). Guard the outbox with a per-device rate cap so a bug costs money in nothing but is also not silently throttled into invisibility.

**Edge Functions** are the operational risk, not the cost. The current design does one OAuth2 JWT signing + token exchange **per push** (`getAccessToken()` mints a fresh RS256 JWT with `exp: now + 3600` on every invocation). That is two extra network round trips and an RSA sign in the critical path of a ring. Cache the access token in module scope with an expiry margin — Deno isolates persist across warm invocations, so this is nearly free and cuts p50 latency measurably. Cold starts are the other tail: an outbox with retry makes a cold-start timeout survivable; the current fire-and-forget makes it a dropped call.

**Where the design stops being adequate:**
- Below ~200 concurrent: current architecture is fine once retry + outbox exist.
- 200–500 concurrent: needs Pro ($25/mo) **or** background-socket-teardown discipline.
- Multi-device per user: needs the `device_tokens` table before it works at all; today the second device breaks the first.
- Real delivery SLOs: needs client acks (free) — FCM's Data API lags up to 5 days and its BigQuery export needs Blaze.
- Devices with force-stop-on-swipe ROMs (OnePlus, Xiaomi, Huawei): **no amount of scaling or paying fixes this.** The cost is engineering time on an onboarding/diagnostics screen, and the ceiling is whatever fraction of users flip the toggles.

**Cost of the correct architecture on free tier:** an `outbox` table + a `device_tokens` table + a `push_acks` table are a few thousand rows/day at this scale — negligible against the 500 MB database allowance. The retry drain can run on the existing webhook path plus a `pg_cron` sweep for stragglers. Nothing here requires a paid tier except >200 concurrent realtime connections and BigQuery-based analytics.
