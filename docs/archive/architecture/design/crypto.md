# Encryption and key management for the Closer suite (private vault, fantasy jar, body map, memory threads, afterglow, time capsules) — Miles, Flutter + Supabase, com.miles.miles

## Current design
**What exists today, verified in source.**

One symmetric key per couple, derived live by ECDH between two device keys. `E:/LDR/mobile/lib/core/crypto_core.dart:98-107`: `X25519.sharedSecretKey(myKeyPair, partnerPub)` → `HKDF-SHA256(info='miles-closer-v1', salt=empty)` → 32 bytes held in the **static field** `CryptoCore._sharedKey`. AEAD is XChaCha20-Poly1305 (24-byte nonce, 16-byte Poly1305 tag). The private half is one X25519 seed, base64, in `flutter_secure_storage` under the fixed non-user-scoped name `'miles_x25519_priv_v1'` (crypto_core.dart:36). Public halves go to `public.partner_keys(user_id PK, public_key text, updated_at)` — `E:/LDR/supabase/partner_keys.sql` — which is the entire server-side key state. There is no ratchet, no per-item key, no key version, no escrow, no backup, no device concept, no revocation.

**Why this fails, and it is not a scale failure — it is broken at n=2.**

`android:allowBackup="false"` (`E:/LDR/mobile/android/app/src/main/AndroidManifest.xml:54`) means a reinstall or a new phone destroys the seed. `publishMyPublicKey()` (`supabase_repository.dart:151-170`) then upserts a *new* public key over the old row. The content key is a pure function of both private halves, so the moment the innocent partner next calls `ensureSharedKey()` they derive a different key and **every Closer row ever written becomes permanently undecryptable for both people**. Vault, fantasy jar, body map, memory threads, afterglow — all of it. There is no re-encryption path, so support cannot fix it.

The error message is worse than the loss. `keyWasReplaced` is a **process-local static** set only on the device that rotated (`supabase_repository.dart:142, 162-164`). The innocent partner's copy is `false`, so `closer_load_result.dart:39-42` renders "N items couldn't be opened — your partner may need to open Closer." That is factually false: it is never coming back.

The same root cause spawns the rest of the list, which is why patching them individually has failed:
- `CryptoCore.clearCache()` has **zero callers** (grepped across `lib/`) — the derived key outlives sign-out in a static.
- One keystore entry per *device*, not per account, so two accounts on one phone share one identity keypair.
- Three mutually incompatible envelope layouts coexist: `packMacAndCiphertext` = `mac||ct` (vault, memory threads, afterglow gratitude), `fantasy_jar_repository._pack` and `body_map_repository._pack` = `ct||mac` (opposite order, hand-rolled per repo), `packFull` = `nonce||mac||ct` (afterglow photos). `body_map_repository.dart:36-60` carries a fourth private copy of the key-derivation preamble.
- `CryptoCore.hmacTag()` is documented as HMAC-SHA256 and is actually **keyless 32-bit FNV-1a** (crypto_core.dart:179-187) over a **fixed 12-item public taxonomy** (`fantasy_jar_repository.dart:15-28`). Anyone with DB read computes all 12 tokens in a second and learns exactly which kinks each user selected.
- Fantasy "private from your partner" is `.eq('author', myId)` in Dart. Both partners hold the identical key and RLS is couple-wide, so the partner decrypts the other's entries with `associatedData = partnerId`.
- Body-map `x, y` are **cleartext `real` columns** (`intimacy_tables.sql:99-104`). The coordinates are the sensitive part; only the caption is hidden.
- Media: full-resolution JPEGs (`imageQuality:85`, no `maxWidth`) into `bytea`, fetched by `.select()` with no projection and no pagination on every screen open, shipped by PostgREST as a hex literal (~2x wire).
- Storage posture is obscurity, not policy. `couple_media` is a **public** bucket accessed with `getPublicUrl` (`chat_repository.dart:157,165,266`; `home_screen.dart:132`; `settings_screen.dart:59`; `chat_theme_picker.dart:37`). `couple_media`, `couple_intimate` and `chat-bg` have **no DDL anywhere** in `E:/LDR/supabase` — only `capsule-media` is created (`capsules.sql:110`). `touch_map_screen.dart:601` mints a 1-hour signed URL to an intimate photo and puts it on a broadcast payload; **there is not a single `private: true` channel in the client** (grepped), so `touch:<coupleUuid>` is joinable by any JWT holder who knows the couple UUID — and `hardening_2026_08.sql:24-25` itself records that couple UUIDs are not secret.
- Retention is a label. `retention='ephemeral'` writes `reconfirm_due = now()+90d` and nothing reads it; `deleted=true` and `state='deleted'` never hard-purge. The only `cron.schedule` calls in the whole SQL tree are `breath_events.sql:37` and `reach_pulses.sql:34`. The 14-day mutual-delete window is computed on the **device clock**.
- Account deletion looks broken for exactly the couples that used Closer. `delete_my_account()` (`account_deletion.sql:57`) deletes `auth.users` → cascades to `profiles`; but `vault_items.created_by/delete_requested_by/deleted_by` (`intimacy_tables.sql:79,84,87`), `memory_threads.accepted_by` (:137) and `:155 initiated_by` reference `profiles(id)` with **no ON DELETE clause**, and when the partner remains (`v_others > 0`) the couple and its rows survive. That should raise a foreign_key_violation. *This one is a source-read inference — I did not execute it; it needs a 60-second repro against a local `supabase start`.*

## Target architecture
**The single mechanism: content keys are WRAPPED, never DERIVED.**

Every bug above descends from one decision — content is encrypted under `f(deviceA_priv, deviceB_pub)`. Invert it. Content is encrypted under a random key that exists as N independently sealed copies. Losing a device removes one copy. That removes reinstall loss, new-phone loss, partner-coupled loss, sign-out leakage, the two-accounts-one-device collision, and the "app must be open" dependency in one move.

**Key hierarchy — four levels, one job each.**

- **DK — Device Key.** Per (device, account). X25519 for wrap/unwrap plus Ed25519 for signing. The X25519 seed is generated with `Random.secure`, sealed under an AES-GCM key held in the Android Keystore (StrongBox where available), and the sealed blob stored on disk. Never leaves the device, never wrapped to anything, never backed up. Replaces `'miles_x25519_priv_v1'`, which is keyed per device rather than per account.
- **IK — Identity Key.** Ed25519, per *user*. Signs the user's device list. This — and only this — is what the safety number hashes over. IK is itself wrapped into the recovery envelopes, so a recovered user keeps their identity and the safety number does not change. A user who re-bootstraps with no recovery path gets a new IK, which is the loud event.
- **CRK — Couple Root Key.** 32 random bytes, minted once at couple formation by the first device. Never derived, never transmitted in the clear. Derives epoch keys and the fantasy tag-HMAC key.
- **PK_u — Personal Key.** 32 random bytes per user. Wrapped **only** to that user's own DKs and that user's own recovery credentials — never to the partner. Encrypts fantasy-jar text and personal-vault content. This is what makes "private from your partner" a key-possession fact instead of a Dart filter.
- **DEK — Data Encryption Key.** 32 random bytes per item / per storage object. Wrapped under `EK_n` (couple content) or `PK_u` (personal content); the wrap lives in the row next to the ciphertext.

**Epochs.** `EK_0 = HKDF(CRK, "epoch-0")`. Rotation follows Labyrinth: `EK_{n+1} = HKDF(EK_n || fresh_entropy, "epoch-" || n+1)` — the new root needs the previous root *and* new entropy, so a device holding only `EK_{n+1}` cannot walk backwards. Rotation happens **only on explicit user action** ("reset shared history", breakup, stolen phone), never automatically on device add/remove. Old epochs are not re-encrypted; surviving devices simply keep their old epoch keys in their keyring.

**Data model — three new tables, all holding ciphertext or public material only.**

```
devices(device_id pk, user_id, x25519_pub, ed25519_pub, sig_by_ik,
        state 'pending'|'active'|'revoked', label, created_at, last_seen_at)
couple_epochs(couple_id, epoch int, created_at, created_by_device)
key_wraps(couple_id, epoch, key_kind 'crk'|'pk', key_owner uuid,
          recipient_kind 'device'|'recovery', recipient_id,
          wrapped_blob bytea, wrapped_by_device, created_at,
          pk(couple_id, epoch, key_kind, key_owner, recipient_id))
recovery_credentials(id pk, user_id, kind 'code'|'platform_vault'|'partner',
                     pub_x25519, enrolled_at, revoked_at)
key_requests(id pk, couple_id, requester_user, requester_device,
             pake_commitment bytea, attempts int, state,
             expires_at timestamptz)  -- server-set, default now()+15min
```

`wrapped_blob` is a sealed box: ephemeral X25519 → HKDF → XChaCha20-Poly1305 over the 32-byte key, AD = `(couple_id, epoch, key_kind, key_owner, recipient_id)` so a wrap cannot be replayed into another slot. RLS: a user reads `key_wraps` rows whose `recipient_id` is one of their own non-revoked devices or credentials; a user inserts wraps only for a `recipient_id` belonging to their own couple. **The server never holds a key, and no combination of rows it can read produces one.**

**Storage — private by construction.**

Object bytes are XChaCha20-Poly1305 ciphertext under a per-object DEK, always. Object path is 32 random bytes — no couple id, no user id, no date, no extension (today it is `<coupleId>/body/<uid>_<ms>.jpg`, which is why `hardening_2026_08.sql` had to note couple UUIDs are not secret). The couple → object mapping and the wrapped DEK live in an RLS-gated row. Consequence: a public bucket, a leaked signed URL, a CDN edge entry that outlives its token, and a stolen service-role key are all equivalent to holding random bytes. That makes it *correct* to serve the bytes from a public bucket with a one-year TTL — which is also the cheaper option, because Supabase private buckets check permissions per object per user and therefore bill as **uncached** egress at $0.09/GB (research/supabase.md:155, 318). Size still leaks; pad to PADMÉ-style buckets. Media leaves `bytea` entirely — `bytea` holds text and metadata only, ≤4 KB.

**A URL is never a capability.** Broadcast payloads and push payloads carry an opaque object id; the receiver resolves the row under RLS and downloads. Every channel is created `private: true` with an RLS policy on `realtime.messages` scoped to couple membership. That closes touch, touch_trace, mood_lamp and capsule_proximity in one change.

**Device state machine.**

`absent → pending → active → revoked`. A new install generates DK, inserts a `pending` device row, and then tries, in order: (1) platform vault entry, (2) user-entered Recovery Key, (3) partner-assisted re-wrap, (4) give up. **Registration is additive: it never updates or deletes any existing wrap row, and no server path can.** Four honest outcomes, differing in exactly what is restored:

| Path | IK | Safety number | Couple history | Personal content |
|---|---|---|---|---|
| Platform vault (Block Store / iOS Keychain) | restored | unchanged | readable | readable |
| Recovery Key (40 chars) | restored | unchanged | readable | readable |
| Partner-assisted re-wrap | **new** | **changes** | readable | **lost** |
| Nothing | new | changes | empty | empty |

Partner-assisted restores CRK but not PK_u, because the partner was never given a wrap of PK_u. That is the design working, not a gap — and it is the argument for making Recovery Key enrolment mandatory.

**Partner-assisted re-wrap sequence — deliberately slow, polled, and row-driven.**

1. A's new device inserts a `key_requests` row with a PAKE commitment. `expires_at` is set by a column default from server `now()`.
2. B is hinted by a payload-free FCM data message and by the private couple channel. **Both are hints.** The row is the source of truth and is read on app open. Nothing here is latency-sensitive — setting up a new phone is a deliberate moment, so the flow is designed to work when the socket does not, when the app is backgrounded, and on OEM ROMs that defer wakeups indefinitely.
3. Both screens show the same **6-digit code**, compared out of band (they are a couple — a phone call). CPace PAKE over that code, **3 attempts**, the request row is destroyed on the third failure. The code is never sent; a malicious server cannot stand in the middle.
4. On success B's device wraps CRK for every epoch it holds to the new DK's X25519 public key and inserts the wrap rows. B's own rows are untouched throughout.

**Key-change state machine — ported from `SignalBaseIdentityKeyStore.java`, not reinvented.** Local SQLite (`identities`), never server-side: the server has no business knowing trust state. `isTrusted(peer, key, RECEIVING)` returns **true unconditionally**. Send is gated on: key mismatch, `UNVERIFIED`, or `!approved && !first_use && now - changed_at < 5s`. On change: `VERIFIED`/`UNVERIFIED` both collapse to `UNVERIFIED`, a permanent transcript row is inserted, sessions are archived not deleted. Safety number is the WhatsApp/Signal construction verbatim — sort the peer's device identity keys, iterate SHA-512 over `(sorted_keys || user_id)` **5,200** times, take 30 bytes, six 5-byte big-endian chunks mod 100000, per-conversation 60-digit number = both 30-digit fingerprints sorted-concatenated. Under 1 ms on the IN2015 (research/e2ee.md:192). Plus **cross-signing**: after an in-person comparison each device signs the partner's IK and stores the signature locally, so a substituted key fails a signature check instead of raising an advisory a user can swipe away.

**Two events, not one.** "Sam added a new device" (IK unchanged, signature chain valid) is routine and non-blocking. "Sam's safety number changed" (new IK) is permanent, in-thread, and gates sending. The current app has neither.

**Encrypted vs. not.** Encrypted: vault note text and photo bytes and filename; fantasy text (under PK_u); **body-map x,y** — moved inside the ciphertext, the `real` columns dropped after backfill; memory title/note/photo and exact date; afterglow gratitude and photo; **capsule item text and media**, which today are wholly plaintext. Fantasy tags become `HMAC-SHA256(HKDF(CRK,"fantasy-tags-v2"), normalized_tag)` truncated to 16 bytes — opaque and non-enumerable without CRK, replacing keyless FNV-1a over a public 12-item list.

Cannot be encrypted, and must be published as a list rather than assumed to be nothing: row existence and count, `couple_id`, `author`, `created_at`, item `kind`, ciphertext length (padded, not hidden), storage object size and access time, realtime topic names and join timing, push timing, IP. Two deliberate leaks with a stated reason: a coarse `happened_month` for timeline ordering and pagination, and the `retention` class in cleartext — because the *server* enforces purge and cannot act on a value it cannot read.

**Retention and purge.** One `purge_expired()` SECURITY DEFINER function on `pg_cron`, hourly, driving off server `now()` only. Every retention timer is an `expires_at timestamptz` set by a column default or trigger, never accepted from a client. A `storage_ledger(object_path, couple_id, expires_at)` table lets purge delete the row and the object in one transaction; a nightly sweep over the previous month's partition reaps objects with no ledger row (that is what finally collects `<coupleId>/reactions/*`, which accumulates forever today). And because every object carries a wrapped DEK in a row, **destroying the wrap is the delete** — the object is unreadable at that instant, before the byte purge runs, regardless of the documented 60-second CDN invalidation delay and the fact that expiring a signed URL does not purge its cache entry.

## Invariants
- **Content keys are wrapped, never derived.** No Closer plaintext is ever encrypted under a key that is a function of two live device private keys. Every content key traces to one 32-byte CRK that exists on the server only as N independently sealed ciphertexts. Therefore the number of devices that must survive for the couple's data to survive is one, not two — and it is never a *specific* one.
- **Device registration is additive-only.** Publishing a device key INSERTs rows; it never UPDATEs or DELETEs a `key_wraps` row, and no server code path is granted permission to. Therefore one partner reinstalling cannot make the other partner's history unreadable, because the other partner's readability depends only on their own wrap row, which nothing touched.
- **Every wrap is bound to its slot by AEAD associated data** `(couple_id, epoch, key_kind, key_owner, recipient_id)`. Therefore a wrap row copied, replayed, or moved into another slot by a malicious server or a compromised client fails to open — the server can withhold a wrap (a detectable denial of service) but can never redirect one.
- **Every expiry and consent window is evaluated against `now()` inside a SECURITY DEFINER function, and no expiry timestamp is ever accepted from a client.** Therefore a wrong, skewed, or hostile device clock cannot advance a mutual-delete window, expire a signal early, or hold one open for ten years — which is exactly what the current client-clock 14-day vault window and client-chosen `window_expires_at` permit.
- **The trust decision gates SENDING only.** `isTrusted(peer, key, RECEIVING)` returns true unconditionally. Therefore a key change can never cause silent inbound loss; the worst reachable outcome is 'approve before you speak', never 'you never heard them'.
- **Verified status is monotonically downgradable and never automatically upgradable.** On an identity-key change, VERIFIED and UNVERIFIED both collapse to UNVERIFIED, a permanent transcript row is written, and sessions are archived rather than destroyed. Only a human comparing a safety number restores VERIFIED.
- **Every byte at rest outside Postgres is ciphertext under a key that is not in the storage service's trust domain.** Therefore a public bucket, a leaked signed URL, a CDN entry that outlives its token, and a stolen service-role key are all cryptographically equivalent to holding random bytes — privacy stops depending on the secrecy of a URL or a couple UUID.
- **A URL is never a capability.** Nothing that grants read access to bytes is ever placed on a realtime payload, a push payload, or any row a non-member can read; references are opaque object ids resolved under RLS. Combined with `private: true` on every channel, knowing a couple UUID grants nothing.
- **Destroying the wrapped DEK IS the delete.** An item is unreadable the instant its wrap row is removed, independent of CDN caches, read replicas, WAL, and backups already taken — so 'delete' is honest even though the bytes take up to an hour to disappear.
- **Author-scoped content is encrypted under a key the partner's devices have no wrap of.** There is no `key_wraps` row with `key_kind='pk'`, `key_owner=A`, `recipient` belonging to B. Therefore 'private from your partner' is enforced by key possession, not by `.eq('author', myId)` in Dart.
- **Tag tokens are keyed by a per-couple secret.** `HMAC-SHA256(HKDF(CRK,'fantasy-tags-v2'), tag)` cannot be enumerated by anyone without CRK, so a 12-entry taxonomy is no longer a rainbow table. The residual — a partner CAN enumerate, because overlap computation requires a shared key — is a published limitation, not a claim.
- **Recovery credentials are enrolled, individually revocable objects, and the server holds no oracle for any of them.** Revoking one is deleting its wrap rows; it does not affect the others, and none is an implicit backdoor. There is no server-side guess counter anywhere in the design, because a Postgres row holding `attempts_remaining` is restorable from backup and provides zero cryptographic guarantee (research/e2ee.md:210).
- **Devices per user are capped at three, server-enforced.** The fourth registration is refused with 'remove a device first' rather than silently ignored. This bounds wrap fan-out at `devices × epochs` and prevents the partial-history failure mode where a single historical epoch's only surviving wrap sits on a dead phone.
- **Every field the server can read is declared in `E:/LDR/docs/architecture/metadata-exposure.md`, and CI fails if a Closer table gains a non-encrypted column with no entry.** What the operator can observe is enumerated and published rather than assumed to be nothing.

## Why this mirrors the top tier
**Meta Labyrinth** is the closest mirror and the primary source. The envelope model — a root key distributed as per-recipient wrapped material rather than derived, with `epochRootKey = kdf(newEpochEntropy, epochChainingKey, "epoch_root_key")` and only the 32-byte entropy ever shared — is taken directly (research/e2ee.md:108-115, 263). So is the recovery-object model: five independently revocable mechanisms, one Virtual Device each, so revoking one does not revoke the others (:123, :157). So is the recovery-code encoding, verbatim on research/e2ee.md:212's explicit recommendation: 40 characters, 1 version + 1 identifier + 34 entropy + 4 ECC over GF(32), constrained alphabet with B/G/I/O folded to 8/C/1/0 — that ergonomic choice is the difference between a recovery key people can use and one they cannot.

**Three deliberate differences from Labyrinth.** (1) No epoch rotation on device change — only on explicit user action. Meta publishes that "epoch rotation has not yet been implemented on device removal" (:125) and we would be inheriting the complexity for a case that barely occurs in a two-person app. (2) We drop the PIN-in-vault tier entirely; there is no enclave and no rollback-proof guess counter on this stack (:210). (3) We **add** a tier Labyrinth does not have — partner-assisted re-wrap. A couples app has a second human who is already trusted with the plaintext, so the partner is a better escrow than any HSM, is free, is zero-knowledge to the server, and covers the modal event of one phone being replaced at a time. That is the one place this design is genuinely better fitted than the systems it copies.

**Signal** supplies the key-change state machine, ported exactly from `SignalBaseIdentityKeyStore.java` (:23-45, :245): `isTrustedIdentity(..., RECEIVING)` unconditionally true, send-side gate, `TIMESTAMP_THRESHOLD_SECONDS = 5`, automatic VERIFIED→UNVERIFIED downgrade, `markIdentityUpdate` writing a permanent transcript event, `archiveSiblingSessions` archiving rather than deleting. Deliberate difference: we do **not** copy the prekey machinery — X3DH/PQXDH pools, `BATCH_SIZE = 100`, `ONE_TIME_PREKEY_MINIMUM = 10`, Sesame session convergence. Those exist to establish an asynchronous session with a stranger who may never have been online at the same time. This product has no strangers; a couple is a fixed two-party relationship and the wrap is performed once. Skipping them also skips the Prekey Pogo attack surface (:19, :166) and the Kyber storage blow-up the research prices at 1.6 GB for 10k users (:223).

**WhatsApp/Signal** supply the safety number verbatim: 5,200 iterated SHA-512 over sorted identity keys plus user identifier, 30 bytes, six 5-byte chunks mod 100000, per-conversation 60-digit (:47-54, :259). Deliberate difference: we add cross-signing after in-person verification (:216), which for a two-person topology is strictly stronger than what key transparency gives Signal users who never compare numbers — and it costs about fifty lines against a KT server, prefix trees, a Monitor endpoint and a third-party auditor relationship (:235).

**Apple iCloud Keychain** supplies the per-device-wrap shape and the cleanest statement of the trade-off (:130). **Signal Secure Backups** supplies the media discipline — encrypt the already-encrypted file again and pad it to obscure its true size (:144) — and the honest pre-emptive wording: "Losing it means losing access to your backup permanently, and Signal cannot help you recover it."

**What we deliberately refuse to copy: SVR2/SVR3 and the WhatsApp HSM Backup Key Vault.** Every one reduces to a tamper-evident device that destroys a secret after N wrong guesses and cannot be rolled back. Research/e2ee.md:210 is unambiguous that this cannot be built on Supabase, and :233 states there is no scaled-down version — SVR3's $0.0025/user/year assumes amortisation over 500M users across three vendors' confidential-compute SKUs. We take the escape hatch both vendors themselves ship: the user-held high-entropy key with no server component (:103, :212).

## Scale ceiling
**Key material is O(devices), not O(messages) — it is never the bottleneck.** Per user: one device row (~200 B of public keys and signatures) and at most 4 wrap rows (~120 B each). At 100k users with the 3-device cap that is ~200k device rows plus ~600k wrap rows ≈ 150 MB. Contrast the prekey path we rejected, which research prices at ~1.6 GB for 10k users on Kyber pubkeys alone (research/e2ee.md:223) — enough to blow the free-tier database on prekeys.

**1k users (500 couples).** No crypto-attributable ceiling. Everything is client-side; the only server work is inserting wrap rows. Failure mode: none.

**10k users (5k couples).** First pressure is the hourly `purge_expired()` job and the storage orphan sweeper. With partial indexes on `(expires_at) where not deleted`, deleting ~10k rows/hour is nothing; the sweeper comparing `storage.objects` against the ledger is the part that degrades. **Failure mode at the ceiling: the sweeper's full scan runs long enough to overlap its next invocation and pile up, holding locks on `storage.objects`.** Designed-in fix, applied before it bites: partition the ledger by month and sweep only the previous partition.

**100k users (50k couples).** The ceiling is **media egress and storage, not cryptography**. Research/supabase.md:277-278 prices 2 TB of private media at $157.50/mo uncached egress plus $40/mo storage and rising. Encrypting the bytes lets them live in a public bucket with a one-year TTL, converting most of that to cached at $0.03/GB. **Failure mode at the ceiling: a bill, not a correctness break** — which is the right kind of ceiling to have.

**The one genuine cryptographic ceiling, named honestly.** Wrap fan-out is `devices × epochs` per couple. A couple that accumulated many devices over many epochs would need a device holding `EK_n` to be online to mint `EK_{n+1}`, and an epoch whose only surviving wrap sat on a dead phone becomes an unreadable *slice* of history — partial loss, which is more confusing to a user than total loss. Two structural mitigations: devices per user capped at 3 and enforced server-side (the 4th registration is refused, not silently dropped), and epochs rotated only on explicit user action rather than on every device change. With those, a couple's maximum is 6 devices × a handful of epochs — tens of unwraps at first unlock, milliseconds.

**The residual permanent-loss cohort, quantified.** Today, research/e2ee.md:231 estimates ~2% of users replace a phone monthly with no backup; at 50k couples that is **~1,000 destroyed couple histories per month, each destroying it for both people**. Under this design a history is lost only when *both* devices die inside the same window *and* the Recovery Key was never enrolled *and* no platform-vault entry survived. If dual-loss is ~0.05% of couples per month (≈25/mo at 50k), Recovery Key enrolment is 40%, and platform-vault coverage is 85%, the residual is ~25 × 0.6 × 0.15 ≈ **2 per month**. That is the delta the whole design buys: roughly 1,000/mo → 2/mo. If Recovery Key enrolment is made mandatory to enable Closer, it goes to approximately zero.

**Explicitly stated ceiling that is not a bug:** total loss of every authenticator is terminal by design, and the product must say so on the setup screen *before* the fact rather than in a support reply after it.

## Cost
**Assumptions, stated so they can be argued with:** 2 users per couple; 40% of couples enable Closer; per active Closer couple 15 photos/month at 900 KB after a client-side resize to 1600px long edge, plus 40 text items; reads ≈ 3× writes. Supabase Pro $25/mo base, 8 GB disk then $0.125/GB, 100 GB storage then $0.0213/GB, 250 GB egress then $0.09/GB uncached and $0.03/GB cached.

**1,000 users (500 couples, 200 Closer).** New media 2.7 GB/mo → ~32 GB in year one. Storage: inside the 100 GB allowance, **$0**. Egress ~8 GB/mo, inside 250 GB, **$0**. Key rows ~2k devices + 6k wraps ≈ 1.5 MB. Edge Function invocations for push dispatch and wrap rate-limiting ≈ 2k/mo against Pro's 2M. **Crypto-attributable cost: $0/mo.** The migration is cost-*negative* — those same 32 GB currently go into Postgres `bytea`, which exceeds Pro's 8 GB disk in about three months and then bills $0.125/GB (~$4/mo and climbing) while riding in every database backup.

**10,000 users (5k couples, 2k Closer).** New media 27 GB/mo → ~324 GB year one. Storage overage (324−100) × $0.0213 = **~$4.80/mo** at year end. Egress ~81 GB/mo, inside 250 GB, **$0**. Key rows ~20k devices + 60k wraps ≈ 15 MB. **Crypto-attributable cost ≈ $5/mo**, against a total bill research/supabase.md:267 puts at ~$70–110/mo.

**100,000 users (50k couples, 20k Closer).** New media 270 GB/mo → ~3.2 TB year one. Storage (3,200−100) × $0.0213 = **$66/mo**, rising ~$5.75 each month. Egress ~810 GB/mo, 560 GB over allowance: **$50/mo if private/uncached, $17/mo if public-bucket-cached**. Encrypting the bytes is what makes the cached path safe, so the encryption choice **saves ~$33/mo at this scale and grows**. Key rows ~150 MB ≈ $19/mo of Pro disk. **Crypto-attributable cost ≈ $85/mo**, against a total the research puts in the $700–1,100/mo band.

**The counterfactual, priced.** The escrow designs this rejects are not expensive at scale — they are expensive at *any* scale, because the cost is fixed. A single enclave-capable instance (m5.xlarge class) is roughly **$140/mo**; SVR3's actual design needs three across separate vendors for its security claim, so **$400–1,500/mo minimum**. At 1,000 users that exceeds the entire Supabase bill, which research/supabase.md:264 puts at ~$58/mo. Research/e2ee.md:233 states it plainly: "There is no scaled-down version of this design: the fixed cost is the fixed cost."

**Client CPU, for completeness.** Per-item XChaCha20-Poly1305 on a 32-byte DEK, one sealed-box unwrap per key at unlock, and 5,200 SHA-512 iterations for a safety number — under a millisecond on the IN2015 (research/e2ee.md:192). No Argon2, because there is no PIN. **$0.**

## Migration
**A design requiring a bulk re-encrypt would be a failed design. This one never re-encrypts in a batch — legacy rows are re-wrapped lazily, by whichever device can still read them, and the app works with a mixed-version partner at every stage.**

**Stage 0 — stop the bleeding. No crypto change, no data migration, ships alone.**
`private: true` on every channel plus an RLS policy on `realtime.messages` scoped to couple membership; today there is not one private channel in the client, so `touch:<coupleUuid>` and `capsule_proximity:<coupleUuid>` are joinable by any JWT holder. Stop putting signed URLs on broadcast payloads (`touch_map_screen.dart:601`); broadcast the object id. Add DDL for `couple_media`, `couple_intimate` and `chat-bg` to `E:/LDR/supabase` — three live buckets currently have no definition anywhere. Fix the missing `ON DELETE` on `vault_items.created_by/delete_requested_by/deleted_by`, `memory_threads.accepted_by` and `memory_revisits.initiated_by` so `delete_my_account()` stops throwing. Fix the proximity-unlock authorization gap (`capsules.sql:91-95` validates the date only for modes `date` and `both`, so a proximity capsule opens from anywhere). Every item here is independently revertible.

**Stage 1 — introduce the CRK alongside the derived key. Dual-read, no migration.**
Add `devices`, `couple_epochs`, `key_wraps`, `recovery_credentials`, `key_requests`. On first launch of the new build a device that can still derive the legacy shared key mints CRK, wraps it to its own DK and to every registered partner device, and sets `couple_epochs.epoch = 1`. Reads try the epoch key first and fall back to `CryptoCore._sharedKey`; the existing all-zero-nonce legacy plaintext detection is untouched, so pre-2026-08 rows keep reading. Writes use the CRK. Old partner builds are unaffected because nothing about `partner_keys` changes.

**Stage 2 — lazy re-wrap, rate-limited, in the background.**
Any device that can still derive the legacy key re-encrypts old rows under the CRK, oldest-first, tracked by a per-couple `legacy_rows_remaining` counter shown as a quiet progress state. This is the *only* remaining window in which the old loss bug applies, and it shrinks monotonically. When the counter hits zero, drop the legacy path. Couples where one side has already lost their key: those rows are unrecoverable *today* — mark them `undecryptable` with honest copy and stop showing "your partner may need to open Closer" (`closer_load_result.dart:39-42`), which is false.

**Stage 3 — recovery enrolment. Three independently shippable pieces, in this order.**
(a) **Partner-assisted re-wrap** first: highest coverage, zero user homework, and it is the tier the research's sources do not have and a couples app does. (b) **Platform vault** (Android Block Store / iOS Keychain) — covers same-device reinstall and Android device-to-device transfer, the statistically largest cohort (research/e2ee.md:181). (c) **Recovery Key** — 40 chars with ECC, shown once, confirmed by typing back four randomly chosen positions. Note for (b): on Android, unlike iOS, app data including EncryptedSharedPreferences *is* deleted on uninstall, so Labyrinth's "persists across uninstalls" keychain trick does not transfer for free — Block Store is the correct analogue and its current entry-size and count limits must be verified before committing. Do **not** re-enable app-wide `allowBackup`; that undoes the disguise posture.

**Stage 4 — media out of Postgres.**
New writes go to Storage under a per-object DEK with a 32-byte random path. Old `bytea` rows migrate lazily on read: decrypt → upload encrypted → write the object id → null the `bytea`. Simultaneously add column projection and pagination to every Closer fetch — `fetchItems()` and `fetchThreads()` currently do a bare `.select()` that downloads every photo the couple has ever saved on screen open.

**Stage 5 — schema tightening.**
Body-map `x, y` move inside the ciphertext; the `real` columns stay until backfilled, then drop. Fantasy text moves under `PK_u`; tag tokens move to the keyed HMAC (old FNV tokens are recomputed during the Stage-2 re-wrap the device is already doing). Capsule items get encrypted. Retention columns become server-set `expires_at`; `purge_expired()` goes on `pg_cron`; the storage ledger and orphan sweeper land.

**Stage 6 — safety numbers and the key-change state machine.**
Last, because it hashes over a stable device list that only exists after Stage 1 and only matters after Stage 3. Ship the safety-number screen, the QR, cross-signing, the transcript event, and the send-side gate together.

Stages 0, 1, 3a, 3b, 3c, 4, 5 and 6 are each independently shippable and independently revertible. Only Stage 2 depends on Stage 1.

## Verification
**The premise: make the crypto a pure function of state, then test the state machine instead of the devices.** Every previous fix passed on two NTP-synced phones on one wifi because that configuration exercises exactly one path through a state machine with dozens.

**1. A deterministic key-lifecycle simulator in `test/`, with property tests.** Model devices as plain objects; inject a fake keystore and a fake Supabase (an in-memory table set that enforces the same RLS predicates as the real policies). Then random-walk the event alphabet: `{addDevice, loseDevice, reinstall, recoverByPartner, recoverByCode, recoverByPlatform, rotateIdentity, revokeDevice, rotateEpoch, writeItem, readItem, purge}`. **One asserted property:** for every item written at time *t*, and every device *d* that is a couple member at *t' > t* holding at least one surviving recovery credential, `read(d, item)` succeeds. Ten thousand seeds in CI. This test fails on seed 1 against today's code — the two-event sequence `{reinstall(A), readItem(B)}` violates it — which is precisely the evidence that was never gathered.

**2. Golden vectors, checked in.** `(CRK, device keys, plaintext) → expected wrap and envelope bytes`. There are currently **three mutually incompatible packing layouts** in the codebase (`mac||ct`, `ct||mac`, `nonce||mac||ct`); a golden-vector test makes a fourth impossible to add silently. Additionally, a compat gate that decrypts vectors generated by the *previous release binary* — that is what catches a refactor that changes the format for existing users.

**3. Two isolates, one process, for "two phones".** Partner-assisted recovery is two state machines exchanging messages. Run both in one test connected by a channel the test fully controls: it drops, reorders, duplicates and delays messages, and advances each side's clock independently. Every condition the brief forbids depending on becomes a scripted scenario — partner offline for three days, app killed mid-PAKE, socket dead but HTTP alive, clocks eight hours apart, the same approval delivered twice.

**4. Clock-skew testing is free, because the invariant forbids client clocks — so assert the invariant mechanically.** A CI query over `information_schema.column_privileges` that fails if any Closer table exposes a client-writable timestamp column used in an expiry predicate. That is a static check that no future commit can regress, and it is strictly better than trying to reproduce skew on hardware.

**5. RLS tests in SQL against a local `supabase start`.** For every Closer table, as three roles: user A, partner B, and stranger C holding a valid JWT *and knowing the couple UUID*. Assert C reads zero rows everywhere, and assert **B reads zero rows from `fantasy_jar_entries` text and `personal_vault_items`**. That last assertion is the one the current implementation cannot pass, and it is the whole product promise of the Fantasy Jar.

**6. Storage posture as an executable assertion.** A CI query asserting `select id, public from storage.buckets` matches a checked-in expected map — which also fails today, because three live buckets have no DDL at all. Plus a test that fetches an object's public URL **unauthenticated** and asserts the first bytes are not a JPEG magic number, i.e. proves the bytes on the wire are ciphertext. That single test is the durable proof that privacy no longer depends on URL secrecy.

**7. A channel-privacy assertion.** A grep-level CI check that every `.channel(` call site passes `private: true`, plus an integration test where a stranger JWT joins `touch:<known-uuid>` and asserts the join is rejected.

**What still needs hardware — and it is one phone, not two, not two networks.** Does the Keystore-sealed device key survive an app upgrade, a force-stop, and a reboot on the IN2015, the Vivo and the OnePlus 7? Three devices, three reboots, one afternoon, and it is the only claim in this design that a simulator cannot make.

## Rejected alternatives
**Server-side escrow with a Postgres guess counter.** Rejected on research/e2ee.md:210, which is categorical: a row holding `attempts_remaining` is decremented by code you control, restorable from a nightly backup, and readable by anyone with the service-role key — "It provides *zero* cryptographic guarantee." Every escrow design in the corpus (SVR2/SVR3, the WhatsApp HSM vault, iCloud Keychain) reduces to a tamper-evident device that destroys the secret after N guesses and cannot be rolled back: Signal uses in-memory Raft across enclave replicas specifically so an operator cannot restore an old counter from a replica; Apple destroyed the HSM admin cards. We have none of those. Building the shape without the substrate is security theatre.

**PIN-based recovery (Signal SVR shape).** Rejected as a consequence of the above — a PIN's only job is to gate a rollback-proof oracle, and without one a 4-digit PIN is a 10,000-entry offline break. The app already demonstrates the failure twice: Memory Threads stores `'fnv1a:<32-bit>'` (its own comment admits it is not a KDF) and the app-lock PIN is unsalted SHA-256 in plaintext SharedPreferences.

**pgsodium / Transparent Column Encryption.** Rejected: Supabase documents pgsodium as pending deprecation and explicitly advises against Server Key Management and TCE on their platform (research/e2ee.md:273). It also is not end-to-end — the server holds the key.

**Full Signal protocol (Double Ratchet, X3DH/PQXDH prekey pools, Sesame) for Closer.** Rejected on a category error, not on cost. Closer is a shared mutable *store*, not a message stream. A ratchet provides forward secrecy per message, which is actively wrong for content whose entire purpose is to be re-read in three years — it is a deletion mechanism dressed as a security property. Prekey pools solve asynchronous session establishment with a stranger, and this product has no strangers. Skipping them also avoids the Prekey Pogo drain-and-oracle surface (research/e2ee.md:19, :166) and the Kyber pool storage blow-up priced at 1.6 GB per 10k users (:223). Keep the ratchet for chat if chat wants it; Closer needs an envelope.

**WhatsApp's per-device identity key with Account Signature, Device Signature and a signed device list.** Rejected for now on research/e2ee.md:218 — "For two people with two phones, Signal's model. If you ever add a tablet or web client you actually want to revoke, WhatsApp's." The wrap-based content model is orthogonal and survives either choice, so this is a cheap decision to defer rather than a fork.

**Key transparency (log tree, prefix trees, Monitor endpoint, third-party auditor).** Rejected on research/e2ee.md:216 and :235. KT exists to *approximate* out-of-band verification for users who cannot meet. These two users share a bed. In-person safety-number comparison plus cross-signing gives a strictly stronger local guarantee for about fifty lines, against a dedicated service and an auditor relationship.

**Keeping media in `bytea`.** Rejected: unbounded blobs in a 500 MB free / 8 GB Pro database, ~2× wire inflation through PostgREST's hex encoding, a full-table fetch of every photo on screen open, and permanent residence in every database backup. Encrypted objects in Storage are cheaper, pageable, purgeable, and CDN-cacheable.

**Re-encrypting all history on breakup or device compromise.** Rejected as a big bang. Epoch chaining plus crypto-shredding delivers the same product outcome — the revoked party cannot read new content, and deleted content is unreadable immediately — without a bulk re-encrypt that would take hours, need both devices online, and be unresumable.

**Encrypting `couple_id`, `author`, `created_at` or the retention class.** Rejected: RLS predicates and the purge job need them. Encrypting them moves authorization into the client, which is the exact bug class already present in five features (fantasy privacy, desire-temp reveal, dice tier consent, modest mode, the vault 14-day window). Better to leak them deliberately and publish the list.

**Private Set Intersection for fantasy-tag overlap.** Rejected as disproportionate. The honest fix is changing the product copy to match what a shared key can actually promise.

## Open decisions
**1. Is Recovery Key enrolment mandatory to enable Closer?** *Recommend: yes.* Show the 40-character code once, require the user to type back four randomly chosen positions. The alternative is a support queue you cannot serve — you have no key, so "I lost everything" has no reply. Closer is already opt-in, so the friction lands on exactly the users whose data justifies it. Accept that some users will not enable Closer; for adult content that is the correct trade. This is also the only path that restores `PK_u`, so without it partner-assisted recovery silently loses personal content.

**2. Ship the platform-vault tier (Android Block Store / iOS Keychain)?** *Recommend: yes, but verify first.* This covers the largest real-world cohort — uninstall-and-reinstall on the same phone (research/e2ee.md:181). But Labyrinth's "persists across uninstalls" is an iOS Keychain property; on Android, app data and Keystore material are removed on uninstall, so Block Store is the analogue. **I have not verified Block Store's current entry-size and count limits, or whether cloud-backed entries require a device screen lock for E2EE, against the live docs in this session** — check before committing. If it does not fit, the Recovery Key alone is sufficient and this tier is pure convenience. Do **not** solve it by re-enabling app-wide `allowBackup`; that undoes the disguise posture the app deliberately maintains.

**3. Does the partner get a wrap of your Personal Key — a "legacy contact"?** *Recommend: no by default, offered as an explicit revocable enrolment with unambiguous copy.* This is the most emotionally loaded switch in the design and it should never be on by accident. It is also the only decision here that a user would experience as a betrayal if defaulted wrong.

**4. Retention default for Closer items.** Today `keep` for the vault and `ephemeral` for afterglow, and **neither is enforced by anything**. *Recommend: default `keep`, plus a server-enforced 24-month dormancy purge for couples with no session in 24 months, announced by push and email 30 days ahead.* That bounds both the storage bill and the breach blast radius for abandoned accounts, which is the population most likely to be breached and least likely to notice.

**5. How long to keep the legacy dual-read path (Stages 1–2)?** *Recommend: two releases or 90 days, whichever is longer,* with an in-app countdown for couples with un-migrated rows. Longer means the old loss bug stays live for longer; shorter risks stranding a couple where one partner does not update.

**6. Encrypt `happened_on` and body-map `x,y`, at the cost of server-side ordering and any future server-side feature?** *Recommend: encrypt both.* Keep a coarse cleartext `happened_month` for timeline ordering and pagination. The body-map coordinate leak is the single sharpest contradiction of the E2EE claim in the whole suite — the server currently sees exactly where on the body each pin sits, and only the caption is hidden.

**7. Fantasy Jar copy.** Once tags are matched under a couple-shared key, the partner can enumerate your full tag set — not just the overlap. That is inherent to any shared-key matching scheme, and the only escape is a PSI that is not worth building. *Recommend: change the promise to what is true* — "your partner sees which themes you both picked; never your words" — and delete the doc comment claiming HMAC-SHA256 protection that the code does not implement.

**8. Escalation path for the retry/repair window.** The corpus notes a real trade nobody warns about (research/e2ee.md:237): a repair loop needs a local plaintext outbox, which is a plaintext store on disk — a genuine risk for an app where device seizure is plausible. *Recommend: Closer needs no repair loop at all,* because a wrap is idempotent and re-openable rather than a consumed ratchet step. If chat later adopts one, pick the window deliberately and write the number down; do not inherit Signal's 14 days by default.
