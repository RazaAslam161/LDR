# Reliable message delivery and the sent → delivered → seen state machine (WhatsApp, Signal, Telegram, Matrix), mapped onto Flutter + Supabase

## Mechanism
## 0. The one structural idea

Every one of these systems splits the problem into two layers that never mix:

- **Layer A — "the message is not lost."** A server-assigned *monotonic integer* per queue/account, at-least-once delivery, and a client-advanced *cursor* that doubles as the ack. Wall clocks appear nowhere.
- **Layer B — "the state is correct."** Delivery and read are *separate facts with separate owners*, each stored as a **monotone watermark** (highest ordinal delivered / highest ordinal read), never as a per-message boolean.

Nobody attempts exactly-once on the wire. All four do **at-least-once + idempotent apply**, keyed on an id the *sender* chose before the first attempt.

## 1. Server-side per-recipient queue (Signal) vs fan-out-on-read (Telegram, Matrix)

### Signal — real per-(account, device) queue. DOCUMENTED (source code + code-reading write-up)

Storage is Redis (hot) + DynamoDB (persistent), keyed by `(accountUuid, deviceId)`. The Lua script `insert_item.lua`:
- if the message's **`guid` already exists**, it reuses the existing `messageId` → **insert is idempotent**;
- otherwise it `INCR`s a per-queue `counter` key to mint a new **monotonically increasing per-queue messageId**, then `ZADD`s (score = messageId, member = envelope).

So Signal's queue is a per-device sorted set ordered by a server-minted monotonic counter, with dedup on guid. Undelivered messages carry a **7-day TTL** in DynamoDB (the older Postgres implementation kept only the **latest 1000 messages per destination device**). `MessagesManager` documents "Expiration of messages from Redis and Dynamo is handled automatically and do not require any interaction with this class."

Delivery over the authenticated websocket (`WebSocketConnection.java`, read directly):
- source is a reactive `messageStream.getMessages()`;
- `limitRate(MESSAGE_PUBLISHER_LIMIT_RATE)` = **100** messages of backpressure;
- `flatMapSequential` with `MESSAGE_SENDER_MAX_CONCURRENCY` = **256** — concurrent sends, but **emission order is preserved**, i.e. strict per-device FIFO;
- each envelope is sent as HTTP-over-websocket **`PUT /api/v1/message`**;
- the client replies with a `WebSocketResponseMessage`; **status 200–299 is the ack** → `messageStream.acknowledgeMessage()` → the item is deleted from the queue. A non-2xx reply does *not* acknowledge, so the item stays queued (INFERRED from the ack-then-delete ordering);
- when the queue drains, the server sends **`PUT /api/v1/queue/empty`** — an explicit *"you are now caught up"* marker;
- a second connection for the same device throws `ConflictingMessageConsumerException` → close with code **4409** (single consumer per device, enforced);
- disconnect with messages still pending → a push notification is scheduled **1 minute** later.

### Telegram — no per-recipient queue; a per-account *message box* with `pts`. DOCUMENTED

Telegram keeps one copy of the message and gives each account a monotonically increasing **`pts`** ("points"), plus **`qts`** (secret chats and some bot updates), **`seq`** (on the `Updates` envelope) and `date`. Each update carries `pts` **and `pts_count`** (how much it advances the counter — updates can be grouped).

Gap arithmetic (core.telegram.org/api/updates — this host was unreachable from this environment, quoted via search excerpts):
- `local_pts + pts_count == pts` → **apply**;
- `local_pts + pts_count > pts` → **already applied, drop** (this is the idempotency rule);
- `local_pts + pts_count < pts` → **gap**: buffer the update and call `updates.getDifference`.
- Envelope level: apply iff `local_seq + 1 == seq_start`; `local_seq + 1 < seq_start` → gap.

`updates.getDifference(pts, date, qts, pts_limit, pts_total_limit, qts_limit)` returns `updates.differenceEmpty` / `difference` / `differenceSlice` (paginate by re-calling with the returned intermediate state) / **`differenceTooLong`** (local state is beyond recovery — discard and resync from scratch). "The specified limit does not limit the total number of updates that can be fetched … it just limits the number of updates returned by each individual getDifference call."

Channels get their **own per-channel `pts`** and `updates.getChannelDifference` / `channelDifferenceTooLong` — i.e. Telegram *shards the counter* precisely because a single account-wide counter would be a bottleneck for large channels.

The trap they explicitly designed around: **self-initiated RPCs also advance the server's pts.** `messages.readHistory`, `messages.deleteMessages` etc. return `messages.affectedMessages{pts, pts_count}`, and the client must apply that locally or it will detect a phantom gap. gotd exposes this as `Manager.HandleAffected(ctx, channelID, pts, ptsCount)`.

Send idempotency: `messages.sendMessage` requires **`random_id`** — a "unique 64-bit client message ID required to prevent message resending"; the server dedups on it, and the client uses it to reconcile its optimistic local row with the server-assigned message id.

### Matrix — fan-out-on-read over a server-authoritative monotonic stream. DOCUMENTED

Synapse's internal abstraction is a **"stream"**: "an append-only log `T1, T2, …, Tn`", each fact carrying a `stream_id`, and "**readers should only process facts in ascending stream ID order**." The published *current* position is "the largest stream ID where all transactions added by W with equal or smaller ID have completed", and current stream IDs "are monotonic, but they may 'skip' or jump over IDs because facts complete out of order." **This is the exact hazard of using a Postgres sequence as a cursor** — a row with id 105 can become visible before 104 commits, and a naive `WHERE id > cursor` reader loses 104 forever. Synapse solves it by tracking in-flight ids per writer and only advancing the published token past fully-committed ids.

Client-facing: `GET /_matrix/client/v3/sync?since=<next_batch>&timeout=…` long-polls; the response carries **`next_batch`** ("a session identifier that the client must include in a subsequent request"). Per-room, `timeline.limited: true` plus `timeline.prev_batch` means **the server declares a gap**, and the client backfills via `GET /rooms/{roomId}/messages?from=<prev_batch>`. The client never has to *infer* a gap.

## 2. The exact ack protocol — who acks what, when, to whom

There are three distinct acks in play, and confusing them is the classic bug.

**(a) Transport ack — "the socket handed it over."**
XEP-0198 Stream Management, which WhatsApp's FunXMPP descends from, is the cleanest specification of this. Two counters per direction, both **start at 0** when `<enable/>`/`<enabled/>` is exchanged, **+1 per handled stanza**, and "the value of 'h' SHALL be reset from 2³²−1 back to zero" on overflow. "Handled" is defined precisely as the server having "**accepted responsibility** for a stanza … to process, deliver to a local entity, or route to a remote entity" — explicitly *not* "the peer read it." `<r/>` requests an ack, `<a h='N'/>` gives one; on `<resume previd='…' h='N'/>` both sides retransmit everything above the peer's reported h.

The XEP states the limitation in one sentence that should govern any design: *"Because unacknowledged stanzas might have been received by the other party, resending them might result in duplicates; there is no way to prevent such a result in this protocol."* → at-least-once is the ceiling; dedup must be at the application layer.

WhatsApp's version (from whatsmeow, a mature reverse-engineered client): **every received stanza must be `<ack>`ed**, built with `{class: node.Tag, id: node.Attrs["id"], to: node.Attrs["from"]}` plus optional `participant`/`recipient`/`type`/`error`. Failure is a NACK with a code: `487` parsing error, `488` unrecognized stanza, `491` invalid protobuf, `495` missing message secret, through `552` DB operation failed.

Signal's version: HTTP-over-websocket, **2xx response = ack = delete from queue**.

**(b) Cursor ack — "I durably have everything up to N."**
Matrix makes this explicit and it is the single most transferable idea in this research. For to-device (the reliability-critical channel): *"Events are treated as acknowledged when the server receives a new request with the `since` value set to the previous response's `next_batch` value. Acknowledged events are permanently deleted from the server, and MUST NOT be returned to the client should another request with an older since value be sent."* The client **MUST persist `next_batch` to persistent storage between requests.**

MSC4186 (Simplified Sliding Sync) states the invariant in full: *"The server cannot assume that a client has received a response until it receives a new request with the `pos` token set to the `pos` it returned in the response"*, and *"The server MUST ensure that any per-connection state it tracks correctly handles receiving **multiple requests with the latest pos token**"* (re-presenting the cursor must be idempotent). Expiry is an explicit protocol event: HTTP **400 `M_UNKNOWN_POS`** → client restarts from scratch. Telegram's equivalent is `differenceTooLong`; Matrix `/sync`'s equivalent is `limited: true` + `prev_batch`.

Telegram's cursor is `pts`/`qts`/`seq`, advanced only after the update is applied locally. Signal's cursor is implicit — the ack deletes the item.

**(c) Application receipt — "a human's device has it / a human saw it."** This is Layer B, below.

## 3. Idempotency and de-duplication

| System | Idempotency key | Semantics |
|---|---|---|
| Matrix | `PUT /rooms/{roomId}/send/{eventType}/{txnId}` | DOCUMENTED: *"The homeserver should identify a request as a retransmission if the transaction ID is the same as a previous request, and the path of the HTTP request is the same."* Retransmission returns **the original response** (same `event_id`). Scoped **per device and per endpoint**; scope resets on login/logout. Recommended format: **v4 UUID**, or timestamp concatenated with a monotonic counter. |
| Telegram | `random_id` (64-bit, client-generated, required) | DOCUMENTED: "required to prevent message resending"; also used to "associate the previously transmitted message with the one delivered to the server." |
| Signal | `DataMessage.timestamp` (uint64, sender-chosen) + server `guid` | DOCUMENTED: the sender's timestamp *is* the message id across `DataMessage`, `SyncMessage.Sent`, `SyncMessage.Read` and `ReceiptMessage`. Server-side, `insert_item.lua` dedups on `guid`. Envelope carries a **separate `serverTimestamp = 10`**. |
| WhatsApp | stanza `id` | DOCUMENTED (whatsmeow): the `id` attribute is the dedup key. Additionally, with `EnableDecryptedEventBuffer`, **SHA-256 hashes of the ciphertext** are cached, and a repeat hash returns the cached plaintext rather than re-running the ratchet — dedup *below* the message-id layer, so a redelivered ciphertext can't corrupt ratchet state. |

At the crypto layer, Signal's Double Ratchet handles reordering natively: the header carries **`N`** (message number in the current sending chain) and **`PN`** (length of the previous sending chain); the receiver stores skipped keys in **`MKSKIPPED`** ("dictionary of skipped-over message keys, indexed by ratchet public key and message number"), bounded by **`MAX_SKIP`** ("high enough to tolerate routine lost or delayed messages, but low enough that a malicious sender can't trigger excessive recipient computation" — the spec gives no number). The spec is explicit that it provides **no ordering guarantees**; replay protection comes from deleting a message key after first use (INFERRED — the Double Ratchet spec does not discuss replay).

## 4. Delivered vs read — who is authoritative

**Signal.** Two entirely different mechanisms, DOCUMENTED:
- **Delivery receipt**: if sealed sender was *not* used, **the server itself** emits the delivery receipt to the sender when the device acks (the server knows both ends). If sealed sender *was* used (now the default), the server doesn't know who the sender is, so **the recipient's device** emits `ReceiptMessage{type: DELIVERY, timestamp: [...]}` as an ordinary E2EE content message back to the sender.
- **Read/viewed receipt**: **always** client-generated, `ReceiptMessage{type: READ | VIEWED}`, user-disableable.
- Proto (libsignal-service-java): `message ReceiptMessage { enum Type { DELIVERY = 0; READ = 1; } optional Type type = 1; repeated uint64 timestamp = 2; }` — note **`repeated`**: one receipt acknowledges a *batch* of message ids.
- Own-device consistency is explicit, not derived: `SyncMessage.Sent{destinationUuid, timestamp, message}` replicates your outbound message to your other devices, and `SyncMessage.Read{senderUuid, timestamp}` replicates your read state to your other devices.

**WhatsApp.** whatsmeow's `ReceiptType` constants are the actual on-wire vocabulary, with upstream doc comments:
- `""` (`ReceiptTypeDelivered`) — "the message was delivered to the device (but the user might not have noticed)"
- `"sender"` — "sent by your other devices when a message you sent is delivered to them"
- `"retry"` — "**the message was delivered to the device, but decrypting the message failed**"
- `"read"` — "the user opened the chat and saw the message"
- `"read-self"` — "the current user read a message from a different device, and has read receipts disabled in privacy settings"
- `"played"` / `"played-self"` — view-once media opened
- plus `"server-error"`, `"inactive"`, `"peer_msg"`, `"hist_sync"`

Read receipts are **batched watermarks**, not one stanza per message: `MarkRead` puts the first id in the node's `id` attribute and the remainder in `<list><item id="…"/>…</list>` children, with `t` = the read timestamp.

The critical design point in `"read-self"`: **even with read receipts disabled toward the sender, read state still propagates to your own devices.** The privacy setting suppresses the outbound receipt, not the internal state sync. Matrix's `m.read.private` is the same idea, formalised.

WhatsApp's public state machine (Meta's own Cloud API status webhook reference, DOCUMENTED):
- `sent` — "the message was successfully sent from our servers"
- `delivered` — "successfully delivered to the WhatsApp user's device"
- `read` — "**displayed in an open chat thread** in the WhatsApp user's device"
- `played` — first playback of a voice message
- `failed`
- and the invariant that most homegrown implementations get wrong: *"In some cases, like when a user receives a message while in the chat screen, the message is both delivered and read at the same time. In these cases, the **'delivered' webhook is not sent** because it's implied that the message was delivered since it was read."*

→ **The states are a monotone lattice with implication (read ⇒ delivered ⇒ sent), and intermediate transitions may be skipped.** A receiver must clamp upward and must never require the intermediate step. Per Meta's docs, `delivered` also means delivered to **at least one** of the user's devices.

**Telegram.** Read is a **watermark integer per dialog per direction** — not per message. `messages.readHistory(peer, max_id)`; `dialog` carries `read_inbox_max_id`, `read_outbox_max_id`, `unread_count`; movements are pushed as `updateReadHistoryInbox` / `updateReadHistoryOutbox`. Telegram has **no "delivered" state at all** for cloud chats — the message is on the server, therefore it's deliverable; the UI shows one tick (sent) and two ticks (read).

**Matrix.** Three receipt types, all **watermarks pointing at an event id**:
- `m.read` — public, federated
- `m.read.private` — DOCUMENTED: servers *"MUST NOT send receipts of receiptType `m.read.private` to any other user than the sender"* and *"MUST NOT send them to any server over federation"*; echoed back to the sender's own devices so notification counts clear everywhere
- `m.fully_read` — room account data, a private bookmark, never shared

Monotonicity is normative: **"both receipts can only move forwards."** When both a public and private receipt exist, *"the receipt that is more 'ahead' of the other takes precedence when considering notifications."* The server computes `notification_count` / `highlight_count` (and MSC2654's `unread_count`, with `highlight_count <= notification_count <= unread_count`) as the events since the receipt.

**Matrix has no delivery receipt whatsoever.** That is a deliberate omission and, along with the ordering problem below, its biggest weakness for a 1:1 chat UX.

## 5. Multi-device consistency

- **Signal (Sesame, DOCUMENTED)**: per-device sessions in `UserRecord → DeviceRecord`. Sending iterates "each non-stale DeviceRecord in the UserRecord that contains an active session", and the recipient set "includes the device's own UserID", so a device always sends a copy of each outbound message to the user's other devices. Stale records are kept until "the timestamp is older than `MAXLATENCY`" so in-flight messages aren't dropped. Session convergence: "when a message is received on an 'inactive' session, that becomes the new active session."
- **WhatsApp (Meta engineering blog, DOCUMENTED)**: **client-fanout** — the sender encrypts and transmits the message N times to the N devices in the sender's and receiver's device lists; each device has its own identity key; groups use Sender Keys to avoid quadratic blow-up.
- Consequence in both: **receipts are per-device.** The Careless Whisper paper (USENIX-track, arXiv 2411.11194) confirms each active device independently issues a delivery receipt, and that this is precisely what makes device-level activity tracking possible. The sender's UI must aggregate with an explicit rule (WhatsApp: `delivered` = at least one device).
- **Telegram/Matrix**: multi-device consistency is free because state is *server-side and per-user*, not per-device. One `read_inbox_max_id` / one `m.read` per user. Cheaper, but you lose per-device granularity.

## 6. Offline for hours or days

The pattern is identical in all four: **queue or log with a retention bound + cursor catch-up + an explicit "too far behind, resync from scratch" escape hatch.**

| | Retention of undelivered | Catch-up | "Too far behind" signal |
|---|---|---|---|
| Signal | **7 days** TTL (DynamoDB); older Postgres impl kept last **1000/device** | queue drain on websocket connect, ends with `PUT /api/v1/queue/empty` | none — beyond TTL the message is genuinely gone |
| WhatsApp | **30 days** encrypted on server, then deleted (privacy policy) | reconnect + offline stanza drain; `hist_sync` receipt type for history sync | history sync via companion device |
| Telegram | messages are permanent cloud storage | `updates.getDifference` from stored `pts`, paginated via `differenceSlice` | `differenceTooLong` / `channelDifferenceTooLong` → discard state, refetch `updates.getState`, restart |
| Matrix | events are permanent in the room DAG; to-device deleted on ack | `/sync?since=…`; `limited:true` + `prev_batch` → `/rooms/{id}/messages` | `M_UNKNOWN_POS` (sliding sync) → full resync |

Signal's push behaviour is worth copying verbatim: **on disconnect with a non-empty queue, schedule a push notification 1 minute later.** Push is a *wake-up*, not a delivery channel.

## 7. How clock skew is kept out entirely

This is the part that is uniformly, deliberately designed, and the part homegrown implementations always get wrong.

1. **Ordering never uses a clock.** Telegram: `pts`. Signal: per-queue `INCR` counter. Synapse: `stream_id`. XEP-0198: `h`. Matrix receipts: event ids ordered by the server's stream.
2. **Timestamps are opaque labels, not comparables.** Signal's `DataMessage.timestamp` is *chosen by the sender* and functions purely as an identifier — receipts reference it by equality, never by `<`. The server records `Envelope.serverTimestamp` in a *separate* field so the two are never conflated.
3. **Where a clock does leak in, it is documented as broken.** Matrix's `origin_server_ts` is written by the originating homeserver, and — per an Element engineer's analysis — *"different servers can have very different clocks, and events in /messages responses don't have to be in chronological order, so origin_server_ts is neither accurate to the local homeserver's view, nor monotonically increasing."* Worse, Matrix receipts point at an event id but *"the spec does not provide a way for a client to determine which events are before or after it in this ordering, making it essentially impossible for clients to handle read receipts"* correctly — hence MSC4033 proposing an explicit per-event **order number**. Existing homeservers fall back to "the order in which they received the message."
4. Matrix also has three *different* orders in one protocol — stream/arrival order (`/sync`), topological order (`/messages`, `/context`, `/relations`), and `origin_server_ts` — which is the cautionary tale: **pick one total order, assign it server-side, expose it to the client, and use it everywhere.**
5. MTProto is the exception that proves the rule: `msg_id` *is* time-dependent, which forces every client to continuously synchronise its clock to the server's — the cost of admitting a clock into the protocol.

## Invariants
- MESSAGE IDENTITY IS CLIENT-CHOSEN AND FIXED BEFORE THE FIRST SEND. Telegram random_id (64-bit), Matrix txnId (path-scoped, per-device), Signal DataMessage.timestamp, WhatsApp stanza id. Because the id exists before the network call, a timeout is never ambiguous: retry the identical request and the server either dedups or returns the original response. Corollary: the retry path needs no new logic at all.
- AT-LEAST-ONCE ON THE WIRE + IDEMPOTENT APPLY = EXACTLY-ONCE EFFECT. No protocol here attempts exactly-once delivery. XEP-0198 says it outright: resending unacked stanzas 'might result in duplicates; there is no way to prevent such a result in this protocol.' Every duplicate-suppression mechanism lives above the transport.
- ORDER IS A SERVER-ASSIGNED MONOTONIC INTEGER, NEVER A CLOCK. Telegram pts (+ pts_count), Signal's per-queue INCR counter, Synapse stream_id, XEP-0198 h. The integer is per-queue or per-account, not global, so it can be sharded (Telegram gives every channel its own pts).
- THE CURSOR ADVANCE *IS* THE ACK, AND IT IS THE ONLY THING THAT AUTHORISES DELETION. Matrix: to-device events are acknowledged when the next request arrives carrying the previous next_batch, and only then are they permanently deleted. Signal: only a 2xx on PUT /api/v1/message triggers acknowledgeMessage() and removal from the queue.
- RE-PRESENTING THE SAME CURSOR MUST BE IDEMPOTENT AND MUST NOT SKIP. MSC4186 makes this normative: the server 'MUST ensure that any per-connection state it tracks correctly handles receiving multiple requests with the latest pos token.' A client that crashes after receiving a batch but before persisting the cursor must get the same batch again, not the next one.
- A CURSOR MUST NEVER BE PUBLISHED PAST AN UNCOMMITTED WRITE. Synapse: the current position is 'the largest stream ID where all transactions added by W with equal or smaller ID have completed'; positions are monotonic but 'may skip or jump over IDs because facts complete out of order.' Handing out a cursor of 105 while 104 is still in flight loses 104 permanently.
- GAPS ARE SERVER-DECLARED, NOT CLIENT-INFERRED, AND THERE IS ALWAYS A DOCUMENTED GIVE-UP PATH. Matrix timeline.limited:true + prev_batch; Telegram's pts arithmetic plus differenceTooLong / channelDifferenceTooLong; sliding sync's HTTP 400 M_UNKNOWN_POS. The client never guesses whether it missed something, and 'resync from scratch' is a first-class protocol state rather than an error.
- DELIVERED AND READ HAVE DIFFERENT OWNERS. Delivered is a per-*device* fact owned by the recipient device (or, when the server can see both endpoints, by the server — Signal's non-sealed-sender case). Read is a per-*user* fact owned only by the device where a human looked at the screen. No server ever infers 'read'.
- READ AND DELIVERED ARE MONOTONE WATERMARKS, NOT PER-MESSAGE BOOLEANS. Telegram read_inbox_max_id / read_outbox_max_id; Matrix's normative 'both receipts can only move forwards'; WhatsApp batches read receipts into one stanza with a <list> of ids. O(1) state per participant, idempotent under replay, immune to out-of-order receipt arrival.
- THE STATES FORM A LATTICE WITH IMPLICATION, AND INTERMEDIATE STATES MAY BE SKIPPED. Meta documents it: when a message is delivered and read simultaneously, 'the delivered webhook is not sent because it's implied that the message was delivered since it was read.' A receiver must clamp upward (read implies delivered implies sent) and must never require or wait for the intermediate transition.
- CLOCK VALUES ARE PAYLOAD, NOT CONTROL. Signal's message 'timestamp' is an identifier compared only by equality, with the server's view kept in a separate Envelope.serverTimestamp field. Where a clock does leak into control (Matrix's origin_server_ts, MTProto's time-derived msg_id), the ecosystem documents the resulting pain — 'neither accurate to the local homeserver's view, nor monotonically increasing' — and proposes an explicit order number instead (MSC4033).
- ONE CONSUMER PER QUEUE, ENFORCED. Signal closes a duplicate device connection with code 4409. Matrix documents the opposite failure: two processes sharing one /sync token means the one that advances first deletes to-device events the other never saw (hence MSC3885's opt-in acknowledgement).
- PRIVACY SETTINGS SUPPRESS THE OUTBOUND RECEIPT, NOT THE INTERNAL STATE SYNC. WhatsApp's 'read-self'/'played-self' and Matrix's m.read.private exist so a user's own devices stay consistent and notification counts still clear even when the sender is told nothing.
- CRYPTO-LAYER FAILURE IS A DISTINCT FAILURE CLASS WITH ITS OWN RETRY CHANNEL. WhatsApp's 'retry' receipt means 'delivered to the device, but decrypting the message failed' — transport succeeded, semantics failed. Without this channel you get permanent 'Waiting for this message' holes that no amount of transport reliability fixes.

## Failure modes designed for
- Client dies between server-write and client-ack. Solved by ack-then-delete ordering: Signal only calls acknowledgeMessage() on a 2xx, Matrix only deletes to-device events when the next request carries the previous next_batch. The item is redelivered on reconnect and deduped by id.
- Sender cannot tell whether a timed-out send landed. Solved by the pre-generated idempotency key (random_id / txnId / DataMessage.timestamp), with the server returning the *original* response on retransmission so the client gets the same server-assigned message id and never creates a twin.
- Silent gap after a brief disconnect. Telegram's pts arithmetic detects it deterministically (local_pts + pts_count < pts) rather than relying on the client noticing a missing message; Matrix's server sets timeline.limited:true and hands over prev_batch.
- Offline for hours or days. Bounded server-side retention (Signal 7-day DynamoDB TTL, previously last-1000-per-device; WhatsApp 30 days encrypted then deleted) plus cursor catch-up. Beyond the bound the message is genuinely lost, and the design accepts that rather than pretending otherwise.
- Offline so long that catch-up would be unbounded. Explicit protocol states: Telegram differenceTooLong / channelDifferenceTooLong (discard local state, refetch updates.getState, restart), sliding sync M_UNKNOWN_POS (400), Matrix limited:true + backfill. Catch-up is paginated (differenceSlice; per-call pts_limit that bounds each call but not the total).
- Two readers sharing one cursor. Signal kicks the duplicate device connection with close code 4409. Matrix documents the bug it causes when unprevented: 'once a token is used for a sync request, to-device events that were part of the previous sync response will be deleted… if one process uses a newer token before another process uses an older token, the second process will miss all events from the earlier sync response' (motivating MSC3885).
- Self-initiated actions silently advancing the server cursor. Telegram's messages.readHistory / deleteMessages return messages.affectedMessages{pts, pts_count}; if the client doesn't apply them it manufactures a phantom gap and triggers a pointless full getDifference. gotd exposes HandleAffected specifically for this.
- Decryption failure after key rotation, reinstall, or a missed SenderKeyDistributionMessage. WhatsApp's 'retry' receipt asks the sender to re-encrypt with a fresh session; Baileys caps this at 3 attempts with a 100ms initial delay, and falls back to requestPlaceholderResend (PeerDataOperationRequestMessage / PLACEHOLDER_MESSAGE_RESEND). Signal's equivalent is Sesame session convergence — 'when a message is received on an inactive session, that becomes the new active session'.
- Out-of-order and skipped ciphertexts. Double Ratchet headers carry N and PN so the receiver can jump ahead and stash skipped keys in MKSKIPPED, bounded by MAX_SKIP so a malicious sender can't force unbounded key derivation. Explicitly: the protocol offers no ordering guarantee and does not need one.
- Ciphertext replay / redelivery corrupting ratchet state. whatsmeow caches SHA-256 of the ciphertext and returns the cached plaintext on a repeat instead of re-running the ratchet; Baileys serialises Signal-state updates per session with a keyed mutex to prevent out-of-order counter increments.
- Stale device dragging state backwards. Matrix makes it normative that receipts 'can only move forwards', and when public and private receipts disagree the one further ahead wins. Watermarks are GREATEST-only by construction.
- Device is offline when a message arrives. Signal schedules a push notification 1 minute after a disconnect that left messages queued — push is a wake-up hint, and the real delivery still happens over the queue on reconnect.
- Multi-device receipt ambiguity. Meta's rule: a 'delivered' status means delivered to at least one of the user's devices. Sesame keeps stale DeviceRecords until older than MAXLATENCY so in-flight messages to a just-removed device aren't dropped.
- Receipts as a metadata side channel. The Careless Whisper paper shows delivery-receipt RTT leaks screen-on/off and foreground/background state (WhatsApp ~350ms foreground vs >1s screen-off), and that both WhatsApp and Signal emit receipts for references to messages that never existed — so anyone with a phone number can silently probe a device. Threema's stricter validation is called out as the counter-design.
- Clock skew corrupting order. Eliminated by never comparing clocks: order comes from server-assigned integers, and timestamps are compared only by equality (as identifiers). Matrix, which did admit a clock, is the documented cautionary case.

## Applicability to Supabase
"## What transfers directly (build these; they are cheap on the free tier)\n\n**1. A per-conversation monotonic `seq`, assigned inside the insert transaction.** This is Telegram's `pts` and Synapse's `stream_id`. Do NOT use a Postgres SEQUENCE and do NOT use `created_at`.\n\n```sql\n-- inside one tx, in a SECURITY DEFINER rpc\nupdate conversations set last_seq = last_seq + 1\n where id = p_conversation_id returning last_seq into v_seq;\ninsert into messages (conversation_id, sender_id, client_msg_id, seq, body)\nvalues (p_conversation_id, auth.uid(), p_client_msg_id, v_seq, p_body)\non conflict (conversation_id, sender_id, client_msg_id) do update\n  set body = messages.body            -- no-op, forces RETURNING\nreturning *;\n```\n\nWhy the row-counter and not `nextval`: sequences are non-transactional, so ids are consumed on rollback and — the killer — a row with seq 105 can become *visible to readers* before seq 104 commits. A client polling `WHERE seq > cursor ORDER BY seq` then advances past 104 and loses it permanently. This is precisely the problem Synapse solves with in-flight token tracking. The `UPDATE … RETURNING` counter serialises writers within a conversation, which for a two-person app is zero contention, and makes holes structurally impossible.\n\n**2. `client_msg_id uuid` as the idempotency key**, unique on `(conversation_id, sender_id, client_msg_id)`, generated by the Flutter client before the first attempt. `ON CONFLICT … RETURNING` gives back the original row, so the client always learns the real `seq` and `id`. This is Matrix's txnId rule verbatim ('identify a request as a retransmission if the transaction ID is the same'). Once this exists, the client can retry forever with backoff and there is no send-path special-casing.\n\n**3. A local outbox in the Flutter app** — Drift/SQLite table with `client_msg_id`, `status ∈ {pending, sent, failed}`, `attempt_count`, `next_attempt_at`. Drain on connectivity change and on app foreground. **This component does not exist in the stack and must be written.** It is the difference between 'usually works' and 'never loses a message'.\n\n**4. Catch-up query as the source of truth; Realtime as a hint only.** This is `/sync?since=`:\n\n```sql\nselect * from messages\n where conversation_id = $1 and seq > $2\n order by seq limit 200;   -- return has_more = (count = 200)\n```\n\nRun it on every app start, every foreground, every socket reconnect, and after every FCM wake — *then* subscribe. `has_more:false` is your `PUT /api/v1/queue/empty`. This single pattern makes Supabase Realtime's documented lack of delivery guarantees irrelevant: the socket can drop every message and the app still converges.\n\n**5. Delivery and read as monotone watermarks, one row per participant per device.**\n\n```sql\ncreate table participant_state (\n  conversation_id uuid, user_id uuid, device_id text,\n  delivered_seq bigint not null default 0,\n  read_seq      bigint not null default 0,\n  primary key (conversation_id, user_id, device_id)\n);\n-- monotone by construction:\nupdate participant_state\n   set delivered_seq = greatest(delivered_seq, $new)\n where conversation_id = $1 and user_id = auth.uid() and device_id = $2;\n```\n\nAdd a BEFORE UPDATE trigger raising on `new.read_seq < old.read_seq` — Matrix's 'receipts can only move forwards' as a database constraint, so a device resuming with stale state cannot regress the partner's ticks. RLS: `using (user_id = auth.uid())` on UPDATE, `using (conversation_id in (…my conversations…))` on SELECT.\n\nThe sender renders state purely by comparison, with no per-message state rows at all:\n`msg.seq <= peer_read_seq ? seen : msg.seq <= peer_delivered_seq ? delivered : sent`\n\nFor multi-device, aggregate exactly as WhatsApp documents: `delivered = max(delivered_seq) over the peer's devices` ('delivered to at least one of the user's devices'), `read = max(read_seq)`.\n\n**6. Authority, enforced by RLS rather than convention.** `sent` = the row exists (server). `delivered` = written by the *recipient device* only after the row is committed to its local SQLite — not when Realtime emitted it, not when FCM arrived. `read` = written by the recipient device only on actual widget visibility. RLS prevents the sender from ever writing the peer's watermark.\n\n**7. FCM carries `{conversation_id, seq}` only — never the message body.** The client wakes, runs the catch-up query, writes `delivered_seq`. Mirrors Signal's 'schedule a push 1 minute after disconnect with a non-empty queue'. Never mark delivered on FCM receipt: Doze, collapse keys and quota make FCM a hint, not a channel.\n\n**8. Clock skew: use `seq` for everything that matters.** `created_at timestamptz default now()` comes from the single Postgres clock and is display-only. If you want the composed-at time, store it in a separate column and never compare it to `created_at`. The device clock enters no comparison, ever.\n\n**9. A `read-self` equivalent.** If you add a 'hide read receipts' toggle, keep writing `read_seq` for the user's own devices and suppress only what the partner is allowed to SELECT (separate column, or a view). WhatsApp's `read-self` and Matrix's `m.read.private` both exist for exactly this.\n\n## What needs a paid tier\n\n- **Realtime concurrency.** Free tier is a hard 200 peak concurrent connections, 100 messages/sec, 100 joins/sec, 100 channels/connection. Thousands of users at even 10% concurrency breaches it. Pro is $10 per 1,000 peak connections above 500.\n- **Realtime message volume.** 2M messages/month free ≈ 67k/day. A chat app where a message, a delivery watermark, a read watermark and typing each cost a broadcast burns this at roughly 4x the naive estimate. Mitigation that costs nothing: **debounce watermark broadcasts** (they are idempotent watermarks — coalescing three read updates into one loses nothing) and **do not broadcast typing at all** on the free tier.\n\n## What must change or be replaced\n\n- **Drop Postgres Changes; use Broadcast-from-Database.** Postgres Changes evaluates RLS per subscribed client per change (the documented scaling failure) and has no replay whatsoever: 'if a client disconnects for 30 seconds and reconnects, the changes that happened during those 30 seconds are gone.' Use a trigger calling `realtime.broadcast_changes` on a private per-conversation topic.\n- **Do not treat Broadcast Replay as catch-up.** Private channels only, Broadcast-from-Database messages only, `since` in epoch ms, **limit max 25**, 72-hour retention, alpha. Your own `seq > cursor` query is unbounded, free, and strictly better.\n- **Broadcast is fire-and-forget** unless you set `config.broadcast.ack: true`, and even then the ack only means the server accepted the push — never that a peer received it. Heartbeat at least every 25s or the connection times out.\n\n## What does not exist in the stack and has to be designed around\n\n- **No server-side per-recipient queue** — and you do not want one. `messages` + per-participant cursor *is* fan-out-on-read, the Telegram/Matrix model, which is cheaper than Signal's per-device queue and needs no TTL sweeper.\n- **No stable device identity.** Supabase Auth gives you a user, not a device. Mint a UUID on first run, persist it in secure storage, and include it in `participant_state`; without it, two devices fight over one watermark row and you get flapping ticks.\n- **No scheduler in Edge Functions.** Use `pg_cron` for the 'still undelivered after N minutes → nudge push' job and any retention sweeps; `pg_net` or an Edge Function for the FCM call.\n- **No retry-receipt equivalent** — only relevant if you add E2EE later. If you do, budget for it explicitly: WhatsApp's `retry` receipt type exists because transport success and decryption success are different events, and without a resend channel you get permanent undecryptable holes.\n- **Privacy note specific to this app.** Careless Whisper shows delivery-receipt latency leaks screen-on/off state to anyone who can address the account. For a private couples app with a deliberately disguised launcher, the cheap mitigations are: only ever emit receipts to the bound partner, never to an unknown sender; never emit a receipt for a message id that does not exist; and coarsen the receipt timestamp (server `now()` at watermark-write, not device time)."

## Scale
"## Fan-out-on-write vs fan-out-on-read — where each breaks\n\n**Per-recipient-device queue (Signal).** Cost is O(devices) rows per message plus a per-device queue structure. Breaks on write amplification in large groups, and on abandoned devices holding rows until TTL — hence the hard bounds: 7-day DynamoDB TTL now, last-1000-messages-per-device in the old Postgres implementation. Read side is trivial (drain a sorted set), which is why Signal can serve a device with one `ZRANGE`. For a two-person conversation this is 2–4 rows per message: free, but it buys nothing you don't already get from a cursor.\n\n**Fan-out-on-read over a monotonic log (Telegram, Matrix).** One row per message; per-recipient state is a single integer. Wins decisively as group size grows. The cost is the counter: a per-account/per-conversation monotonic value is a hot row. Telegram's answer is to shard it — every channel carries its own `pts` and its own `getChannelDifference` precisely because one account-wide counter cannot absorb a large channel's write rate. **A Flutter+Supabase couples app is the ideal case for this model: conversations are 1:1, so the per-conversation counter row has exactly one writer at a time and contention is zero.**\n\n## Where the Supabase-specific pieces break\n\n**The counter row.** `UPDATE conversations SET last_seq = last_seq + 1 RETURNING last_seq` takes a row lock for the duration of the insert transaction. At two participants this is unmeasurable. It becomes a real ceiling somewhere around hundreds of writes/second *into one conversation* — irrelevant here, and the fix if it ever matters is Telegram's: shard the counter (per conversation already, then per conversation-shard).\n\n**Postgres sequences as cursors — the actual landmine.** `nextval` is non-transactional: ids are burned on rollback, and, worse, commit order does not match id order. A reader doing `WHERE seq > cursor ORDER BY seq` can observe 105 while 104 is still uncommitted, advance its cursor to 105, and lose 104 permanently with no error anywhere. Synapse's published current position exists solely to prevent this — it advances only past ids where 'all transactions added by W with equal or smaller ID have completed', and is documented as monotonic but gap-skipping. The in-transaction counter sidesteps the whole class.\n\n**Supabase Realtime, free tier.** 200 peak concurrent connections is the first wall and it is hard. 'Thousands of users' at a realistic 5–15% concurrency is 150–450 simultaneous sockets — you cross it somewhere between 1,500 and 4,000 users. Also 100 messages/sec, 100 channel joins/sec, 100 channels per connection, 256 KB broadcast payload. Pro pricing above that is $10 per 1,000 peak connections over 500.\n\n**Realtime message quota.** 2M/month on Free. Every broadcast to every subscribed client counts. A naive design (broadcast the message + broadcast delivered + broadcast read + broadcast typing) is roughly 4 events per message before fan-out. At 2 recipients that is ~8 counted messages per user message, so 2M/month supports ~250k user messages/month — about 8k/day across the whole app. That is small. Debouncing watermark broadcasts to at most one per second per conversation and dropping typing indicators on the free tier cuts it by roughly 4x for free, precisely because watermarks are idempotent and coalescible.\n\n**Postgres Changes specifically.** RLS is evaluated per subscribed client per change; this is the documented reason it does not scale, and Supabase now steers users to Broadcast-from-Database. It also has zero replay — a 30-second disconnect loses everything in that window.\n\n**Broadcast Replay is not a catch-up mechanism at this scale or any scale.** Max 25 messages per request, 72-hour retention, private channels only, Broadcast-from-Database only, public alpha. A user offline overnight in an active conversation blows past 25 immediately. The `seq > cursor` query has none of these limits and costs one indexed range scan.\n\n**Retention.** Unlike Signal (7 days) and WhatsApp (30 days), Postgres keeps everything, so 'undelivered' never expires — this is strictly better for a couples app and removes the entire class of 'the message aged out' failures. The cost moves to the 500 MB free-tier database limit: with text-only messages that is on the order of a few million rows, so media in Storage (not bytea) is the thing that actually decides when you outgrow the tier.\n\n**Edge Functions.** 500k invocations/month free. If push fan-out is an Edge Function per message, that caps you at ~500k messages/month — comparable to the Realtime ceiling. `pg_net` called from a trigger avoids the invocation charge entirely and is the cheaper architecture on the free tier.\n\n## Cost of the correctness machinery itself\n\nAll of it is nearly free at this scale: one extra bigint column on `messages`, one unique index for idempotency, one small `participant_state` table with two bigints per participant per device, and one indexed range query per reconnect. The expensive parts of the top-tier designs — per-device queues, TTL sweepers, multi-writer stream position tracking, per-channel pts sharding, retry receipts and session repair — are all things a 1:1 non-E2EE app on Postgres genuinely does not need. What it does need, and what no part of Supabase provides, is the client-side outbox and the discipline that Realtime is a hint and the cursor query is the truth."
