# Mobile client architecture for reliability and smoothness: local-first storage + sync engine (outbox, cursors, optimistic UI with surfaced failures) and Flutter-specific jank/measurement, benchmarked against a Flutter + Supabase couples app (E:\LDR\mobile)

## Mechanism
## 1. The local database is the application, the network is a replication detail

**Signal-Android (DOCUMENTED, source code).** Sending a message is not a network call. `MessageSender` writes a row into the local SQLite `messages` table first, then enqueues a persisted job. `IndividualSendJob` is constructed with `Job.Parameters` that carry the whole reliability policy declaratively:
- `queue = recipient.id.toQueueKey(hasMedia)` — a *per-recipient* serial queue. Two messages to the same person can never race or reorder; two messages to different people run in parallel. Scheduled sends get a separate `toScheduledSendQueueKey()`.
- `constraints = [NetworkConstraint.KEY, SealedSenderConstraint.KEY]` — the job is not attempted at all until the OS reports a network. There is no "try and fail" burn on airplane mode.
- `lifespan = TimeUnit.DAYS.toMillis(1)` (86,400,000 ms), `maxAttempts = Parameters.UNLIMITED`. Retry forever, but only for 24 hours.
- `onFailure()` → `SignalDatabase.messages.markAsSentFailed(messageId)` + `notifyMediaMessageDeliveryFailed(...)`. Terminal failure is a **state transition in the local DB**, which the UI is already bound to. Nothing is swallowed and nothing needs a live listener to observe it.
(https://github.com/signalapp/Signal-Android/blob/main/app/src/main/java/org/thoughtcrime/securesms/jobs/IndividualSendJob.kt)

Defaults in `Job.java` are deliberately hostile: `maxAttempts = 1`, `lifespan = IMMORTAL (-1)`, plus explicit priority tiers (`PRIORITY_HIGH=1`, `DEFAULT=0`, `LOW=-1`, `LOWER=-2`). Every job has to opt into retry, so nothing retries by accident. The jobmanager package persists jobs (`persistence/`, `JsonJobData`), migrates them across app versions (`JobMigrator`), reschedules after reboot (`BootReceiver`), and drives execution from `AlarmManagerScheduler` + `JobSchedulerScheduler` via `CompositeScheduler`. The queue survives process death, app upgrade, and reboot.

Backoff (DOCUMENTED, `BackoffUtil.java`): `2^min(attempt,30) * 1000 ms`, clamped by `Math.min(exponentialBackoff, maxBackoff)` where maxBackoff is remote-config'd (was 30 s), then multiplied by a jitter factor `0.75 + random()*0.5` (±25%). Note this is *proportional* jitter, weaker than AWS "Full Jitter", but it is enough because Signal's contention is a few thousand clients hitting one endpoint after an outage, not N clients CAS-looping one row.

**Telegram / TDLib (DOCUMENTED).** The client persists a durable replication state `{pts, qts, date, seq}` plus a per-channel `pts`. Every update carries the sequence position it advances to and how many events it covers (`pts_count`). The client validates locally: if `local_seq + 1 == seq_start`, apply; if `local_seq + 1 > seq_start`, it is a redelivery — **discard, idempotently**; if `local_seq + 1 < seq_start` there is a hole, so buffer and call `updates.getDifference` / `updates.getChannelDifference` to fill it. Gaps are *impossible to miss* because they are detected arithmetically, not by hoping the socket stayed up. TDLib is explicitly described as owning "networking, local storage and data consistency". Known limits: `getDifference` results do not themselves carry sequences (the client must trust the server for that batch), and `ChannelDifferenceTooLong` is unrecoverable — the client throws that channel away and resyncs it from scratch.
(https://core.telegram.org/api/updates, https://pkg.go.dev/github.com/gotd/td/telegram/updates)

**WhatsApp (DOCUMENTED, whitepaper).** For multi-device app state (chat mutes, archives, contacts), the server holds a **Patch Queue** per collection; each patch has a monotonic version and a client-computed `PatchMAC`. A server-side "Base Roller" periodically compacts the queue into a **Snapshot** with a `SnapshotMAC`. The integrity primitive is `LtHash16`, a 1024-bit **homomorphic** set hash: because it is homomorphic, a client can take the hash of the old snapshot, add/subtract the deltas from the patches it just applied, and get a value that must equal the server's declared snapshot hash — so a client that has been offline for a month can accept a compacted snapshot it never watched being built and still prove the server did not tamper with or drop any mutation. Catch-up is "give me patches after version V", falling back to snapshot+patches when V is too old — structurally identical to Telegram's `getDifference` / `differenceTooLong`.
(https://www.whatsapp.com/security/WhatsApp-Security-Whitepaper.pdf)

**Linear (DOCUMENTED via reverse-engineering repo endorsed by Linear's CTO).** `lastSyncId` is a single global monotonically-incrementing integer — the version number of the whole database. Server mutations increment it and are broadcast as **delta packets** (typed sync actions: Insert / Update / Archive / Delete / Covering / sync-group changes) carrying full changed property values, not just acks. On WebSocket reconnect the handshake compares the client's `lastSyncId` against the server's; any shortfall is a request for the missing delta range. Client writes live in a transaction queue with four explicit phases — `createdTransactions`, `queuedTransactions`, `executingTransactions`, `persistedTransactionsEnqueue` — and are **serialized into an IndexedDB `__transactions` table before being sent**, so a crash mid-flight replays on next launch. Transactions created in the same event-loop turn share a `batchIndex` and are flushed together by a microtask scheduler, bounded by a mutation-size limit. Conflict policy is last-writer-wins with rebasing: when a delta packet lands for a property with a still-executing local transaction, the transaction's base value is updated to the server value and the in-memory model is re-pointed at the pending local value (OT-like behaviour without transformation functions).
(https://github.com/wzhudev/reverse-linear-sync-engine)

**Figma (DOCUMENTED).** Explicitly rejected both OT ("a combinatorial explosion of possible states") and CRDTs (designed for decentralised systems; with an authoritative server "we can simplify our system by removing this extra overhead"). The model is a **last-writer-wins register per object-property**, with the server defining the total order — no vector clocks, no timestamps. The client-side anti-flicker rule is the important one: *the client discards incoming server changes that conflict with its own unacknowledged property changes*, because the unacked local value is "our best prediction of what the eventually-consistent value will be". Offline reconnect after an arbitrary gap: download a fresh document, reapply local offline edits on top, resume streaming.
(https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)

**PowerSync (DOCUMENTED)** is the closest thing to a productised version of this for Postgres. Server-side data is partitioned into **sync buckets** (parameterised, e.g. `user_todo_lists["A"]`), each an ordered op-log of PUT/REMOVE with monotonic op ids. A row is only deleted client-side when removed from *all* buckets containing it. Sync rounds are **checkpoints**: client sends its per-bucket last op id, server replies with a checkpoint id + per-bucket checksums, streams ops, then signals checkpoint complete — so the client only makes data visible at a consistent boundary, never mid-stream. Checksum mismatch → delete the bucket and re-sync it (same escape hatch as `ChannelDifferenceTooLong`). Local writes go to an **upload queue**; after uploading, the client requests a **write checkpoint**, and the server confirms durability by tracking the CDC position (Postgres LSN) — so "my write is safely replicated" is a positive, provable signal rather than a 200 OK.
(https://docs.powersync.com/architecture/powersync-protocol)

## 2. The composite pattern all five share

1. **Client-generated stable id** on the write (UUID). It is the idempotency key for retries and the dedupe key for the server echo.
2. **Single atomic local transaction**: write the entity row *and* the outbox row together. Never write the entity and then "remember to enqueue".
3. **Optimistic apply to the read model immediately**, with an explicit `sending / sent / failed` status column — not a separate in-memory list.
4. **A worker drains the outbox** under a network constraint, serialised per logical stream, with exponential backoff + jitter and a lifespan cap.
5. **The server assigns the authoritative order** (`seq` / `pts` / `lastSyncId` / op id). Clients never invent ordering.
6. **A persisted cursor** advances *only after the local apply commits*. Cursor-then-apply is the classic data-loss bug.
7. **Reconnect is not "resubscribe"** — it is "compare cursor, fetch the difference, then resubscribe", with a hard fallback to full resync when the gap is too old.
8. **Terminal failure is a persisted state**, rendered in the row itself, with a retry affordance.

## 3. Retry, backoff, coalescing, and the train

**Backoff (DOCUMENTED, AWS).** Exact formulas:
- no jitter: `sleep = min(cap, base * 2^attempt)`
- **Full Jitter**: `sleep = random(0, min(cap, base * 2^attempt))`
- Equal Jitter: `sleep = min(cap, base*2^attempt)/2 + random(0, min(cap, base*2^attempt)/2)`
- Decorrelated Jitter: `sleep = min(cap, random(base, sleep*3))`

Simulated with 100 contending clients over a 10 ms-mean / 4 ms-variance network: Full and Equal Jitter each cut total calls by **more than half** vs. un-jittered backoff. Full Jitter does the least work (slightly more wall-clock); Equal Jitter does more work *and* takes much longer; Decorrelated does slightly more work than Full. **Full Jitter is the default choice.** The post is explicit that jitter does not change the underlying O(N²) contention — it only stops synchronised retry storms.
(https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)

**Request coalescing (singleflight).** Key in-flight operations by a stable key; a second caller for the same key attaches to the existing future instead of issuing a second request. Critical caveat: singleflight is per-process — it deduplicates within one client, it does not deduplicate across the fleet. On the client the keys that matter are "fetch messages since cursor X for conversation C" and "refresh session", both of which get hammered on every resume/reconnect.

**Connectivity is a hint, never a gate (DOCUMENTED).** `connectivity_plus`' own README: "Connection type availability does not guarantee that there is an Internet access... You should not rely on the current connectivity status to decide whether you can reliably make a network request." Android's `NET_CAPABILITY_INTERNET` means the network claims internet; `NET_CAPABILITY_VALIDATED` means the OS actually probed successfully — you need both, and even then a captive portal or a dying cell handoff will still fail. Correct shape: use connectivity events to *wake the drainer early* and to reset backoff, but let the actual request timeout be the authority.

**Train behaviour (30 s tunnels, repeated).** The failure that hurts is not the outage, it is the **reconnect stampede** afterwards: socket reconnect + token refresh + catch-up fetch + image reloads all firing at once, on the worst 200 ms of signal, from every user in the carriage simultaneously. What good clients do:
- Never block the UI thread or the user's action on the network; the local write already succeeded.
- Backoff resets to base on a *successful* request, not on a connectivity event — otherwise every tunnel exit resets everyone to zero simultaneously (this is precisely the correlated-retry case jitter exists for).
- Coalesce the resume storm: one catch-up request per conversation keyed by cursor, hedged behind a short debounce (a few hundred ms) so `onResume` + `connectivity change` + `socket open` produce one fetch, not three.
- Treat "socket open" as unproven: the first thing after reconnect is the cursor comparison, and until it completes the UI shows the local data, not a spinner.
- Push is the backstop, not the transport. FCM stores and retries for **up to 2,419,200 s (28 days)**, default four weeks; **max 4 distinct active collapse keys** per token; **max 100 pending messages** stored per app instance for a disconnected device (after that FCM discards and sends a `deleted_messages` tickle — the client's answer to that must be "run the cursor catch-up", which is exactly why the cursor must be persisted). High-priority messages can wake a device in Doze with limited network access; FCM uses **7 days** of behavioural history to decide whether to deprioritise a sender that does not produce user-visible notifications.
(https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan, https://firebase.google.com/docs/cloud-messaging/android/message-priority)

## 4. Flutter: the frame budget and where it goes

**Budget (DOCUMENTED).** 60 fps ⇒ **~16 ms per frame**; the docs split it as roughly **8 ms UI thread + 8 ms raster thread**. 120 Hz devices ⇒ **under 8 ms total**. The performance overlay shows the **last 300 frames** for UI and raster separately; **white lines mark 16 ms increments**; red bars mark over-budget frames. Red on the UI graph = your Dart is too expensive; red on the raster graph = the scene is too expensive to draw.
(https://docs.flutter.dev/perf/ui-performance)

**The expensive things, in order (DOCUMENTED).**
- `saveLayer()` — allocates an offscreen buffer and forces a render-target switch, "particularly disruptive on mobile GPUs". Triggered by `ShaderMask`, `ColorFilter`, `Chip` with `disabledColorAlpha != 0xff`, `Text` with an `overflowShader`, and `Clip.antiAliasWithSaveLayer`. Detect with `checkerboardOffscreenLayers`.
- `Opacity` in animations — use `AnimatedOpacity` / `FadeInImage`, or bake the alpha into the colour when there is no overlap.
- Clipping — cheaper than `saveLayer` but still real; prefer `borderRadius` over a clip; pre-clip before animating.
- **Intrinsic passes** — two layout passes instead of one, and they poll *all* cells of a grid/list rather than the visible ones. Enable "Track layouts" in DevTools and look for `'$runtimeType intrinsics'` events. Fix by fixing cell size or nominating an anchor cell.
- `AnimatedBuilder.builder` containing subtrees that do not depend on the animation — those rebuild every tick. Hoist them into the `child` parameter.
- Overriding `operator ==` on widgets → **O(N²)** behaviour.
- Non-lazy `Column`/`ListView(children: [...])` for mostly-offscreen content.

**List virtualisation (DOCUMENTED).** `ListView.builder`/`.separated`/`.custom` build lazily; the default constructor builds everything. `RenderAbstractViewport.defaultCacheExtent = 250.0` **logical pixels** of off-screen build-ahead on each side — so a list of ~90 px rows keeps ~3 extra rows live per edge; a list of full-screen items keeps a fraction of one. `itemExtent` or `prototypeItem` is documented as "more efficient than letting the children determine their own extent because the scrolling machinery can make use of the foreknowledge". `addAutomaticKeepAlives` and `addRepaintBoundaries` both default to `true`.
(https://api.flutter.dev/flutter/widgets/ListView-class.html, https://api.flutter.dev/flutter/rendering/RenderAbstractViewport/defaultCacheExtent-constant.html)

**Images (DOCUMENTED).** `ImageCache` defaults: **1000 images and 100 MB**, LRU, with three populations — pending, cached (keepAlive), and *live* (has listeners, count never dropped to zero). `clear()` does not touch live images; `clearLiveImages()` does. `ResizeImage` "instructs Flutter to decode the image at the specified dimensions instead of at its native size" and is "generally used to reduce the memory footprint of ImageCache" — `Image.network(..., cacheWidth:)` composes it via `ResizeImage.resizeIfNeeded`. The decode cost and the cache cost are both a function of the *decoded* pixel count, so a 4000×3000 JPEG costs ~48 MB of RGBA regardless of the 220 dp box you draw it in; `cacheWidth` at device-pixel size cuts that by ~2 orders of magnitude.
(https://api.flutter.dev/flutter/painting/ImageCache-class.html, https://api.flutter.dev/flutter/painting/ResizeImage-class.html)

**Isolates (DOCUMENTED).** "Use isolates when large computations cause UI jank" — i.e. anything that can exceed the frame gap. `Isolate.run(callback)` for one-shot; on mobile `await compute(fn, msg)` ≡ `await Isolate.run(() => fn(msg))`. Messages are **copied**, except immutable objects (Strings, unmodifiable byte buffers) which pass by reference, and `Isolate.exit` which transfers ownership without copying. There is real overhead in both spawning and copying, so repeated work should use a **long-lived** isolate (`Isolate.spawn` + `ReceivePort`/`SendPort`). Background isolates cannot access `rootBundle`/`dart:ui` and cannot receive unsolicited platform-channel messages — you can *query* from an isolate but you cannot host a long-lived platform listener there.
(https://docs.flutter.dev/perf/isolates)

**Impeller (DOCUMENTED).** Default since **Flutter 3.27** on iOS and **Android API 29+**; below API 29 or without a working Vulkan driver it falls back to OpenGLES. It "precompiles a smaller, simpler set of shaders at engine-build time so they don't compile at runtime" — which is why SkSL warm-up (`--cache-sksl`) is obsolete and first-run shader jank is largely gone. Disable with `--no-enable-impeller` or the `io.flutter.embedding.android.EnableImpeller` manifest meta-data.
(https://docs.flutter.dev/perf/impeller)

## 5. Measuring instead of guessing

**In the lab (DOCUMENTED).** `flutter run --profile` on a **physical device** — debug mode's asserts and JIT make its numbers meaningless. DevTools → Performance: the Flutter frames chart pairs a UI bar and a raster bar per frame; **frames over ~16 ms get a red overlay**, and frames doing shader compilation are marked **dark red**. "Enhance Tracing" adds *Track Widget Builds* (with widget names in the timeline), *Track Layouts* (shows intrinsic passes), and *Track Paints* — all three degrade frame times while enabled, so read them relatively. Rebuild Stats gives per-widget rebuild counts (the fastest way to find a `setState` scoped too high). Raster Stats breaks a slow frame into per-layer draw cost. Toggles for "Render Clip layers", "Render Opacity layers", "Render Physical Shape layers" isolate which effect is responsible. Timeline Events shows everything including custom `dart:developer` `Timeline`/`TimelineTask` spans — wrap each sync phase (drain outbox, catch-up fetch, apply) in one so sync work shows up on the same timeline as the frames it janks.
(https://docs.flutter.dev/tools/devtools/performance)

**In the field (DOCUMENTED).** `SchedulerBinding.instance.addTimingsCallback` delivers `FrameTiming` objects with `buildDuration` (UI thread), `rasterDuration` (raster thread), `totalSpan` (vsync start → raster finish) and `vsyncOverhead` (vsync signal → build start). The API docs are explicit that debug-mode numbers "may be very different" from profile/release. `addTimingsCallback` is preferred over `PlatformDispatcher.onReportTimings` because it supports multiple listeners. This is the only way to know what a mid-range Android phone on a train actually experiences: aggregate p50/p95/p99 of `totalSpan` and a jank-frame ratio per screen, batch them, and ship them with the same outbox that ships everything else.
(https://api.flutter.dev/flutter/dart-ui/FrameTiming-class.html)

## Invariants
- Every write has a client-generated stable id (UUID) created before any network attempt. That id is simultaneously the primary key, the retry idempotency key, and the dedupe key against the server echo — so at-least-once delivery becomes exactly-once observed state, and a retry after an ambiguous timeout is safe by construction.
- The entity row and its outbox row are written in ONE local transaction. There is no window in which the user sees a message that nothing is responsible for sending, and no window in which something is queued that the UI does not show.
- The server is the sole authority on order. Every replicated row carries a server-assigned monotonic position (Signal: server-ordered delivery; Telegram: pts/qts/seq; Linear: lastSyncId; PowerSync: bucket op id). Clients never invent ordering from local clocks, so two clients that have applied the same cursor range have byte-identical history.
- Gaps are detected arithmetically, not probabilistically. Because positions are dense and monotonic, `expected == received` is a decidable local check: equal → apply, lower → already applied, discard idempotently, higher → a hole exists, fetch the difference. There is no 'probably fine' branch.
- The persisted cursor advances only AFTER the local apply has committed. Crash between fetch and apply replays; it never skips. (PowerSync makes this explicit with checkpoint boundaries: data is only made visible at a consistent checkpoint, never mid-stream.)
- Per-logical-stream serialisation, global parallelism. Signal's queue key is the recipient, so ordering is guaranteed exactly where it is observable and nowhere else. One stuck conversation cannot stall another.
- Retry policy is declarative and bounded on two axes independently: attempts (Signal: UNLIMITED) and wall-clock lifespan (Signal: 24 h). A job that can never succeed still terminates, and termination is a state, not a silence.
- A failed operation is a persisted row state (`sent_failed`), not a caught exception, not a toast, not an in-memory flag. It survives process death, it is visible in the same list the user was already looking at, and it carries a retry affordance. Signal's onFailure() writing markAsSentFailed to the DB is the canonical form.
- Optimistic local state outranks stale server state for values the client has not yet had acknowledged (Figma: 'discard incoming changes from the server that conflict with unacknowledged property changes'). Otherwise the UI flickers back to the old value between send and ack.
- Every catch-up path has a defined bailout to full resync when the incremental path is too far behind (Telegram: differenceTooLong / ChannelDifferenceTooLong; PowerSync: checksum mismatch → drop bucket and re-sync; Figma: download a fresh document). Unbounded history replay is never the fallback.
- Retry timing is randomised so that N clients recovering from the same outage do not re-converge (AWS Full Jitter; Signal's ±25% proportional jitter). Correlated retry after a shared outage is the load spike, not the outage itself.
- Connectivity state is an optimisation input (wake the drainer early), never a correctness gate. The authority on 'can I reach the server' is a request that succeeded or timed out.
- Integrity of compacted state is verifiable without having witnessed the compaction (WhatsApp's homomorphic LtHash16 over snapshots; PowerSync's per-bucket checksums). A client that was offline for a month can accept a server-built snapshot and still prove nothing was silently dropped.

## Failure modes designed for
- Process death mid-send. Linear serialises transactions to IndexedDB before dispatch; Signal persists jobs to SQLite and restores them via BootReceiver + JobMigrator across app upgrades. An in-memory queue loses the user's message with no trace — the single most common local-first bug.
- Ambiguous timeout: the request landed but the response did not. Solved by the client-generated id + idempotent server insert. Linear's write-up flags exactly this hole ('the client sends a transaction... but the window closes before receiving a response') as a source of non-idempotent resubmission errors.
- Server echo arriving before, after, or instead of the ack. Same-id dedupe means the optimistic row is reconciled rather than duplicated, whichever arrives first.
- The message emitted into a socket that no longer exists. Realtime pub/sub has no replay: a change published between socket-drop (T0) and resubscribe (T2) is delivered to nobody and never re-emitted. Every one of these systems answers with a durable ordered log plus a persisted cursor, queried on reconnect — never with 'resubscribe and hope'.
- Redelivery after reconnect. Telegram's local_seq+1 > seq_start branch drops already-applied updates; without it, catch-up duplicates every message that arrived in the overlap window.
- Offline longer than the retention of the incremental log. Handled by an explicit too-long signal and full/partial re-bootstrap rather than an unbounded backfill.
- Correlated retry storms after a shared outage (the train-carriage-exiting-a-tunnel case). Full Jitter; backoff reset on request success rather than on a connectivity event.
- Head-of-line blocking. Per-recipient/per-conversation queue keys mean one undeliverable message blocks exactly one conversation.
- Battery and radio cost of futile attempts. NetworkConstraint gating means jobs are not even attempted without a network; Doze-aware push priority means the radio wakes only for things that produce user-visible output — FCM actively deprioritises senders that abuse this, using 7 days of history.
- Silent socket death with no error. Supabase documents this explicitly for backgrounded apps: throttled heartbeat timers → server assumes disconnect → 'your application then stops receiving events without any explicit error message'. Designed-for answer is an application-level liveness check (heartbeat callback / cursor probe on resume), not trusting the socket's own state.
- Credential expiry across an offline window. A 1-hour JWT expiring while the device is in a tunnel means the socket reconnects with a dead token; the refreshed token must be pushed into the realtime layer explicitly.
- Concurrent edits to the same value. Deliberately NOT solved by merge in Figma's case — atomic per-property LWW means 'the result is always one client's complete value, never a merge', and they accept that simultaneous text editing of one value does not work rather than pay for OT/CRDT.
- A malformed or unparseable row poisoning the whole catch-up batch. Robust clients skip the row and continue rather than aborting the sync.

"## What I found in the actual codebase (E:\\LDR\\mobile)\n\n**There is no local database.** `pubspec.yaml` lists no drift / isar / hive / objectbox / sembast; `sqflite` appears only transitively in `pubspec.lock`. Persistence is `shared_preferences` and `flutter_secure_storage`. `ChatRepository.fetch()` does `.select().limit(500)` straight from PostgREST on screen open, and `ChatSendQueue._pending` is a plain `List<PendingSend>` in a singleton — **gone on process death, with the user's photo in it**. This is the read-the-network-in-the-UI architecture that every system above moved away from.\n\n**One concrete correctness bug, worth fixing before anything else.** `lib/features/chat/chat_screen.dart` lines ~125-129:\n\n```dart\ntry {\n  await ChatRepository.sendText(coupleId, body, id: id, replyToId: replyId);\n} catch (_) {\n  /* it's already on screen; the DB retry isn't worth blocking */\n}\n```\n\nThe optimistic bubble is already rendered AND the text has already been fanned out to the partner over `sendBroadcastMessage`. So when the insert fails, the partner has *seen* the message, the sender *sees* the message, and it exists in no database. On next launch both sides lose it — with no error at any point. This is the exact failure mode Signal designed `onFailure() → markAsSentFailed(messageId)` to make impossible. Two fixes, in order: (1) the catch must set a `failed` status on the local row and surface a retry, exactly like `ChatSendQueue` already does for media; (2) the broadcast should not fire until the insert commits, or the partner should treat broadcast-only messages as provisional until the postgres echo confirms them.\n\n**What is already right and should be built on, not replaced.** `ChatRepository.fetchSince(coupleId, afterSeq)` — `.gt('seq', afterSeq).order('seq').limit(500)` — is a proper monotonic sync cursor, and the comment above it correctly diagnoses the socket-drop/resubscribe gap that Telegram's `getDifference` exists to solve. The client-generated `Uuid().v4()` shared across the optimistic row, the broadcast payload, and the DB insert is exactly the idempotency key the pattern needs. The `seq` column is the local equivalent of `pts`/`lastSyncId`. **The primitives exist; they are just not persisted and not universal.**\n\n## What transfers directly, free tier, no new service\n\n1. **Make `seq` durable.** Persist `last_seq` per couple to disk (SQLite, or `shared_preferences` as a stopgap), not to a screen's state. On resume/reconnect/FCM-tickle: `fetchSince(persisted_seq)`, apply, then advance the cursor — apply-then-advance, never the reverse. This alone converts your realtime channel from a source of truth into a latency optimisation, which is what it should be.\n2. **Idempotent server insert.** Change the inserts in `chat_repository.dart` (lines 228, 249, 279, 309) to `upsert(..., ignoreDuplicates: true)` on the `id` PK, or an RPC doing `insert ... on conflict (id) do nothing`. Without this, retrying an ambiguous timeout is a 23505 and your outbox can never be safely aggressive.\n3. **A real outbox table** in local SQLite (drift is the sane choice for a Flutter+Riverpod codebase; you already have sqflite transitively). Schema mirroring Signal's Job.Parameters: `id, couple_id, kind, payload, queue_key, attempt, next_attempt_at, expires_at, status`. Write the message row and the outbox row in one `db.transaction`. A single drainer isolate/timer pulls due rows ordered by `next_attempt_at`, serialised per `queue_key`. Signal's exact policy is a good starting point: `lifespan = 24h`, unlimited attempts within it, `backoff = min(2^attempt * 1000, 30_000) * (0.75 + rand()*0.5)` — or upgrade to AWS Full Jitter, `random(0, min(30_000, 1000 * 2^attempt))`, which is strictly better under correlated recovery and is the same three lines.\n4. **Unify media and text through it.** Right now `ChatSendQueue` handles image/video with retry, and text and voice bypass it entirely (`sendVoice` goes straight through the repository, and the comment in `chat_send_queue.dart` says so). One outbox, all kinds, one status column driving one UI treatment.\n5. **`sendStatus` is already rendered** (`chat_screen.dart` ~line 1644 branches on `SendStatus.failed`). Once the status lives in SQLite instead of a singleton list, that UI keeps working and starts surviving restarts for free.\n6. **Connectivity as a wake signal only.** `connectivity_plus` events reset the drainer's timer; they must not gate the request, per the package's own README. Reset backoff on a *successful* request, not on a connectivity event — otherwise every device leaving the same tunnel resets to zero attempt simultaneously.\n7. **Request coalescing.** Keep a `Map<String, Future<T>>` of in-flight catch-ups keyed by `coupleId`. `onResume` + connectivity change + `subscribe` callback all fire within ~200 ms of leaving a tunnel and would otherwise produce three identical `.gt('seq', ...)` queries. Same for session refresh.\n8. **`supabase.realtime.setAuth(freshToken)` after every token refresh, and unconditionally on resume.** The default JWT is 3600 s and the client refreshes ~60 s before expiry — a device offline across that boundary reconnects with a dead token and the channel errors. This is a documented, still-open sharp edge (supabase/realtime-js#274, supabase-flutter#1012).\n9. **Treat FCM as a tickle, not a transport.** Max 4 collapse keys, max 100 stored messages per disconnected instance, TTL up to 28 days. Send a data message with a collapse key per couple carrying nothing but 'there is news' — the client answers by running `fetchSince(persisted_seq)`. That makes the 100-message cap irrelevant and means you never have to make push payloads reliable.\n\n## What CRDTs are and are not worth here\n\nDon't. Chat is an append-only per-author log with a server-assigned `seq` — the hard part of CRDTs (concurrent convergent edits to a shared mutable structure) does not arise. Figma, running a far more concurrent product, explicitly chose server-authoritative per-property LWW over both OT and CRDTs and gave the reason: with an authoritative server the extra machinery buys nothing. Your mutable-shared-state surfaces (couple settings, chat theme, shared lists in `together`/`rituals`) are per-property LWW cases: add `updated_at` per field or per row and let last write win. The only place a CRDT would earn its keep is a genuinely co-edited long-lived document, and Dart's Automerge/Yjs bindings are not mature enough to take that bet on.\n\n## What needs a paid tier\n\n- **Realtime concurrent connections.** Free = 200. Pro = 500, Pro-without-spend-cap/Team = 10,000.\n- **Broadcast payload.** 256 KB on Free vs 3,000 KB on Pro. Your `_moodChannel` text broadcast is fine; anything richer is not.\n- **Messages/sec.** Free = 100/s project-wide, joins 100/s. A reconnect stampede (everyone's commute ending) is measured in channel joins, and 100/s is not much when 200 sockets all reconnect at once — jitter your own channel subscribe, not just your HTTP retries.\n\n## What does not exist yet and must be built or bought\n\n- **A local database and a sync engine.** This is the whole gap. PowerSync is a service and costs money past its free tier; the DIY version costs engineering time but keeps you on the free tier.\n- **A durable per-recipient server queue.** Supabase Realtime does not have one and never will — it is fire-and-forget pub/sub with no replay. Your `messages` table plus `seq` IS the durable ordered log. You have three real test devices (IN2015 / Vivo / OnePlus 7) but you will never reproduce a train on your desk.\n\n## Flutter specifics against this codebase\n\n- `chat_screen.dart` is **2,118 lines**. ## Scale
"**The binding constraint for this app is Supabase Postgres Changes, and it is much tighter than the connection cap.** Documented: 'Postgres Changes authorizes every event against each subscriber' — one change with 100 subscribers = 100 RLS evaluations — and changes are 'processed on a single thread to preserve their order, which means larger compute add-ons don't meaningfully increase Postgres Changes throughput.' Published Micro-instance benchmarks WITH RLS: 500 clients → 30 DB changes/sec; 1,500 clients → 10/sec; 3,000 clients → **5 DB changes/sec for the entire project**. For a couple app the fanout per message is only 2, so fanout is not what kills you — the single-threaded, RLS-per-subscriber WAL processor shared across every couple is. At 1,000 concurrent devices you are looking at roughly 10-30 changes/sec *total*, i.e. under one message per second per hundred active users. Supabase's own guidance: above ~3,000 concurrent subscribers on the same changes, use Broadcast. **Migrate to `realtime.broadcast_changes()` from an AFTER trigger, on private channels, before you scale — not after.** Broadcast authorises at channel join and caches the policy for the connection lifetime instead of re-checking per event, and `realtime.messages` is daily-partitioned with 3-day auto-drop so it does not grow unbounded.\n\n**Free-tier Realtime ceiling: 200 concurrent connections.** With both partners online that is ~100 simultaneously active couples, and it is a hard cap, not a soft degradation. Pro is 500; Pro-without-spend-cap and Team are 10,000. 'Thousands of users' means Pro-without-spend-cap at minimum. Secondary free-tier limits: 100 messages/sec and 100 channel joins/sec project-wide — the joins limit is what a synchronised reconnect (commute ending, or a Supabase restart) actually saturates, so client-side jitter on `subscribe()` matters as much as jitter on HTTP retries.\n\n**Where the DIY sync engine breaks.** A drift-backed outbox + `seq` cursor scales essentially forever on the client side; the cost is engineering time and the specific bugs the pattern exists to prevent (cursor advanced before apply, non-idempotent retry, unbounded backfill). Two concrete limits to design around now: (a) `fetchSince` uses `.limit(500)` — a client offline for a week needs *paged* catch-up looping until a short page, plus a 'too far behind' bailout that drops local history and re-bootstraps, which is Telegram's `differenceTooLong` and PowerSync's checksum-mismatch path; (b) deletes need tombstones or the cursor cannot express them — PowerSync's rule is a row is removed only when removed from all buckets, and your equivalent is a `deleted_at` column that `fetchSince` returns rather than a hard DELETE, or you get rows that resurrect on reinstall. Your existing `deleteForEveryone` RPC needs checking against this.\n\n**Where PowerSync sits.** Documented to scale to 'tens of thousands of concurrent clients per PowerSync Service instance' and hundreds of thousands to a million+ rows per client, and it gives you checkpoints, checksums, upload queue and LSN-backed write confirmation for free. Cost: another paid service, another deployment, and its sync-rule model has to be expressed for every table you want offline. For a two-person-per-tenant app with a handful of tables, the DIY version is genuinely simpler and stays on the free tier — the case for PowerSync gets strong only if you want *every* feature (vault, timeline, rituals, capsule) offline-first rather than just chat.\n\n**Where CRDTs break.** Metadata overhead grows with edit history, not document size; Dart bindings are immature; and for LWW-shaped data they buy nothing over a server-assigned order. Figma runs a far more concurrent product on per-property LWW. Cost of adopting one here would be high and the benefit is zero for chat.\n\n**Flutter-side ceilings.** The 16 ms budget is per-frame and non-negotiable; the practical split is ~8 ms UI + ~8 ms raster, halving to 8 ms total on 120 Hz hardware. Impeller (default from 3.27 on API 29+) removed shader-compilation jank as a class of problem, so the remaining jank sources are yours: oversized `build()` scopes, intrinsic layout passes (two passes, polling all cells), `saveLayer`, and full-resolution image decode. `ImageCache`'s 100 MB / 1000-image default is generous enough to be an OOM risk on the low-end devices in your test set. Isolate spawn + message copy is not free — per-message crypto or per-thumbnail resize through `Isolate.run` will cost more in copying than it saves, so long-lived isolates for anything repeated.\n\n**Backoff economics.** AWS's own simulation is honest that jitter does not change the O(N²) nature of contention — it halves the calls and stops the synchronised spike. At your scale the spike is what matters (200 sockets reconnecting inside the same second), not steady-state throughput. Full Jitter, `random(0, min(cap, base*2^attempt))`, with cap around 30 s, is the right default; Signal's ±25% proportional jitter is weaker but already 10× better than none.\n\n**Cost of doing nothing.** Today: any message whose insert fails is silently lost after having been shown to both users; any send in flight when the process dies is lost with no trace; and every screen open costs a 500-row network round-trip before anything renders. None of those get better with more users — the last one gets linearly worse in egress and in cold-start latency, and the first two get more frequent as your user base moves onto worse networks than yours."
