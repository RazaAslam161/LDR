# End-to-end encryption key management for a two-person app: identity keys, prekeys, key change / safety numbers, survivable recovery (escrow vs. user-held keys), key transparency, multi-device linking, and metadata minimisation — benchmarked against Signal, WhatsApp, Meta Messenger (Labyrinth) and Apple, then mapped onto Flutter + Supabase.

## Mechanism
## 1. The directory is a dumb, untrusted store of public keys

DOCUMENTED (X3DH §2.4, §3.2, §3.3): each user holds a long-term identity key IK; publishes a medium-term signed prekey SPK plus `Sig(IK, Encode(SPK))`; and a queue of one-time prekeys OPK. A "prekey bundle" is `{IK_B, SPK_B, Sig(IK_B, SPK_B), optionally OPK_B}`. "The server should provide one of Bob's one-time prekeys if one exists, and then delete it. If all of Bob's one-time prekeys on the server have been deleted, the bundle will not contain a one-time prekey." Sessions still establish without an OPK — degraded forward secrecy, not failure. Rotation guidance is soft: "once a week, or once a month", and the previous signed prekey private key is retained "for some period of time, to handle messages using it that have been delayed in transit."

PQXDH adds a parallel KEM tier: a *signed last-resort* pqkem prekey PQSPK plus signed one-time pqkem prekeys PQOPK, each individually signed by IK (Kyber-1024, IND-CCA). The last-resort key is the structural answer to pool exhaustion.

DOCUMENTED (WhatsApp Encryption Overview, Feb 2026): identical shape — "Identity Key Pair – A long-term Curve25519 key pair, generated at install time", "Signed Pre Key – … signed by the Identity Key, and rotated on a periodic timed basis", "One-Time Pre Keys – A queue of Curve25519 key pairs for one time use, generated at install time, and replenished as needed."

**Real constants, from Signal-Android source (not marketing):**
- `PreKeyUtil.BATCH_SIZE = 100` — one-time EC *and* Kyber prekeys generated 100 at a time
- `PreKeyUtil.ARCHIVE_AGE = 30 days` — retired signed prekeys kept 30 days before deletion
- `PreKeysSyncJob.ONE_TIME_PREKEY_MINIMUM = 10` — refill triggered when the server reports < 10 remaining (checked for EC and Kyber independently)
- `PreKeysSyncJob.REFRESH_INTERVAL = 2 days` — signed prekey and last-resort Kyber prekey rotation cadence
- `PreKeysSyncJob.MAXIMUM_ALLOWED_SIGNED_PREKEY_AGE = 14 days`

**Measured (Prekey Pogo, arXiv 2504.07323, WhatsApp):** initial reserve 812 prekeys on Android/iOS (50 Windows, 200 macOS/Web); "all implementations use a fixed refill batch of 812 elements"; "all clients push a new prekey batch (812 elements) to the server as soon as it has only 10 remaining prekeys left"; signed prekeys refreshed "usually once every month" vs Signal's two-day rotation. Critically: "WhatsApp currently does not employ any rate limiting on fetching prekey bundles" — researchers depleted 812 prekeys in ~10 seconds, saw 503s above ~50 req/s and a hard block above ~2,000 req/s, and used refill timestamps as an online/offline oracle.

## 2. Key change — the mechanics almost nobody copies correctly

This is the part where the engineering detail actually lives. From `SignalBaseIdentityKeyStore.java` (Signal-Android):

`saveIdentity(address, identityKey, nonBlockingApproval)`:
- **No record** → save with `VerifiedStatus.DEFAULT`, `firstUse = true` → `SaveResult.NEW`. Silent TOFU, no user-visible event.
- **Key differs from stored** → four side effects, in order:
  1. `VERIFIED` or `UNVERIFIED` → forced to `UNVERIFIED`; anything else → `DEFAULT`. Verified state is **only ever downgraded automatically**.
  2. `IdentityUtil.markIdentityUpdate(context, recipientId)` — inserts a permanent, visible event into the conversation transcript.
  3. `sessions().archiveSiblingSessions(address)` — sessions are **archived, not deleted**, so in-flight ciphertext under the old ratchet still decrypts.
  4. `senderKeyShared().deleteAllFor(recipientId)` — forces sender-key redistribution.
- **Self-key mismatch** → logged and ignored ("Received different identity key for self, ignoring").

`isTrustedIdentity(address, key, direction)`:
```
case SENDING:   return isTrustedForSending(identityKey, record);
case RECEIVING: return true;
```
**Receiving is unconditionally trusted.** A key change can never cause silent inbound data loss. The gate is only on the send path.

`isTrustedForSending` returns false if: no stored record → true (TOFU); stored key ≠ presented key → false; `VerifiedStatus.UNVERIFIED` → false; `isNonBlockingApprovalRequired(record)` → false.

`isNonBlockingApprovalRequired` = `!record.nonBlockingApproval && !record.firstUse && (now - record.timestamp) < TIMESTAMP_THRESHOLD_SECONDS` where `TIMESTAMP_THRESHOLD_SECONDS = 5`.

That 5-second constant is precisely the behaviour Signal's blog describes in prose: "if the warning doesn't appear until *after* you hit 'send', or if the warning only appears briefly *before* hitting 'send', the message will not be delivered unless you explicitly approve it." For contacts explicitly marked verified, "sending a new message to that contact always requires manual approval."

**Safety number computation** (WhatsApp whitepaper, same construction Signal uses):
1. Lexicographically sort the user's device identity public keys and concatenate.
2. **Iteratively SHA-512 hash the sorted identity keys and user identifier 5,200 times.**
3. Take the first 30 bytes.
4. Split into six 5-byte chunks; each chunk as a big-endian unsigned integer mod 100000 → 5 digits.
5. Concatenate → 30-digit fingerprint. The **60-digit** number is the two parties' 30-digit fingerprints concatenated.

Signal moved from per-user to per-conversation ("a sorted concatenation of two 30-digit individual numeric fingerprints") and folded the phone number in to "strengthen the relatively short safety number against cryptanalytic attacks" and block unknown-key-share attacks.

**What happens to previously received messages: nothing.** Plaintext already committed to the local DB is untouched. Old sessions are archived. But the *new* device has no history — Signal's PIN restores "your profile, settings, and who you've blocked", not messages. Documented: if Secure Backups weren't enabled before the reinstall, chat history cannot be recovered.

**The repair loop (`MessageDecryptor.kt`)** — this is the piece nobody implements:
- On `ProtocolUntrustedIdentityException` / `ProtocolNoSessionException` / `ProtocolInvalidMessageException` → build a `DecryptionErrorMessage.forOriginalMessage(...)` and send it back as a **retry receipt** (`SendRetryReceiptJob`).
- If the failing envelope was a **prekey message** → "Forcing a prekey rotation before requesting the retry": `PreKeysSyncJob.create(forceRotationRequested = true).asChain().then(retryJob)`.
- Rate limits (`RemoteConfig.kt` defaults): `retryReceiptMaxCount = 10` per sender within `retryReceiptMaxCountResetAge = 3 hours`, then ignore; the *responding* side will re-encrypt originals up to `retryRespondMaxAge = 14 days` old.
- `ProtocolDuplicateMessageException` → swallowed silently. Redelivery is idempotent by construction.
- If retry receipts are disabled → fall back to a session-reset job plus a visible error message in the thread.

## 3. Multi-device: two incompatible models

**Signal — linked devices share the account identity private key.** Provisioning: the new device generates a Curve25519 keypair and a temporary "provisioning address", encodes both in a QR code; the primary encrypts a `ProvisionMessage` containing `identityKeyPrivate`, address, userAgent and `provisioningCode` to that ephemeral public key. Consequence, confirmed by Signal's CEO: linking/unlinking a device and phone-to-phone device transfer produce **no safety-number change**, because the underlying key material is unchanged.

History sync to a new linked device: the primary bundles everything into "a compressed, encrypted archive" under "a strong, random, one-time-use 256-bit AES key that is securely transferred to the new linked device as part of the provisioning message", uploaded through the normal attachment infrastructure — which "automatically deletes encrypted files 45 days after they are uploaded", which is exactly why the media-sync window is 45 days. Text archives "usually fit in just a few megabytes after compression"; the new device gets pointers to attachments, not re-uploads.

**WhatsApp — every device has its own identity key, bound by a signature pair.** "With multi-device, each device now has its own identity key." Linking produces:
- `Account Signature = CURVE25519_SIGN(I_primary, ACCOUNT_SIGNATURE_PREFIX || L_metadata || I_companion)`, prefix `0x0600` (or `0x0605` for Cloud API)
- `Device Signature` computed by the companion over the primary's identity key
- `Signed Device List Data`, signed by the primary's identity key with prefix `0x0602`

Security codes hash over **all** of the account's device identity keys, so Automatic Device Verification means "someone needs to compare another user's security code only if that user reregisters their entire account." Note the documented scorched-earth event: linking Cloud API "generates a new random Identity Key thereby invalidating all existing companions and existing end-to-end encrypted Signal sessions."

## 4. Survivability — three real escrow designs, with numbers

### (a) Signal SVR2/SVR3: PIN → hardware enclave, hard guess ceiling
Client side (`libsignal/rust/account-keys/src/hash.rs`): the PIN is normalised (trim whitespace; non-Arabic digits → 0-9; NFKD), then **Argon2id, m_cost = 16 MiB, t_cost = 32, p_cost = 1, output_len = 64, 32-byte per-user salt**. The 64 bytes split: "The 32 byte prefix" = `encryption_key`, "The 32 byte suffix" = `access_key`. The access key authenticates to the enclave; the encryption key encrypts the master key client-side. The enclave never sees the PIN or the plaintext master key.

Key derivation as published:
```
auth_key   = HMAC-SHA256(stretched_key, "Auth Key")
c1         = HMAC-SHA256(stretched_key, "Master Key Encryption")
c2         = Secure-Random(32)
master_key = HMAC-SHA256(key=c1, c2)
```
c2 is 256 bits of machine entropy — the master key's strength is *independent of PIN strength*.

`maxTries = 10` (Signal-Android `SecureValueRecoveryV2.kt`). All enclave state lives "in the enclave's hardware-encrypted RAM, and never touch[es] the disk"; **in-memory Raft** across replicas exists specifically so "malicious operators [cannot] roll back guess counters through replica manipulation." SVR3 (OSDI '24) splits the secret across Intel SGX on Azure, AMD SEV-SNP on GCP and AWS Nitro, via a Ristretto OPRF — compromising two of three yields nothing. Published cost: **$0.0025 per user per year, 365 ms per key recovery, designed for 500M+ users.** Stated design priority: "if there is a choice between 'lose the secret material forever' and 'store the secret material but potentially leak it', we'll choose the former."

Registration Lock rides on the PIN and expires after **7 days** of account inactivity (client keep-alives, including linked-device activity, reset the timer). PIN minimum 4 digits, alphanumeric allowed; reminders "get less frequent over time"; "your PIN isn't recoverable if you forget it."

### (b) WhatsApp E2EE backups: OPAQUE + HSM vault (whitepaper v2, May 2026)
- Client CSPRNG generates backup key **K, 256 bits / 32 bytes**, "only known to the client and … never transmitted outside of the client unencrypted". The backup file is symmetrically encrypted with K, then uploaded to iCloud/Google Drive.
- Registration via **OPAQUE**: `RegistrationRequest` → server returns `RegistrationResponse` + `RegistrationResponse_sig` + random challenge `OPAQUE_C`; client's Registration Finish yields `RegistrationUpload` and `OPAQUE_K` (a **64-byte payload**); "The client encrypts key K using **AES-GCM-128 with the first 16 bytes of OPAQUE_K**" and uploads the ciphertext.
- Retrieval: OPAQUE login. "The client sends `CredentialRequest` to the server, **which in turn decrements the attempt count**". Client receives `EK || K_NONCE` wrapped under `SHARED_K`/`RK_NONCE`, unwraps, then `K = AES-GCM(data=EK, key=OPAQUE_K, nonce=K_NONCE)`.
- Vault resilience: "majority-consensus based system … deployed in **seven or more datacenter sites**", organised as a fleet of "islands" of identical replicas. It enforces attempt limits and renders the key "permanently inaccessible after a certain number of unsuccessful attempts."
- Attempt ceiling, stated in Meta's Labyrinth paper: "**Backup Key Vault limits each user to 10 incorrect guesses**."
- Vault authenticity: 2021 design hardcoded fleet public keys in the app. v2 adds over-the-air **Validation Bundles** — Meta submits HSM fleet public keys to **Cloudflare Key Transparency** under namespace `meta.encrypted_backups.fleet_keys.v1`; Cloudflare signs and keeps an audit log, Meta counter-signs, and the client verifies Cloudflare's signature with a baked-in Cloudflare key, then Meta's counter-signature, then checks the bundle timestamp is inside the validity window, then checks the responding HSM's key is in the list with the right role (`1 = Login`, `2 = Register`).
- **Escape hatch:** the 64-digit key. "the key is not sent to the HSM Backup Key Vault." No escrow at all.

### (c) Meta Labyrinth: multi-device encrypted history with revocation
Per-device keys: `deviceKey` (XEdDSA signing), `epochStorageKey` (X25519 encryption), `epochStorageAuthKey` (X25519 auth). The server stores the public halves plus self-signatures with use-case bytes `0x30` / `0x31`.

**Epochs** = "a period of time during which no device is revoked". First `epochRootKey` = `random(32)`; thereafter:
```
newEpochEntropy = random(32)
(epochChainingKey, epochDistributionPreSharedKey) = kdf(previousEpochRootKey, null,
        "epoch_chaining_" || prevSeqID || "_" || prevEpochID)
epochRootKey = kdf(newEpochEntropy, epochChainingKey, "epoch_root_key")
```
The root key is **never shared directly** — only the 32-byte entropy is, encrypted per-recipient with Labyrinth HPKE, and only after a MAC membership check (`mac(previousEpochDeviceMacKey, deviceKeyPub)`). Stated invariant: "an epoch can only ever be created containing devices that had been members of the previous epoch."

Message keys: `messageKey = kdf(epochRootKey, NULL, "message_key_in_epoch_"||seqID||"_cipher_version_3_thread_"||threadId)`.

Primitives: AES-GCM-Extended (32-byte key, 28-byte nonce, XChaCha-style subkey/subnonce derivation over AES-GCM-256) with **PADMÉ** padding; HMAC-SHA256; HKDF-SHA256; XEdDSA; X25519 HPKE; and a novel **Oblivious Revocable Function** for attachment unlinkability. "Where unspecified, Labyrinth typically uses 32 byte secrets."

**Recovery codes: 40 characters** — 1 version char (currently `2`), 1 identifier char, **34 chars of entropy**, **4 chars of error correction**. Constrained alphabet with `B, G, I, O` folded to `8, C, 1, 0`. ECC over GF(32) with a 4×38 generator matrix such that `G * (entropy || code) = 0`. The code KDFs to `(vdeviceId, vdeviceDecryptionKey)` for a read-only **Virtual Device** — the code never decrypts data directly, it decrypts a key bundle.

**Five independently revocable recovery mechanisms, one Virtual Device each:** (1) user holds the code; (2) user PIN, with the code stored in the WhatsApp Backup Key Vault, 10 guesses; (3) iCloud Drive / Google Drive app-hidden folder — "inaccessible to Meta, but Meta's end-to-end encryption does not protect them from their cloud drive providers"; (4) **device keychain** — a code generated at setup and saved locally, which "will persist across uninstalls", explicitly for "the significant population of users who uninstall and reinstall the app on the same device"; (5) **one-time code** between two devices: a random **6-digit** code, **3 guess attempts**, over a **CPace PAKE**, carrying `temporaryClientState, mailboxRootSalt, epochRootKey, epochID, epochSequenceID`.

**Published known limitations** (rare honesty, worth copying as a practice): epoch rotation "has not yet been implemented on device removal"; virtual-device revocation not fully exposed, so "any recovery code generated may remain viable"; a malicious server can **truncate the epochs** served to a restoring device, colluding with a revoked device so new messages get written under an epoch the revoked device knows; and the server can show each device only a **subset** of the device list (membership enumeration).

Labyrinth 1.1 (May 2026) adds sender-side backup writes: "Each message is wrapped with a message encryption key that the sender places directly into the recipient's encrypted backup", so history survives the recipient being offline at send time.

### (d) Apple iCloud Keychain escrow: the cleanest statement of the trade-off
HSM clusters hold escrow records; the iCloud Security Code is verified with **SRP** so "the code itself isn't sent to Apple"; **exactly 10 attempts**, and on the 10th failure "the HSM cluster destroys the escrow record and the keychain is lost forever." "The administrative access cards that permit the firmware to be changed have been destroyed."

## 5. Key transparency — turning "trust the directory" into "catch the directory"

- **Signal KT server**: search keys are ACI, E164, or username hash → identity key. Two structures: a **log tree** (sequential leaves) and **prefix trees** for "efficient lookups of a specific mapping in the large and ever-growing log tree". Clients call a `Monitor` endpoint to check their own mapping was never silently rewritten. Trail of Bits runs the third-party auditor.
- **WhatsApp AKD** (SEEMless + Parakeet): a binary hash tree over hashed contact identifiers; each **epoch** is a version of the tree identified by its root; Cloudflare audits that epochs are consecutive and digests unique. "If Alice loses her phone and rotates her key, her version is updated to v1 in the next update."
- **Apple Contact Key Verification**: CONIKS-derived **verifiable log-backed map**, "a sparse map indexed with a SHA-256 hash of the output of a Verifiable Random Function (VRF) for an iMessage identifier." **Signed Mutation Timestamps** are "auditable promises to make changes to the map" so a new device is usable instantly rather than after the **48-hour Maximum Merge Delay**. An account key in iCloud Keychain signs each device's iMessage keys. Users compare short codes via the **Vaudenay SAS** protocol. "If the account key ever changes … Messages displays an error in the conversation transcript."

## 6. Metadata: what can't be encrypted, and how it's shaved down

Signal **sealed sender**: clients fetch "a short-lived sender certificate from the service attesting to their identity" containing "the client's phone number, public identity key, and an expiration timestamp"; they derive "a **96-bit delivery token** from their profile key" and register it. Messages are handed over **unauthenticated** with the recipient's delivery token; the recipient verifies that the identity key which encrypted the envelope matches the certificate. Blocking a user triggers **profile key rotation**. What remains visible to the operator: recipient, IP, timing, size, connection pattern.

Signal-Server's undelivered-message store is a DynamoDB table with a TTL — the reference config sets `messages: expiration: P30D` (30 days).

Signal Secure Backups (2025): a **64-character recovery key** generated on-device; "Losing it means losing access to your backup permanently, and Signal cannot help you recover it." Free tier = 100 MiB of message storage + the last **45 days** of media; **US$1.99/month** for 100 GB and full media history. Media is double-encrypted ("encrypting the already-encrypted files a second time with a key unique to your backup") and padded "to obscure their true size". View-once messages and anything set to disappear within 24 hours are never backed up.

## Invariants
- The server is an untrusted public-key directory and nothing more. It holds only public material, hands out at most one one-time prekey per request and deletes it, and no security property depends on it behaving honestly. Compromising the server yields the ability to substitute keys — which is detectable — never the ability to read messages.
- Session establishment never fails closed. If the one-time prekey pool is empty the bundle simply omits the OPK (X3DH) or falls back to the signed last-resort PQ prekey (PQXDH). Degraded forward secrecy is preferred over an undeliverable message, and pool exhaustion is a routine event, not an error path.
- The identity private key leaves a device only along a channel the user physically authorised in that moment. Signal: encrypted to an ephemeral key the user scanned off a screen. WhatsApp: it never leaves at all — companions generate their own and get a signature chain instead.
- Verified trust state is monotonically downgradable and never automatically upgradable. On a key change, VERIFIED and UNVERIFIED both collapse to UNVERIFIED; only a human action restores VERIFIED.
- A peer's identity key change is a permanently recorded, user-visible event in the conversation transcript. Never silent, never a transient toast, never only in a settings screen.
- The trust decision gates SENDING only. `isTrustedIdentity(..., RECEIVING)` returns true unconditionally, so a key change can never cause silent inbound message loss — the failure mode is 'you must approve before you speak', never 'you never heard them'.
- Session state is archived, never destroyed. `archiveSiblingSessions` plus retaining the previous signed prekey private key for ~30 days means ciphertext already in flight under the old ratchet still decrypts after the rotation.
- Redelivery is idempotent by construction: a duplicate is a typed, silently-swallowed exception (`ProtocolDuplicateMessageException`), not a user-visible error and not a duplicated row.
- Any secret a human can remember is an authenticator to a rate-limited, rollback-proof oracle — never itself the key. Signal's master_key = HMAC(c1, c2) with 32 random bytes of c2; WhatsApp's K is 32 CSPRNG bytes. PIN strength bounds only the number of guesses an attacker gets, never the key's entropy.
- The guess counter must be tamper-evident and rollback-proof, or it is worthless. Signal uses in-memory Raft across enclave replicas precisely so a malicious operator cannot restore an old counter from a replica; WhatsApp uses majority consensus across 7+ datacenter sites; Apple destroys the HSM admin cards so the firmware enforcing the ceiling cannot be changed.
- Every recovery path is an explicitly enrolled, individually revocable object. Labyrinth models each mechanism (user-held code, PIN-in-vault, cloud drive, device keychain, one-time code) as its own Virtual Device with its own recovery code, so revoking one does not revoke the others and none is an implicit backdoor.
- Forward access is bounded by epoch membership: 'an epoch can only ever be created containing devices that had been members of the previous epoch', and only the new entropy — not the derived root key — is distributed, gated on a MAC proof of prior membership.
- Ciphertext length is treated as content. PADMÉ padding in Labyrinth; Signal double-encrypts backup media and pads 'to obscure their true size'. Anything that reveals plaintext length is a leak that must be budgeted for, not ignored.
- What the operator can observe is enumerated and published, not assumed to be nothing. Signal publishes what sealed sender does and does not hide; WhatsApp explicitly documents which chats are not E2EE; Meta publishes Labyrinth's unfixed epoch-truncation and membership-enumeration weaknesses.
- Total loss of all authenticators is designed to be terminal, and the product states this before the fact rather than after. 'the HSM cluster destroys the escrow record and the keychain is lost forever' (Apple); 'Losing it means losing access to your backup permanently, and Signal cannot help you recover it'.

## Failure modes designed for
- Server substitutes an identity key to MITM a conversation. Countered by safety numbers (5,200 iterated SHA-512s over sorted identity keys + user identifier), the automatic VERIFIED→UNVERIFIED downgrade, a permanent in-thread key-change event, a send block, and — at scale — key transparency logs with third-party auditors so equivocation is provably detectable.
- Server exhausts or withholds one-time prekeys, either to force weaker sessions or to deny service. Countered structurally: the signed prekey (X3DH) and the signed last-resort pqkem prekey (PQXDH) let a session form with zero one-time prekeys available.
- Attacker drains the prekey pool as a side channel. Prekey Pogo showed WhatsApp had no rate limit on bundle fetches: 812 prekeys drained in ~10 seconds, and refill timestamps became an online/offline and device-platform oracle. Signal's much smaller pool (100) plus a 2-day refresh cadence reduces the surface but does not eliminate it.
- Peer reinstalls or replaces their phone mid-conversation. Handled by: unconditional trust on the receive path, archiving rather than deleting sibling sessions, a visible transcript event, downgrading verified state, deleting shared sender keys, and a retry-receipt repair loop.
- A message is undecryptable because the peer's session state was deleted or rolled back. Signal sends a structured `DecryptionErrorMessage` retry receipt; if the failing envelope was a prekey message it forces a prekey rotation *before* retrying; senders honour retry requests for originals up to 14 days old; capped at 10 retries per sender per 3 hours so the loop cannot become a self-inflicted DoS.
- Delayed or reordered messages arriving after a signed prekey rotation. Both X3DH and Signal's implementation retain the previous signed prekey private key (30 days in Signal-Android) specifically for this.
- Duplicate delivery from at-least-once transport. Typed as `ProtocolDuplicateMessageException` and silently dropped — no error surface, no duplicate row.
- Both parties initiate a session simultaneously. Sesame's active/inactive session lists converge over a few exchanged messages; a bounded send-loop limit stops a malicious server from spinning the client forever on orphaned sessions.
- A malicious server rolls back the PIN/password guess counter by manipulating a replica. Countered by in-memory Raft consensus (Signal SVR) and majority consensus across 7+ datacenter sites (WhatsApp vault).
- One enclave vendor or cloud is compromised. SVR3 secret-shares across Intel SGX on Azure, AMD SEV-SNP on GCP and AWS Nitro — two of three compromised still yields nothing.
- The client is tricked into talking to a rogue HSM fleet. Countered by hardcoded fleet public keys (2021), then by Cloudflare-signed, Meta-counter-signed Validation Bundles with a freshness window and per-key role checks (Login=1, Register=2).
- A revoked or stolen device keeps every key it ever saw. Labyrinth's epoch rotation means new entropy is only distributed to devices that were members of the prior epoch and that pass a MAC membership check; revocation additionally requires the server to delete the device's ORF state.
- A malicious server truncates the epoch list served to a restoring device, colluding with a revoked device so new messages get written under a compromised epoch. Meta published this as an unfixed limitation with a proposed mitigation, rather than pretending it does not exist.
- Account takeover by SIM swap or number reuse. Registration Lock ties re-registration to the PIN, with a 7-day inactivity expiry so a genuinely locked-out user is not permanently locked out.
- Brute force of a low-entropy human secret. Layered: Argon2id at 16 MiB / t=32 / p=1 client-side, a hard 10-guess ceiling enforced in hardware, and for the device-to-device path a 6-digit code with 3 attempts run through a CPace PAKE (so the code itself is never sent).
- Ciphertext length or attachment linkage leaking content. PADMÉ padding, double-encrypted and padded backup media, an Oblivious Revocable Function plus a MAC on an indirection object so attachments cannot be linked to a mailbox at rest, and CDN URLs that expire on a TTL.
- The operator building a social graph from message routing. Sealed sender: short-lived sender certificates, a 96-bit delivery token derived from the profile key, unauthenticated delivery, and profile key rotation on block.
- Users who uninstall and reinstall on the same phone — statistically the largest recovery cohort. Labyrinth pre-emptively writes a recovery code to the device keychain at setup, which 'will persist across uninstalls', so the modal case never reaches a recovery flow at all.

## Applicability to Supabase
## Transfers essentially unchanged, on the free tier, for a two-person app

**The directory.** Two tables and one RPC. `device_keys(user_id, device_id, identity_key_pub bytea, signed_prekey_id int, signed_prekey_pub bytea, signed_prekey_sig bytea, kyber_last_resort_pub bytea, kyber_last_resort_sig bytea, rotated_at)`; `one_time_prekeys(user_id, device_id, key_id int, pubkey bytea, kind text)`. RLS: the partner can `SELECT` public keys, only the owner can write their own rows. Claiming is a `SECURITY DEFINER` function doing `DELETE FROM one_time_prekeys WHERE ctid = (SELECT ctid FROM one_time_prekeys WHERE user_id = $1 ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *` — `SKIP LOCKED` is the exact Postgres equivalent of "provide one and then delete it" under concurrency. Return the bundle with a NULL one-time prekey when the pool is empty and let the client fall back to the signed prekey; never error.

Copy Signal's constants verbatim, they cost nothing at your scale: batch 100, refill below 10, rotate the signed prekey and last-resort Kyber key every 2 days, reject signed prekeys older than 14 days, retain retired signed prekey privates 30 days locally.

The Prekey Pogo finding is *more* relevant to you than to WhatsApp, not less. RLS gives you authenticated fetches for free, but a claim endpoint with no counter lets one partner (or a compromised session) drain the other's pool, and the `rotated_at`/refill timestamp is a clean online-status oracle for anyone who can read the row. Rate-limit claims per (claimer, target) inside the RPC and do not expose refill timestamps to the peer.

**Safety numbers.** Pure Dart, no server. Sort the peer's identity keys, iterate SHA-512 5,200 times over `(sorted_keys || user_identifier)`, take 30 bytes, six 5-byte big-endian chunks mod 100000, concatenate both parties' 30-digit fingerprints in sorted order. 5,200 SHA-512s over ~64 bytes is well under a millisecond on an IN2015. Render as 12 groups of 5 plus a QR containing version, both user ids, and the full 32-byte identity keys — exactly WhatsApp's QR contents.

**The key-change state machine.** This is the highest-value thing to copy and the most commonly botched. Local table `identities(peer_user_id, identity_key bytea, verified_status int, first_use bool, changed_at timestamptz, nonblocking_approval bool)` — client-side SQLite, not Postgres; the server has no business knowing your trust state. Then port the logic exactly: receive path never blocked; send path blocked on key mismatch, on UNVERIFIED, or on `!approved && !first_use && now - changed_at < 5s`; on change downgrade verified state, insert a permanent transcript row, archive (never delete) the session. Your app is a couple's app — the "safety number changed" event carries real social weight, so the copy matters: "your partner reinstalled or got a new phone; messages you already have are unaffected; nothing you sent before was exposed."

**The repair loop.** Also directly portable and also the thing nobody builds. On decrypt failure, send a typed retry request over the same Realtime channel carrying `(original_message_id, sender_device, client_timestamp)`; the peer looks up its local plaintext outbox and re-encrypts if the original is ≤14 days old; cap at 10 per 3 hours. On a failed prekey message, force a prekey rotation before the retry. For two people this is a few hundred lines and it is the difference between "this message could not be decrypted" being transient and being permanent.

**Metadata discipline within Supabase's shape.** You CAN encrypt: message body, attachment bytes, filename, mimetype, dimensions, reactions, quoted text, link previews (generate client-side), the disappearing-timer value, profile display name and avatar. You CANNOT hide, and must accept: row existence and count, `created_at`, `sender_id`/`recipient_id` (the RLS predicate needs them), thread id, ciphertext length (mitigate with PADMÉ-style padding), Storage object size and access time, Realtime topic names and join/leave timing, presence, IP, device, FCM token, push timing. Concretely: store ciphertext as `bytea`, never base64 in `text` (33% inflation on a 500 MB free-tier DB); name Storage objects with random UUIDs, never `couple_id/thread/2026-08-09-selfie.jpg`; do not enable Postgres Changes on encrypted tables (it ships the whole row payload over the socket, doubling your realtime message count for no benefit) — use Broadcast with an id only.

**FCM.** Nothing decryptable in the payload. Data-only message carrying a message id; the client wakes, fetches, decrypts, and posts the notification locally. This is the same shape Signal uses. The Android cost is real and you will feel it on the Vivo and OnePlus 7 in particular: OEM battery managers kill background wakeups aggressively, so notification latency becomes cold-start + round trip, and on some ROMs it becomes "when the user opens the app". Budget for that, and keep a foreground-service or high-priority path for calls.

## Needs a paid tier

The binding constraint is **200 concurrent Realtime connections on Free**, and a two-person app has the worst possible connection amortisation — every couple wants both sockets live for the experience to feel instant. 1,000 couples is up to 2,000 sockets: Pro (500 included, then $10 per 1,000) or Pro-without-spend-cap (10,000). Free also caps at 100 messages/sec, 100 channel joins/sec, and 256 KB Broadcast payload (Pro: 3,000 KB) — a padded text ciphertext is fine, anything image-shaped must go through Storage.

The 2M realtime messages/month is tighter than it looks: 1,000 couples means 2,000 messages/couple/month ≈ 66/day, and that counts every presence beat, typing indicator and read receipt, not just messages. Typing indicators alone will consume it. Either drop them or send them at a throttled rate over a separate ephemeral channel you are willing to lose.

## Does not exist and cannot be built on this stack

**There is no enclave, no HSM, and therefore no rollback-proof guess counter.** This is the load-bearing gap. Every escrow design above — SVR2/SVR3, the WhatsApp Backup Key Vault, iCloud Keychain escrow — reduces to "a tamper-evident device that will destroy the secret after N wrong guesses and cannot be rolled back". A Postgres row holding `attempts_remaining` is decremented by code you control, restorable from a nightly backup, and readable by anyone with the service-role key. It provides *zero* cryptographic guarantee. Building it would be security theatre, and pgsodium is pending deprecation with Supabase explicitly advising against Server Key Management and Transparent Column Encryption on their platform anyway.

The honest conclusion: **take WhatsApp's 64-digit path, not the password path.** A user-held, high-entropy recovery key with no server component is the only design whose security claim you can actually make. But copy Labyrinth's *ergonomics* rather than shipping raw hex — 40 characters, constrained alphabet, B/G/I/O folded to 8/C/1/0, and error-correction characters so a mistyped code is corrected instead of silently failing. That single design choice is the difference between a recovery key people can use and one they cannot.

The best available substitute for escrow is exactly Labyrinth's tiers 3 and 4, and both are free: write a recovery code to the Android Keystore / EncryptedSharedPreferences at setup so uninstall-reinstall on the same phone never reaches a recovery flow at all (the largest real-world cohort), and optionally offer storage in the user's own Google Drive app-hidden folder — with Meta's exact disclosure: inaccessible to us, but not protected from Google.

**No key transparency, and you do not need it.** KT exists to approximate out-of-band verification when users cannot meet. Your two users share a bed. The substitute is strictly stronger and free: an in-person safety-number/QR comparison, plus a permanent transcript record of every key change, plus — worth the extra 50 lines — cross-signing: after a successful in-person verification, each device signs the partner's identity key and stores the signature locally, so a server-substituted key fails a signature check rather than merely raising an advisory the user can swipe away.

**Multi-device: pick one model deliberately.** Signal's (share the identity private key via a QR-provisioned ephemeral X25519 encryption) is far less code and matches the intuition that buying a tablet should not change your safety number — but a compromised second device is a compromised account, and revocation means rotating the identity key, which does change the safety number. WhatsApp's (per-device identity key + Account Signature + Device Signature + signed device list) gives real per-device revocation at the cost of a signature chain, device-list distribution, and fan-out encryption. For two people with two phones, Signal's model. If you ever add a tablet or web client you actually want to revoke, WhatsApp's.

**Edge Functions must never see plaintext or private keys.** Their legitimate roles here are exactly three: minting TURN credentials (already the case), rate-limiting prekey claims, and dispatching payload-free FCM pushes. Any design where a Deno function decrypts anything is not end-to-end encrypted, regardless of what the marketing copy says.

## Scale
**Prekey pool — never the bottleneck.** 100 EC + 100 Kyber public keys per user is roughly 160 KB per user with Kyber-1024 pubkeys (~1.5 KB each), so Kyber, not X25519, dominates: 10,000 users ≈ 1.6 GB, which blows the 500 MB free-tier DB on prekeys alone. If you adopt PQXDH, drop the one-time Kyber pool entirely and rely on the signed last-resort Kyber prekey, or cut the batch from 100 to ~20. Pure-X25519 prekeys are ~32 bytes and never matter. The real scaling risk is the claim RPC under concurrency — use `FOR UPDATE SKIP LOCKED` with a partial index on `(user_id)`, and it will not contend at any scale you will see.

**Realtime — the hard wall, and it arrives early.** 200 concurrent connections on Free means roughly 100 couples online simultaneously, and for a couples app "simultaneously online" is close to the entire point. At 1,000 couples with typical concurrency you are into Pro-uncapped ($10 per 1,000 above 500) — call it $20–60/month, which is cheap. The lever that actually saves money is not paying for connections but dropping the socket when the app is backgrounded and relying on FCM data messages for wake-up. That converts a persistent-connection cost into a cold-start latency of one to two seconds, and on aggressive Chinese OEM ROMs (your Vivo, your OnePlus 7) into "whenever the OS feels like it". For a couples app the latency regression on a message you are actively waiting for is worse than the bill; keep the socket while foregrounded, drop it after ~30 s in background.

**Realtime messages — 2M/month is tighter than the connection cap.** At 1,000 couples that is 66 events per couple per day *including* presence, typing, receipts and reactions. Typing indicators at even 1 Hz during composition will exhaust it alone. Either drop typing indicators, or throttle to one event per 3 s and accept loss. Also: never enable Postgres Changes on encrypted message tables — it broadcasts the full row (up to 1,024 KB) and doubles your event count for zero benefit when the payload is opaque anyway.

**Padding costs storage, and free tier is 500 MB / 1 GB.** PADMÉ overhead is bounded at ~12% but ciphertext framing, nonces and tags add ~50 bytes per message on top. Storing ciphertext as base64 `text` instead of `bytea` costs another 33% — at 1,000 couples × 50 messages/day × 1 KB that is ~1.5 GB/month of message rows before media. Free tier dies at a few hundred active couples; Pro's 8 GB dies at a few thousand unless you expire old rows or move history to client-held backups (which is what Signal's 100 MiB free message quota and 45-day media window are quietly doing).

**Escrow decision does not scale-break, it support-breaks.** At 1,000 couples, if 2% lose or replace a phone monthly with no backup enabled, that is ~20 permanently destroyed histories and 20 conversations per month you cannot resolve — for a couples app, each one is a genuinely upsetting loss of shared history, not a shrugged-off inconvenience. WhatsApp and Signal absorb this with an enormous FAQ surface, a PIN reminder cadence that "gets less frequent over time", and blunt pre-emptive wording. You need the same wording *before* the fact, on the setup screen, and you need the device-keychain recovery code written at setup so the uninstall-reinstall cohort never reaches this path.

**Where copying SVR is not economic.** SVR3's published $0.0025/user/year and 365 ms recovery latency assumes amortisation over 500M users across three cloud vendors' confidential-compute SKUs. A single AWS Nitro Enclave-capable instance costs more per month than your entire Supabase bill at 1,000 users. There is no scaled-down version of this design: the fixed cost is the fixed cost. Buy nothing; ship a user-held key with good ergonomics.

**Where copying key transparency is not economic.** Signal runs a dedicated KT server (log tree + prefix trees + a Monitor endpoint) plus an external auditor; WhatsApp pays Cloudflare to audit epoch consistency. That is a service, an auditor relationship, and a client-side proof-verification implementation. Do not build it. Your two-person topology makes the thing KT approximates — real out-of-band verification — actually achievable, and cross-signing after in-person verification gets you a stronger local guarantee than KT gives Signal users who never compare numbers.

**Where the design breaks that nobody warns you about.** The retry-receipt loop needs a local plaintext outbox retained for 14 days to be able to re-encrypt on request. That is a plaintext store on disk, which is a real trade against your threat model (and against an adult-content app where device seizure is a plausible concern). Signal accepts it because the alternative is permanent undecryptable messages. If you shorten the window to, say, 48 hours, you shrink the exposure and lose repair for anyone offline longer than a weekend. Pick deliberately and write the number down.
