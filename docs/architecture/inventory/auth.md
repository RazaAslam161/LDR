## Session bootstrap and state machine (SessionNotifier)  [risk: high]
- purpose: Single source of truth for 'who am I, who is my partner, am I paired'; drives every redirect and most feature gating.
- files: E:/LDR/mobile/lib/core/session_provider.dart (SessionState l.15-57, init l.65-89, loadProfile l.112-208, _subscribePresence l.212-235, signOut l.244-254); consumed by router.dart l.67 and providers.dart currentProfileProvider/currentCoupleProvider
- tables: public.profiles (self, via .eq('id',uid)), public.couples (via .eq('id', profile.couple_id)), public.profiles again for the partner (.eq('couple_id').neq('id',uid)), public.presence (integrity read + repair write + setOnline).

Requires a live websocket; a missed reconnect means a frozen partner avatar/name/status until reconnectPresence() runs from realtime resume.
- how it works: init() seeds from client.auth.currentSession synchronously, then listens to onAuthStateChange. EVERY auth event with a non-null session (including tokenRefreshed, roughly hourly) calls loadProfile(). loadProfile does up to 5 sequential round trips with 10s timeouts each: profiles select, couples select, partner profiles select, presence couple_id verify, presence repair/setOnline. On any throw it sets loading=false and stores the error string but keeps the previous profile/couple.
- weaknesses: (1) REAL BUG — SessionState.copyWith uses `session: session ?? this.session` (l.49), so a null session can never be written through copyWith. gotrue 2.22.0 emits AuthChangeEvent.signedOut with a null session when a refresh token is rejected (gotrue_client.dart l.1496-1498). The listener at session_provider.dart l.71-74 therefore keeps the dead session, isAuthenticated stays true, the router never sends the user to /signin, and every PostgREST call 401s forever until the app is killed and relaunched. (2) loadProfile is a 5-round-trip fan-out fired on every token refresh and every app resume (main.dart _refreshOnResume, throttled to 10s). (3) fetchPartner uses .maybeSingle() and would throw if a couple ever held 3 profiles. (4) The presence 'integrity guard' (l.172-195) is an unconditional extra read+write on every load, per user, forever — the comment openly calls it '~200ms on every app load'. (5) A transient failure of the couples select leaves couple=null, which the router reads as 'not paired' and funnels a fully paired user to /couple.
- scale reason: Every token refresh and every foreground resume costs 5 serialized DB round trips per user plus a presence write; at thousands of users that is a constant multiplied read load with no caching, and the null-session bug produces permanently wedged clients that keep retrying.

## Router redirect funnel  [risk: high]
- purpose: Force a user through signin → profile → couple → role-setup before any app route is reachable.
- files: E:/LDR/mobile/lib/core/router.dart buildRouter redirect (l.66-118); _SessionListenable (l.334-339) bridges Riverpod to GoRouter refreshListenable
- tables: None directly — reads only the in-memory SessionState.

## Device push-token binding (identity side)  [risk: high]
- purpose: Associate this device's FCM token with the signed-in profile so pairing/reach/call/message pushes can reach it.
- files: E:/LDR/mobile/lib/core/services/fcm_service.dart (registerToken l.84-100, _save l.102, clearToken l.111-116); supabase_repository.dart setFcmToken (l.392-400); called from app_shell _onReady after pairing, from main.dart on every resume (l.286), and cleared on sign-out (settings_screen.dart l.408, couple_page.dart l.122)
- tables: public.profiles.fcm_token + fcm_token_updated_at (fcm_token added by E:/LDR/supabase/fcm_push.sql l.7).
- transport: This IS the push identity. Server-side notify triggers read profiles.fcm_token and call net.http_post (pg_net), and null the column when FCM answers UNREGISTERED.
- how it works: getToken() with up to 4 attempts and 2s backoff, then a single UPDATE of profiles.fcm_token. Re-registered on every app resume specifically to self-heal a token the notify functions nulled.
- weaknesses: (1) ONE token column per profile — the schema physically cannot represent a user with two devices; the second device silently steals push from the first. (2) The token is stored on the same profiles row the partner can SELECT (profiles_select_self_or_partner grants the partner every column, including fcm_token) — the partner can read your device push token. (3) registerToken runs on every resume, so that is one profiles UPDATE per user per foreground event regardless of whether the token changed. (4) Sign-out clears the token only if the network call succeeds; a failed clearToken leaves the device receiving the previous account's pushes.
- scale reason: Single-token-per-user is a schema-level ceiling that breaks multi-device outright, the partner-readable token is a privacy leak that RLS currently permits, and the per-resume write multiplies with user count.
