## chat.transport (message delivery core)  [risk: high]
- purpose: Get a message from one partner's phone onto the other's screen, and keep the on-screen list consistent with Postgres.
- files: E:/LDR/mobile/lib/features/chat/chat_screen.dart (_subscribe L386-460, _onIncoming L512-549, _catchUp L368-384, _onMsgBroadcast L134-151, didChangeAppLifecycleState L321-333); E:/LDR/mobile/lib/features/chat/chat_repository.dart (subscribe L321-355, fetch L204-220, fetchSince L183-200); E:/LDR/mobile/lib/core/realtime_resume.dart; E:/LDR/mobile/lib/features/shell/app_shell.dart (_reconnectRealtime L69-79)
- tables: public.messages (id, couple_id, sender_id, body, image_path, voice_path, video_path, reply_to_id, kind, seq, created_at, deleted_for_everyone, deleted_by, deleted_at, sender_mood, sender_mood_color). Indexes: messages_couple_created_idx(couple_id, created_at), messages_couple_seq_idx(couple_id, seq). RLS via public.current_user_couple_id().
- transport: THREE independent transports, all in use simultaneously. (1) Supabase Realtime BROADCAST on public topic 'mood_burst:<coupleId>' — carries text and image 'msg' events, typing, 'cleared', and mood/GIF bursts. Ephemeral, no persistence, no auth (see weaknesses). (2) postgres_changes on 'messages:<coupleId>' with filter couple_id=eq.<id>, INSERT + DELETE events. (3) FCM data push via a per-row AFTER INSERT trigger (see chat.push). Recovery is a plain REST catch-up query, not a transport.
- how it works: On mount ChatScreen fetches the newest 300 rows ordered by created_at desc (ChatRepository.fetch, hard limit 300, NO pagination — older history is unreachable in the UI). It then calls _subscribe(), which awaits removeChannel() on the three previous channels before joining fresh ones (Supabase never dedupes by topic, so unsubscribe+rejoin left dead channels). Both broadcast and postgres_changes fire _onIncoming; dedupe is by message id held in an in-memory Set<String> _ids. A broadcast-delivered message is constructed client-side with seq=0; when the slower Postgres echo arrives with the same id, Message.reconcileWith() adopts the server's created_at, paths, deletion flags and seq. Because both realtime paths are live-only (their cursor is the moment of join), _catchUp() issues a REST SELECT ... where seq > _maxSeq order by seq limit 500 on every socket re-open (realtimeResumed fires from realtime.onOpen) and on every app resume. _maxSeq is a fold over the whole in-memory list on every access. Every _onIncoming does setState + a full _sortMessages() re-sort of the entire list.
- weaknesses: The broadcast topic 'mood_burst:<coupleId>' is a PUBLIC Realtime channel — no `private: true` anywhere in lib/, and no realtime.messages RLS in any SQL file. couple_id is not secret (it is the first path segment of every never-expiring public couple_media URL, as hardening_2026_08.sql L25 itself admits). Any client that knows a couple_id can join the topic and (a) read every text message and image path in real time, (b) inject a forged 'msg' with an arbitrary 'sender' — _onMsgBroadcast L134-151 does no membership or sender check, and the fake never gets a DB echo so it sits on screen at seq=0 forever, (c) fire 'cleared' to blank the victim's chat view, (d) fire 'mood' with an arbitrary gif URL that the victim's app loads via Image.network. Separately: hard 300-message ceiling with no scroll-back pagination; O(n log n) full re-sort per message (catch-up of 500 rows = 500 setStates and 500 full sorts); _messages grows unbounded across catch-ups; ChatScreen is rendered directly in a Column in app_shell.dart L238-241, NOT an IndexedStack, so switching tabs DISPOSES the screen — all three chat channels are torn down and 300 rows are refetched on every return to the Chat tab.
- scale reason: postgres_changes re-evaluates the messages RLS policy per change per connected subscriber, and the policy calls public.current_user_couple_id() unwrapped (not `(select ...)`), so it is re-evaluated per row rather than cached as an InitPlan. Every open chat holds 3 channels. The public broadcast topic is a confidentiality and integrity hole that scales linearly with user count — one leaked couple_id is a full live wiretap. The 300-row no-pagination fetch on every tab switch multiplies REST load by navigation frequency.
