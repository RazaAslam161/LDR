## Key exchange + CryptoCore (the crypto under all of Closer)  [risk: fatal]
- purpose: Give the Closer suite one couple-shared symmetric key so intimate text/photos are ciphertext in Postgres.
- files: E:/LDR/mobile/lib/core/crypto_core.dart; E:/LDR/mobile/lib/features/closer/closer_crypto.dart (ensureSharedKey, packMacAndCiphertext, packFull, byteaToBytes, bytesToBytea); E:/LDR/mobile/lib/core/supabase_repository.dart:137-186 (publishMyPublicKey / fetchPartnerPublicKey / keyWasReplaced); E:/LDR/mobile/lib/features/closer/closer_screen.dart (_prepareKey); E:/LDR/mobile/lib/features/settings/settings_screen.dart:328

- transport: None. Key publish/fetch is a plain PostgREST upsert + maybeSingle on demand. No realtime, no push, no invalidation signal — a partner's key rotation is only noticed the next time the other device calls ensureSharedKey.
- how it works: Each device generates one X25519 keypair (package:cryptography), stores the seed base64 in flutter_secure_storage (AndroidOptions(encryptedSharedPreferences: true)), and upserts the public half into partner_keys. ensureSharedKey() publishes mine, reads the partner's row, refuses if it is missing or equals the string literal 'plaintext-v1' (CryptoCore.legacyPublicKey), then does ECDH + HKDF-SHA256(info='miles-closer-v1', empty salt) to a 32-byte key held in a STATIC field CryptoCore._sharedKey. Three different packing layouts coexist: closer_crypto.packMacAndCiphertext (mac||ct, vault + memory threads + afterglow gratitude), fantasy_jar_repository._pack and body_map_repository._pack (ct||mac — the OPPOSITE order, hand-rolled per repo), and packFull (nonce||mac||ct, afterglow photos). bytea is written as a Postgres hex literal ('\x…') string and read back by hand-parsing that hex. A row whose nonce AND mac are all zero is treated as legacy plaintext and returned verbatim on read — pre-2026-08 rows in every Closer table are still base64 cleartext in Postgres and still decode fine.
- weaknesses: 1) REINSTALL IS COUPLE-WIDE DATA LOSS, NOT DEVICE-LOCAL. android:allowBackup="false" (AndroidManifest.xml:54) means the private key is gone on reinstall/new phone. The reinstaller publishes a fresh public key; as soon as the OTHER partner next calls ensureSharedKey they re-derive a different shared key, and every Closer row ever written — vault, fantasy jar, body map, memory threads, afterglow — becomes permanently undecryptable FOR BOTH USERS. Only the device that rotated sets SupabaseRepository.keyWasReplaced, so the innocent partner is told 'N items couldn't be opened — your partner may need to open Closer' (closer_load_result.dart:39-42), which is false: it is never coming back. 2) No re-encryption/migration path, so this is unrecoverable by support. 3) The private key is stored under a single non-user-scoped key name, so two accounts on one device share one identity keypair. 4) CryptoCore.clearCache() has ZERO callers — the derived key survives sign-out in a static; SessionNotifier.signOut (session_provider.dart:244) clears neither it nor the stored private key nor the Memory-Threads PIN. 5) The whole shared-key model gives the partner the same key as you, so nothing in Closer is private FROM the partner even where the UI claims it is (see Fantasy Jar). 6) hmacTag() is documented as HMAC-SHA256 but is keyless 32-bit FNV-1a. 7) One in-memory key per process means everything after key derivation depends on the app being open.
- scale reason: Phone replacement is a routine event; here it silently destroys the couple's entire encrypted history for both people with no recovery and a misleading error message. At thousands of users this is a continuous, unfixable support queue plus real data loss. Also blocks any server-side feature (search, moderation, retention enforcement, migration) forever.

## Touch Trace  [risk: medium]
- purpose: Two-way live finger-drawing canvas.
- files: E:/LDR/mobile/lib/features/closer/touch_trace/touch_trace_screen.dart; touch_trace_canvas.dart (route /app/closer/touch-trace)
- tables: None. Nothing is persisted.
- transport: Ephemeral broadcast on 'touch_trace:<coupleId>' with events stroke_point, stroke_end, clear. Strokes are throttled to ~30 fps (33 ms). Re-subscribes on realtimeResumed. No push.
- how it works: Each pan update normalizes to 0..1 against the canvas constraints and broadcasts {from, stroke, point}. The receiver appends to a local stroke list, deciding whether a point starts a new incoming stroke by comparing the last stroke's ARGB against its own current colour (touch_trace_canvas.dart:105-110). FLAG_SECURE is set. Not encrypted (payloads are plain JSON over the realtime socket).
- weaknesses: 1) Requires both partners online, foregrounded, and on this exact screen — otherwise the drawing goes nowhere. 2) The incoming-stroke heuristic is colour equality: if the partner picks the same colour from the shared 6-colour palette, their strokes merge into yours. 3) It uses raw channel()/unsubscribe() + a manual realtimeResumed listener instead of ManagedSubscription — exactly the duplicate-topic 'joined but dead channel' pattern that realtime_service.dart:76-95 documents as the app-wide bug this primitive was written to fix. 4) ~30 messages/second/user on a shared broadcast topic with no backpressure. 5) Non-private topic, same guessable-couple-UUID exposure as Touch Map.
- scale reason: 30 msg/s per active session is the heaviest realtime consumer in the app and it uses the known-buggy subscription pattern, so reconnect storms leave dead channels. No data at risk beyond the drawing itself.

## Mood Lamp  [risk: low]
- purpose: Pick a colour; it glows on the partner's screen.
- files: E:/LDR/mobile/lib/features/closer/mood_lamp/mood_lamp_screen.dart (route /app/closer/mood-lamp)
- tables: public.mood_lamp EXISTS (couple_id, user_id, color_rgb, updated_at — intimacy_tables.sql:30-36), is RLS'd and in the realtime publication, and is NEVER read or written by any client code. Dead table.

The 4-hour auto-fade Timer dies with the widget. The schema author clearly intended mood_lamp to be the store — it is orphaned.
- scale reason: Low traffic and no data at risk; the cost is a permanently broken-feeling feature and a dead table carrying realtime replication overhead.

## Desire Temperature  [risk: medium]
- purpose: Both rate desire 1-10 daily; the partner's number is revealed only if both are >= 7.
- files: E:/LDR/mobile/lib/features/closer/desire/desire_temp_screen.dart (route /app/closer/desire)
- tables: public.desire_temps (couple_id, on_date date, user_id, score int CHECK 1..10, PK(couple_id,on_date,user_id)) — intimacy_tables.sql:21-27.
- transport: Real postgres_changes subscription on 'desire_temps:<coupleId>' via ManagedSubscription, so the reveal re-checks when the partner submits. No push.
- how it works: NOT ENCRYPTED — score is a plain int. Both submit and load compute the date string from the DEVICE clock: DateTime.now().toUtc() formatted as YYYY-MM-DD (desire_temp_screen.dart:68-70 and 110-112). The query selects user_id and score for the whole couple on that date, then the REVEAL GATE IS APPLIED IN DART: `if (mine != null && partner != null && mine >= 7 && partner >= 7)`.
- weaknesses: 1) The reveal gate is client-side only. RLS (desire_temps_select_member) returns the partner's score to the wire unconditionally, so the partner's number is in the HTTP response even when the UI hides it — trivially read with any proxy or a patched APK. 2) The 'day' is the device's UTC date: partners in different timezones, or a phone with a skewed clock, land on different on_date keys and never match. 3) Scores are plaintext in Postgres with no retention limit.
- scale reason: The single privacy rule of the feature is not enforced server-side, and the day-key comes from the client clock — which breaks for exactly the long-distance, cross-timezone couples the app is for.

## Pick for us (dice)  [risk: low]
- purpose: Roll a random suggestion tag per consented tier.
- files: E:/LDR/mobile/lib/features/closer/pick_for_us/pick_for_us_repository.dart; pick_for_us_screen.dart (route /app/closer/pick-for-us)
- tables: public.dice_rolls (couple_id, rolled_at, tier, result_tags text[]) and public.dice_tier_consents (couple_id, tier, user_id, granted, granted_at) — intimacy_tables.sql:110-125.

- how it works: NOT ENCRYPTED. Tiers and their tag pools are compile-time constants in the DiceTier enum.
