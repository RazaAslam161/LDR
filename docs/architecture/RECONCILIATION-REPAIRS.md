## F1

**Problem.** CLIENT-F2 puts the messages INSERT/UPDATE/DELETE revoke AND the BEFORE UPDATE OR DELETE guard trigger in messaging Stage 1. Three windows, two of which the verifier did not fully enumerate. (a) The INSERT revoke at Stage 1 kills every send in the installed fleet — chat_repository.dart:228/249/279/309 are direct PostgREST inserts, the app is sideloaded with no update channel — and directly contradicts messaging.md Stage 1's own requirement that those inserts keep working and stay contiguous during rollout. (b) The guard at Stage 1 blocks the shipped RPC bodies, none of which set any flag: hide_message (settings_and_delete.sql:35-38, UPDATE deleted_by), delete_message_for_everyone (chat_media_cleanup.sql:19-21, UPDATE + storage delete), clear_conversation_everyone (chat_media_cleanup.sql:36-53, storage delete then bare DELETE). (c) A FIFTH mutation path no resolution names: delete_my_account (account_deletion.sql:50) hard-deletes every message row when the couple empties — the guard would block account deletion, a subject-rights path. Two further on-disk facts change the shape: policy messages_update_member (settings_and_delete.sql:28-31) grants authenticated UPDATE on messages today, so the untracked-mutation window is real and not theoretical; and the old fleet reads the table directly with select() and Message.fromJson falls back to kind='text', so control rows landing at Stage 1 would paint a blank bubble on every installed build for every un-send.

**Repair.** Split the revoke by verb and put the guard BEHIND the RPC replacement, all inside messaging Stage 1's single ACCESS EXCLUSIVE transaction, in this order. STAGE 1, one transaction: (1) create the 32 hash partitions, add cseq / target_cseq / for_user, extend kind to {text,image,video,voice,clear,redact,hide}, backfill cseq by row_number() over (partition by couple_id order by seq, id), seed the chat counter; (2) install the BEFORE INSERT allocator trigger on messages, which assigns cseq to ANY insert including the old fleet's direct PostgREST inserts — this trigger, not the revoke, is what makes appends tracked; (3) replace all FOUR sanctioned bodies in place, same names and signatures so no client changes and no release is needed: hide_message, delete_message_for_everyone, clear_conversation_everyone, and delete_my_account (which sets only the suppression flag and allocates nothing, because it deletes the couple and its allocator rows — there is no stream left to signal on); (4) THEN install the BEFORE UPDATE OR DELETE guard, which raises unless the transaction-local flag miles.chat_mutate is set; (5) revoke UPDATE and DELETE on messages from authenticated and drop policy messages_update_member; (6) restrict the messages SELECT policy to entity kinds (text|image|video|voice) so control rows are reachable only through sync_messages, which is SECURITY DEFINER and bypasses RLS — this hides them from the old fleet's direct read and from its postgres_changes subscription, which is filtered through the same policy by apply_rls. STAGE 10, gated on observed app_runtime_config.min_client_build, the same gate Stage 10 already applies to dropping messages.seq: revoke INSERT. CLIENT-F2's sentence 'add the BEFORE UPDATE OR DELETE trigger and the revoke to Stage 1' is WITHDRAWN, as is its assumption that D4-level privileges exist at Stage 1; it must instead state that from Stage 1 to Stage 10 the mutation rule is enforced by the allocator trigger plus the guard trigger plus the canary, and that the INSERT revoke is defence in depth rather than the load-bearing control. data.md D4 records messages as UPDATE/DELETE revoked at messaging Stage 1 and INSERT revoked at messaging Stage 10; D4 itself revokes nothing on messages.

**Invariant restored.** messaging.md Stage 1's 'the old fleet's direct PostgREST inserts stay contiguous during rollout', and CLIENT-F2's 'NO ROW IN A COUPLE'S CHAT STREAM MAY BE REMOVED OR HAVE ITS PAYLOAD ALTERED WITHOUT ALLOCATING EXACTLY ONE cseq' — with no window in either direction, because the state before the transaction is (old RPCs, no guard, mutation possible but by nobody) and after it is (new RPCs, guard, mutation impossible), and there is no state in between.

**Why it cannot regress.** Enforcement is a trigger, not a privilege. A BEFORE trigger fires on every path — RPC, PostgREST, SQL editor, service role, a future SECURITY DEFINER function — whereas a grant is bypassed entirely by any definer function running as owner, which is GRANT-LANDMINE's own argument turned to this use. CI: enumerate every function body in pg_proc containing an UPDATE or DELETE on public.messages and assert each sets miles.chat_mutate, failing on any body not in the sanctioned list — an assertion that catches the next un-reviewed mutation path the way delete_my_account was missed here. The INSERT-revoke timing cannot regress because Stage 10's gate is a measured min_client_build, not a date.

## F2

**Problem.** R1's invariant_after clause (d) defines the permanent canary as contiguity of messages.cseq per couple — ROW contiguity — which is precisely the assertion messaging.md deleted as the cause of its own FATAL 2 ('ISSUED-RANGE CONTIGUITY, NOT ROW CONTIGUITY ... never of the rows physically present'). Rows leave messages by design: clear_conversation_everyone hard-deletes every row for the couple (chat_media_cleanup.sql:53, the live definition; clear_chat_everyone.sql:22 its predecessor) and delete_my_account hard-deletes (account_deletion.sql:50). Because a clear control row is never deleted by a later clear, two clears leave a permanent hole between them, so the alarm goes red on the second clear and stays red — on the one check R1 itself calls the only place the load-bearing invariant is observable in production, and an alarm that is always red is not an alarm.

**Repair.** Clause (d) is WITHDRAWN and replaced by the definition in corrected_canary. The governing change: the canary learns the ISSUED RANGE from the ALLOCATOR ROW and the DELETION FLOOR from a RECORDED WATERMARK, and infers neither from the rows. Contiguity of the issued range is not scanned at all — a counter that only ever does +1 cannot skip a value, so issued-range contiguity is a property of the allocator, guaranteed by the allocator being the sole writer (F3). What the canary scans is only the boundary between the counter and the rows, over the range in which rows are supposed to still exist. To make the floor readable in O(1) and in the same place as the head, couple_cursor gains floor_pos bigint not null default 0 per counter row: for the 'stream' counter it is written by couple_stream_compact, greatest()-guarded, in the same transaction as its DELETE (which also turns sync_head's floor_pos from a min() aggregate into a single-row read); for the 'chat' counter it is written by clear_conversation_everyone, greatest()-guarded, in the same transaction as its DELETE and its control row. The clear control row remains the authoritative signal for CLIENTS — they cannot read couple_cursor — and the two records of the same fact are written in one transaction, so their agreement becomes an extra predicate rather than a second source of truth.

**Invariant restored.** messaging.md's 'ISSUED-RANGE CONTIGUITY, NOT ROW CONTIGUITY (SERVER-ENFORCED + BY CONSTRUCTION)' verbatim, and transport.md's 'A STREAM POSITION SURVIVES ITS ENTITY' — both of which R1's clause (d) contradicted.

**Why it cannot regress.** Every predicate is expressed against a value written in the same transaction as the deletion it accounts for. A deletion path that does not record its floor fails K3 or S3 on the next tick, which is the intended alarm and not a false one — it is exactly the 'someone added a hard delete without reading this document' case the canary exists for. Two named negative tests are committed with it: (i) run two consecutive clears and assert nothing opens; (ii) hard-delete one row with no control row and no floor write and assert K3 opens with page severity within one tick.

## F3

**Problem.** R1 specifies chat allocation as 'UPDATE couple_cursor SET chat_seq = chat_seq + 1 WHERE couple_id = ? RETURNING chat_seq', 'incremented in ONE UPDATE'. Two defects. (1) It increments before send_message's dedup check, inverting messaging.md's stated step order ('the lock comes first, before anything else ... return the original without bumping the counter'). Retry is the normal case in this design ('No network error is ever terminal. Retry is forever'), so every retry of a send the server already committed would consume a cseq naming no row. (2) It contradicts R1's OWN invariant_after, which says both counters are incremented 'only by a BEFORE trigger inside the appending row's own transaction'. Those are two different allocation sites and they cannot both be the allocator. The conflict with visibility is what decides it: a statement in an RPC body must be followed by an INSERT that names the returned value, and the path that has no RPC — the old fleet's direct PostgREST insert, which F1 requires to keep working and to stay contiguous — has no such statement.

**Repair.** WITHDRAW 'in ONE UPDATE' and WITHDRAW the RPC-body allocation statement. THE ALLOCATOR IS THE BEFORE INSERT TRIGGER ON THE STREAMED TABLE, AND NOWHERE ELSE. On messages it executes UPDATE couple_cursor SET value = value + 1 WHERE couple_id = NEW.couple_id AND counter_kind = 'chat' RETURNING value INTO NEW.cseq — assignment to NEW is the only mechanism that makes the position visible to the row that carries it, and it is the only form that also covers the direct-insert path. When NEW.kind = 'clear' the same trigger sets NEW.clear_through_cseq := NEW.cseq - 1 under the same lock, so the clear's own reach is fixed at allocation and needs no follow-up UPDATE. send_message's step order is restored verbatim and promoted to contract text: (1) SELECT couple_id FROM couple_cursor WHERE couple_id = ? AND counter_kind = 'chat' FOR UPDATE — the lock comes first, before anything else; (2) dedup lookup on (couple_id, sender_id, client_msg_id) and, if found, return the original {id, cseq, deduped:true} and commit WITHOUT inserting; (3) INSERT, at which point the trigger allocates under the lock the transaction already holds. The duplicate path is protected by the ABSENCE OF AN INSERT, not by a branch inside the allocator — which is why the allocator can stay a single unconditional statement. Non-chat streams keep the single UPDATE inside their own BEFORE INSERT trigger and take no explicit FOR UPDATE, because they have no dedup branch.

**Invariant restored.** messaging.md's 'EXACTLY ONE CSEQ PER STREAM-MUTATING OPERATION (SERVER-ENFORCED, LOAD-BEARING)' and its supporting sentence 'Because the lock precedes the dedup check, a concurrent duplicate cannot burn a counter value. Holes in the issued range are impossible, not unlikely.' Also restores R1's own invariant_after, which is now the only statement of where allocation happens.

**Why it cannot regress.** Allocation has exactly one site and that site is reachable only by inserting a row, so 'allocate without appending' is unrepresentable and 'append without allocating' is impossible for every path including raw SQL and the service role. messaging.md's verification test 1 already asserts the counter is not bumped on the dedup branch and already fails against today's schema; it becomes the standing regression gate. Add a CI grep failing any function body that names a couple_cursor counter outside the two allocator triggers.

## F4

**Problem.** R1 asserts 'Restoring density costs one extra bigint column on a row that is already locked. Nothing is paid for it.' THAT CLAIM IS WITHDRAWN — it is false, and the cost is not small. Postgres row locks are per-tuple, not per-column, so two counters on one couple_cursor row make every chat write serialize against every reach, capsule, closer and call-signal write for that couple; messaging.md's separate chat_streams row had no such coupling. The concrete harm is cross-domain: clear_conversation_everyone holds the allocator lock while it deletes storage.objects joined against messages and then deletes every message row for the couple (chat_media_cleanup.sql:44-53), and R1 leaves call signalling on next_pos on the same tuple ('§I is unaffected'), so a partner tapping Clear chat blocks answer and ICE appends inside calling.md's 45 s ring window, which calling.md already records as routinely not fitting. transport.md accepted 'purge briefly blocks the partner's sends' for its own domain only; it never accepted blocking another domain. F9's repair, which puts call_signals squarely on the general counter, makes the coupling worse rather than better.

**Repair.** The two-dense-counters DECISION HOLDS; the one-row FORM does not. couple_cursor becomes couple_cursor(couple_id uuid, counter_kind text, value bigint not null default 0, floor_pos bigint not null default 0, primary key (couple_id, counter_kind)) with counter_kind in ('chat','stream'), fillfactor 70, no index other than the pk, two rows per couple created by the same AFTER INSERT ON couples trigger. ONE allocator TABLE, TWO lock domains. R1's CI assertion 'no second allocator table exists' survives verbatim; stream_last_seq is still a single-row read; a chat clear can no longer block a call. THE REAL PRICE, stated rather than denied: (a) one extra row per couple, roughly 40 bytes; (b) deadlock-freedom stops being structural and becomes an asserted property — with one row the rule 'no function body takes two per-couple counter locks' was vacuous, with two rows it is load-bearing, and it is backed by a declared total lock order (chat before stream) for any future function that legitimately needs both; (c) the couple-creation trigger inserts two rows, and the D-stage gate on 'the allocator row existing with both columns' becomes 'both allocator rows existing'. ADDITIONAL RULE, still required with two rows: NO TRANSACTION MAY HOLD AN ALLOCATOR LOCK ACROSS A BULK DELETE, A STORAGE-OBJECT DELETE, OR ANY NETWORK CALL. clear_conversation_everyone's residual hold is now intra-chat only and bounded by ONE hash partition, because hash on couple_id puts a couple's entire history in exactly one of the 32; messaging.md's pgbench test 9 already measures that hold, and if it exceeds budget the fallback is the two-transaction split (control row and floor commit first, the delete runs batched afterwards, safe because the control row carrying clear_through_cseq is the authoritative signal and a crash between them is a retryable no-op).

**Invariant restored.** transport.md's cost model for 'POSITION ORDER IS COMMIT ORDER, AND ALLOCATION IS UNBYPASSABLE' — head-of-line blocking stays inside the domain that chose to accept it — and calling.md's ring-window budget, which is no longer exposed to a chat operation it never agreed to depend on.

**Why it cannot regress.** The lock domains are separated by the primary key, not by discipline, so re-merging them is a migration that changes the allocator's PK — which contract §9 already forces to carry an expectation row and a registry edit. CI asserts pg_constraint shows couple_cursor's PK is (couple_id, counter_kind), and asserts no single function body references both counter_kind values. The blocking is also measurable rather than argued: messaging.md test 9 reports allocator lock hold time per counter_kind.

## F5

**Problem.** R1's rule 'each non-chat streamed table backfills ordered by (id) unless it has a server-assigned monotone column' is wrong for EVERY non-chat streamed table, not merely one. Verified on disk: every streamed entity table is `id uuid primary key default gen_random_uuid()` (schema.sql:44,:57,:65,:74,:85; reach_events.sql:9; capsules.sql:18,:30; intimacy_tables.sql:40,:61,:73,:97,:111), which is UUIDv4, so ordering by id is ordering at random; and a repo-wide search for sequence-backed columns returns exactly one, messages.seq (receipts_v2.sql:30-31). The escape clause therefore never fires and the rule reduces to 'shuffle all history'. The defect it was written to prevent — a client-set created_at — misorders only the rows a client actually forged; the rule itself misorders all of them, for every user, permanently, and R1 presented that as the strictly safer choice.

**Repair.** That presentation is WITHDRAWN and transport.md's ordering is restored. Non-chat streamed tables backfill by (created_at, id); messages backfills by (seq, id) because seq is server-assigned. The general rule, restated so it cannot be misread: A BACKFILL ORDERS BY THE BEST SERVER-ATTESTED TOTAL ORDER THE TABLE ACTUALLY HAS, AND A RANDOM PRIMARY KEY IS NEVER ONE — use a server-assigned monotone column if the table has one, otherwise (created_at, id), recording the table and its residual in the backfill register. The prohibition R1 was reaching for survives in the form that is true and that was always the real requirement: NO LIVE ALLOCATION MAY DERIVE FROM A COLUMN authenticated CAN WRITE. That is satisfied by the append trigger, because after the backfill no position is ever derived from created_at again. The backfill still runs in the same locked transaction that installs the append trigger. RESIDUAL, stated rather than hidden: a row whose created_at a client forged sorts wrongly once, in history only; it cannot create a gap, because contiguity is over the issued range and the backfill assigns positions densely in whatever order it chooses. No such row has been found. If one is later found, that table gets a documented manual correction, not a change of rule.

**Invariant restored.** transport.md's backfill ordering and, through it, the client's rendered history order for reaches, capsules, the Closer set and the rest. R1's actual goal — that no LIVE position derives from a client-writable column — is untouched, because the backfill never produced live positions.

**Why it cannot regress.** created_at appears in exactly one place in the position machinery, the one-time backfill statement, and the append trigger is installed in the same locked transaction, so there is no interval in which a client-writable column influences a live position. CI asserts that no trigger or function body outside the backfill migration references created_at in an ORDER BY or in an inequality on any table registered in stream_registry.

## F7

**Problem.** Shared contract §5 deletes presence's couple:<id>:msg and moves typing onto ch:<couple_id>:<recipient_uid>, whose gate is couple membership, claiming 'Presence's requirement is satisfied exactly, with one fewer channel per device.' It is inverted. presence.md splits :live and :msg precisely because realtime.messages RLS cannot see a broadcast's event name (presence.md:73, :309), so a single channel forces the privacy toggle to either leak typing or break chat delivery. Under §5, share_presence=false leaves typing flowing on ch: — §5 chose 'leak typing' without saying so, in an app whose premise is concealment. presence.md's invariant, its accepted limit 6, its open decision 3, its verification item (e) and its UI copy all depend on the opposite. Secondary and also unstated: transport §A puts the receipt-watermark hint on cl: while messaging puts it on the chat topic, and on cl: the privacy toggle would silently kill read receipts.

**Repair.** TYPING STAYS ON cl:<couple_id>, which §5's own table already gates on reciprocal share_presence for both read and write. ch:<couple_id>:<recipient_uid> BECOMES SERVER-WRITE-ONLY and carries exactly two payloads, both written by a server trigger and neither governed by the privacy predicate: the chat doorbell and the receipt watermark hint. §5's ch: row changes from 'client write: that user's PARTNER only (typing)' to 'client write: NONE', which also removes the last client-writable private topic outside cl: and rt: and makes ch: consistent with the cs:/dev: doctrine. The receipt hint's home is DECIDED here — ch:, not cl: — which is presence.md's own rule that chat, receipts, reach and calls are never affected by the toggle, satisfied exactly. THE GATE IS ON READ, NOT MERELY ON WRITE: a write-only gate on ch: would also stop the leak and would keep the cheaper topology, and it is rejected, because presence.md's invariant is 'a client that must not see presence never receives the bytes — there is no client-side filter that can be forgotten', and only a read-gated topic keeps that property under a mis-parsed helper, a second write path added later, or an RLS decision cached at join. THE COST, which §5 hid and which data.md §Cost must now carry: a per-recipient topic bills 2 per broadcast and a shared one bills 3 under the contract's own billing rule, so typing goes from 240 to 360 billable/user/day. §8's chat-only line becomes doorbells 80, receipt hints 80, typing 360, presence transitions 48, screen/misc 60, probes 30 — subtotal ~658/day, ~19,600/month — and the planning midpoint moves from 30,000 to roughly 33,600 billable/user/month, about +12% on a line that is 85-93% of the bill: roughly $4,200 to $4,600/month at 50,000 users. That is the price of the privacy predicate; it is worth paying and it is not zero, and §5 must stop implying it is. ALWAYS-ON CHANNELS PER DEVICE stays 3 (cs, cl, ch) — the saving from deleting :msg is unaffected, because ch: absorbs :msg's function.

**Invariant restored.** presence.md's 'PRIVACY IS A PREDICATE EVALUATED INSIDE THE REALTIME SERVER', its accepted limit 6, its open decision 3, its verification item (e) ('assert the peer receives zero presence frames and zero broadcast frames', restated over cl:, which is the same topic renamed) and its UI copy verbatim.

**Why it cannot regress.** ch: has no client-write policy at all, so typing cannot be put back on it by adding a payload — it requires ADDING A POLICY, and there are exactly four policies on realtime.messages, all data-owned, each a single call to realtime_topic_allowed(topic, verb) whose body is DDL and is therefore covered by supabase db diff and the migration checksum. Backed by the existing CI test that no source file outside the transport constructs a topic string or calls sendBroadcastMessage, and by presence.md's verification item (e) run as a standing assertion with share_presence=false.

## F9

**Problem.** Neither the eight resolutions nor the shared contract reconciles calling.md's position space with couple_stream, and R1 explicitly preserves both halves ('§I is unaffected — call signalling still uses stream=call on couple_stream'). calling.md allocates calls.signal_seq under the calls row lock (T3, calling.md:78) and its catch-up is `seq > cursor order by seq`; transport §I puts the same rows on couple_stream with a pos from next_pos. call_signals would carry two positions, two orderings and two catch-up paths, breaking contract §1's own rule that every streamed table has exactly one position column, and leaving unstated which one the client's cursor names. Secondary: end_call NULLs every call_signals.payload for the call in one UPDATE, and §1's mutation rule charges one position per payload alteration, so end_call would silently cost one position and one cs: doorbell per signal row.

**Repair.** DECIDED, one position space. call_signals is a streamed table carrying exactly one position, stream_pos, allocated from the 'stream' counter by the shared BEFORE INSERT allocator trigger, and registered in stream_registry with that position column and that counter. calls.signal_seq is WITHDRAWN as an allocator, and with it T3's `update calls set signal_seq = signal_seq + 1 ... returning`. The couple_cursor lock is a strictly stronger ordering than the per-call lock it replaces — couple-total rather than call-total — and calling.md's ring path already does not depend on the stream. WHAT calling.md LOSES AND HOW IT IS RETURNED: signal_seq was doing two jobs and only one was allocation. Its second job, the per-call high-water mark that makes a gap decidable (calling.md:84, :134, :142), is preserved as calls.last_signal_pos bigint — a DERIVED monotone maximum written by the same allocator trigger from NEW.stream_pos, allocating nothing. calling.md's three-state argument ('the row is uncommitted and will appear, or state_ord >= 90 and the call is over, and there is no third state') survives word for word with signal_seq replaced by last_signal_pos. Catch-up becomes `where call_id = $1 and to_user = auth.uid() and stream_pos > $2 order by stream_pos`; index (call_id, seq) becomes (call_id, stream_pos) per partition; call_keepalive returns last_signal_pos; glare resolves on stream_pos, now the only position either peer holds. MECHANICS: call_signals gains couple_id uuid not null, because the allocator keys on it; T3 (party membership, self-attribution, created_at) must set NEW.couple_id before the allocator reads it, and since Postgres fires same-event BEFORE triggers in alphabetical name order the two triggers are named to force that order and a CI test asserts the order rather than leaving it to luck. end_call: it already writes exactly one terminal 'end' signal row, and THAT ROW IS the single position the mutation rule requires for the whole operation. So end_call (1) sets set_config('miles.bulk_purge','1',true), (2) performs the wide payload UPDATE, allocating nothing and taking no allocator lock, (3) then inserts the terminal 'end' row, which allocates the one position. That order also satisfies F4's rule that no allocator lock is held across a wide UPDATE. No schema change beyond couple_id, no extra doorbell, and the client learns by the same two independent paths CLIENT-F2 relies on for redact: a null payload on a fetched row means the call ended and reconcile from calls, and the terminal row arrives at a forward position.

**Invariant restored.** Shared contract §1's 'every streamed table has exactly one position column, named by its stream_registry row'; §1's mutation rule in the form it already grants the bulk purge ('bulk purge costs exactly one position'); and calling.md's gap-decidability, unchanged in substance and renamed in one column.

**Why it cannot regress.** After the change there is no second counter to drift: signal_seq is dropped from calls, so writing it fails at the SQL level. last_signal_pos cannot become an allocator because it is assigned from NEW.stream_pos, which is already allocated by the time it is read. The reason this survived every existing check is that a per-call counter is not a per-couple allocator and so passed R1's CI assertion untouched, so contract §9's registry set must be extended to 'a counter or position space of ANY scope' — without that extension this repair is correct but its anti-recurrence guarantee is not.

## F11

**Problem.** The shared contract leaves the push-to-client background contradiction unresolved and thereby leaves data.md's only delivery-health SLI unimplementable. client.md §E/§M forbid the FCM background isolate from draining and from applying; push.md §7 requires a background catch-up that advances push_devices.cursor_seq and a push_receipts ack within ~3 s, and its headline ~12 pushes/user/day figure is an output of cursor_seq suppression. Contract §2(c) blesses cursor_seq as an optimisation input but never says which isolate writes it or writes a receipt. If client.md holds as written, push_receipts is never written from a background wake, so data.md's accepted_not_delivered — the metric that replaced state='dead' in its FATAL 3 closure — is permanently saturated and useless.

**Repair.** DECIDED, and it splits, because the two writes are not the same kind of thing. CLIENT.MD LOSES EXACTLY ONE NAMED EXCEPTION: the FCM background isolate MAY perform one network write, a push_receipts ack carrying (fcm_message_id, ack_delay_ms, priority, original_priority, displayed) through a single RPC, idempotent on the primary key (device_id, fcm_message_id), 3 s timeout, buffered to SharedPreferences on failure, never blocking the notification. It touches neither the local mirror, nor the outbox, nor any cursor the sync engine owns, so client.md's convergence argument ('rows-union and token-max in any interleaving') is untouched — and client.md's own text already concedes the main-isolate rule is 'for SQLite contention, not for correctness' (client.md:193, :310, :333). This goes into client.md §E and §M as a named allowlist entry with that reason, not as a softening of the rule. PUSH.MD LOSES THE OTHER HALF: the background isolate may NOT advance push_devices.cursor_seq. cursor_seq is a watermark; the background isolate does not apply, so it persists nothing; and the only integer available to an isolate that did not sync is the FCM payload's `w`, which contract §2's rule ('no integer that arrived over a socket may ever reach a read cursor, a watermark, or a highest-seen variable') forbids from reaching it. THE RULE, added to contract §2(c): CURSOR_SEQ IS ADVANCED ONLY BY THE ISOLATE THAT PERSISTED THE PAGE, WHICH IS THE MAIN ISOLATE. push.md §7's trigger list changes from 'catch-up runs on every foreground, socket open, push wake and onDeletedMessages' to '... on every foreground, socket open, sync_due marker consumed by the main isolate, and onDeletedMessages' — which is what push.md's own recovery claim already says: force-stop, TTL expiry, collapse eviction, the 100-cap and Doze are 'all recoverable ON NEXT OPEN'. CONSEQUENCE FOR THE SLI, which is the repair data.md actually needs: accepted_not_delivered becomes implementable because push_receipts is written from the background wake, but it MUST BE SEGMENTED or it inherits the same permanently-red failure — push.md:144 records that network is disabled in the RARE and RESTRICTED standby buckets while plugin.show() still works, so a correctly-behaving device in those buckets displays the notification and cannot ack. Devices classified net_restricted are excluded from accepted_not_delivered and reported as their own counter with its own threshold. CONSEQUENCE FOR PUSH VOLUME, stated rather than assumed away: suppression by cursor_seq now fires only for devices that actually synced, so a backgrounded device that woke, displayed and did not sync no longer suppresses its next push. push.md's ~12 pushes/user/day figure must be re-derived; its binding constraint is unchanged, because the collapsible bucket (12 tokens, refill 1 per 180 s) caps message doorbells to a backgrounded acking device at roughly one per three minutes regardless of cursor_seq — so the figure is bounded by a mechanism that does not depend on this decision, but the number itself is provisional until measured.

**Invariant restored.** client.md's 'the background isolate may not drain and may not apply' — preserved verbatim, because neither permitted behaviour drains or applies; contract §2's socket rule, which the original push formulation would have violated by routing the FCM payload's watermark into cursor_seq; and data.md's FATAL 3 closure, which now has a real evidence source and a threshold that does not fire on devices behaving exactly as Android specifies.

**Why it cannot regress.** The allowlist is one named RPC, so the background entry point has a single exported network symbol and CI can assert the background isolate's call graph reaches no other network function — the same shape as client.md's existing _c.from lint and its golden-fixture suite with the network stack stubbed to throw. cursor_seq cannot be advanced from a payload because the advancing RPC is called only from the page-persist path and the FCM payload's `w` is never bound to a variable that reaches it, which the same lint asserts.

# Corrected canary

PERMANENT PRODUCTION CANARY — replaces R1 invariant_after clause (d) in full. Runs as an ops_job dispatched by ops_tick (60 s), one indexed aggregate per predicate per run, per couple. It reads the ISSUED RANGE and the DELETION FLOOR from the allocator table only; it never infers either from the rows, and it never asserts row contiguity.

WHAT IT READS TO KNOW THE ISSUED RANGE. couple_cursor(couple_id, counter_kind, value, floor_pos) — one row per family per couple. head = value; floor = floor_pos. Contiguity OF THE ISSUED RANGE is not scanned: a counter whose only mutation is +1 in a single BEFORE INSERT allocator trigger cannot skip a value, so issued-range contiguity is a property of the allocator (F3), not of a scan. floor_pos is written greatest()-guarded in the SAME transaction as the deletion it records — by clear_conversation_everyone for 'chat', by couple_stream_compact for 'stream'.

FAMILY 1 — CHAT (messages.cseq, counter_kind='chat').
K1 ALLOCATOR IS AHEAD OF THE ROWS: value >= coalesce(max(messages.cseq), 0) for the couple. Reads one allocator row plus an index-only max on (couple_id, cseq). Catches a row that acquired a cseq without the allocator, and a counter that was reset.
K2 NO VALUE WAS ISSUED TWICE: assert as CATALOGUE facts, not scans, that unique(couple_id, cseq) and NOT NULL on cseq exist and are validated in pg_constraint. Catches the drop of the constraint, which is how a duplicate becomes possible at all.
K3 DENSITY ABOVE THE LIVE FLOOR: count(messages where couple_id = C and cseq > floor_pos) = value - floor_pos. This is the only row-counting predicate; it is issued-range contiguity restricted to the range in which rows are supposed to still exist. It is NOT row contiguity — below the floor rows are expected to be gone. Catches a hard DELETE with no control row and no floor write, which has no other observable.
K4 NOTHING SURVIVES BELOW THE FLOOR EXCEPT THE BLANKING SIGNAL, AND THE TWO RECORDS OF THE FLOOR AGREE: every surviving row with cseq <= floor_pos has kind='clear'; and floor_pos = coalesce(max(clear_through_cseq) over surviving kind='clear' rows, 0). Served by a partial index messages(couple_id, clear_through_cseq desc) where kind='clear'. Catches a partial delete that left content behind the blanking signal (a privacy failure, not only a bookkeeping one) and a floor written without a control row or the reverse.
K5 NO SILENT MUTATION: zero rows with deleted_for_everyone = true having no kind='redact' row whose target_cseq names them. This is the direct observable for 'the stream was mutated without allocating', and it is what makes K1-K4 an alarm about the invariant rather than an alarm about deletion.
K6 STRUCTURAL: both allocator rows exist for every couple; cseq IS NOT NULL holds as a table constraint.
WHY IT IS NOT RED ON THE SECOND CLEAR: after clear#1 at cseq K1 and clear#2 at cseq K2, floor_pos = K2-1 and clear#1's row survives at K1 <= floor with kind='clear'. K3 counts [K2, value] = value - (K2-1). K4 passes on the surviving clear row. Nothing opens. Committed negative tests: (i) two consecutive clears open nothing; (ii) one row hard-deleted with no control row and no floor write opens K3 at page severity within one tick.

FAMILY 2 — GENERAL STREAM (couple_stream.pos, counter_kind='stream'). Same shape, measured over (floor_pos, value].
S1 value >= coalesce(max(couple_stream.pos), 0) for the couple.
S2 the PK (couple_id, pos) exists and is validated — catalogue read, no scan.
S3 count(couple_stream where pos > floor_pos) = value - floor_pos.
S4 zero couple_stream rows at pos <= floor_pos. couple_stream carries no rows a compaction must preserve, so the prefix delete is clean and this is exact; floor_pos is what couple_stream_compact actually deleted through, not a recomputed min(applied_pos), which also turns sync_head's floor_pos into a single-row read.
S5 APPEND BYPASS, SAMPLED: for each table in stream_registry, zero entity rows with a NULL position column, and zero entity rows whose position is above floor_pos with no couple_stream row at that pos — evaluated over the 1,000 newest rows per registered table per run, the same sampling bound R3 uses for bucket_path_shape, because a full anti-join per tick is not affordable. This is the analogue of K5: it catches 'the row commits, is never advertised, and both clients report caught-up'.

Neither family's canary reads created_at, a client-supplied integer, or a device clock. Both open a named alert per predicate with a severity and an age, so an alarm names which predicate and which couple rather than reporting a hole.
