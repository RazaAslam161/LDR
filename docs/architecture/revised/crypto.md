# crypto (revised)

## What changed vs v1
Six fatals, each closed by a named mechanism, plus what is accepted.

**F0 — Stage-1 CRK mint race; AD cannot distinguish two CRKs claiming epoch 1. CLOSED, two independent mechanisms.**
(a) The epoch's identity is now `epoch_id uuid`, not the ordinal, and it is in the AEAD associated data and stamped on every ciphertext row with a FOREIGN KEY to `couple_epochs`. A reader selects the key by stamp instead of trial-decrypting, so two keys can never be silently interchangeable.
(b) The race is removed at its only real occurrence rather than merely detected. Epoch 1 for a legacy couple is **deterministic**: `CRK_1 = HKDF(legacy_derived_shared_key, "miles-crk-bootstrap-v1")`. Both devices independently compute the *identical* CRK, so concurrent mints converge and the primary-key collision on `couple_key_wraps` becomes genuinely benign — `ON CONFLICT DO NOTHING` is correct because the row that wins holds the same 32 bytes. No election is needed for the case the attack actually hits.
(c) For every epoch a legacy key cannot bootstrap (new couples, all rotations), a server-side election: `claim_epoch()` is SECURITY DEFINER, does one `INSERT ... ON CONFLICT (couple_id, epoch_ordinal) DO NOTHING` and RETURNS the committed row. The loser reads back an `epoch_id` different from its proposal, discards its key, and is forbidden to write — enforced by construction, because the FK means it can only stamp a committed epoch and it holds no key for that epoch.
Cannot regress: `unique(couple_id, epoch_ordinal)` and the FK are schema constraints, not client behaviour. A future commit that reintroduces a second epoch 1 fails to INSERT.

**F1 — unspecified DELETE on `key_wraps` is a one-request remote wipe. CLOSED.**
The table is split in two and both are made append-only at the Postgres *privilege* level, not by RLS: `revoke all on <table> from authenticated, anon; grant select, insert on <table> to authenticated`. This repo already proves the technique and its footgun — `hardening_2026_08.sql:43-45` documents that a column-level revoke is a no-op while a table-level grant survives, so the table grant goes first and only SELECT/INSERT come back. `couple_key_wraps` (EK_n) and `user_key_wraps` (PK_u, IK) are separate tables; `user_key_wraps` INSERT is scoped `user_id = auth.uid() AND recipient owned by auth.uid()`, so a partner has no write path into your personal slots at all. Revocation is an append to `key_revocations`, and the RLS SELECT predicate on `couple_key_wraps` filters out tombstoned recipients — so revocation stops future delivery without deleting anything. The partner-assisted flow gets one narrow SECURITY DEFINER RPC that can insert exactly one row, into exactly the slot named by an open `key_requests` row belonging to the other user's own pending device.
Cannot regress: a future policy mistake cannot restore DELETE, because DELETE was never granted to the role. Asserted mechanically in CI via `has_table_privilege('authenticated', 'public.couple_key_wraps', 'DELETE')`.

**F2 — one-way cliff gated on a client-decremented counter. CLOSED.**
`legacy_rows_remaining` is deleted from the design. "Legacy remaining" is a server-side predicate — `count(*) where epoch_id is null`, per couple, computed in a SECURITY DEFINER RPC. Re-wrap is a conditional `UPDATE ... WHERE id = ? AND epoch_id IS NULL`, so a concurrent second writer is a no-op rather than a competing write. Nothing a client says can advance the migration state.
Cannot regress: there is no counter column to double-decrement. The predicate is derived from the data it describes.

**F3 — stage ordering reconstructs the total-loss bug. CLOSED, structurally.**
The stage order is inverted: offline recovery credentials (Recovery Key, then platform vault) ship at Stages 2 and 3, *before* content ever moves to epoch keys (Stage 5), before the lazy re-wrap (Stage 6), and long before the legacy read path is disabled (Stage 7). Stage 7 is the only removal in the whole plan, and its gate is a server predicate evaluated **per user**: disable the legacy fallback for user U only when U's couple has zero rows with `epoch_id is null` AND U has at least one *non-device* wrap of the current epoch. A user with no offline credential keeps the legacy path indefinitely. Additionally, because epoch 1 is deterministically derived from the legacy key, both devices hold CRK_1 from Stage 1 without any wrap exchange — so the window where CRK's only copies are two device keys never opens.
Cannot regress: the removal is gated on a server-evaluated predicate over `couple_key_wraps` and the content tables, not on a build flag or a date.

**F4 — `key_requests.expires_at = now()+15min` versus a force-stopped Vivo. CLOSED.**
`expires_at` defaults to server `now() + 30 days`. Expiry is a *display* state; `purge_expired()` is explicitly forbidden from touching `key_requests`. A pending request is a durable inbox item on the partner's device that survives app kill, OEM wakeup suppression, reinstall of the partner's app, and a three-day gap. FCM and the private channel remain hints with no payload; the row is the truth and is read on app open.
Cannot regress: the security bound moved off the wall clock entirely (see F5), so no future tightening of the timeout has anything to buy.

**F5 — "CPace over a code both screens show" is not a PAKE, and the 3-attempt limit was a Postgres row. CLOSED by picking one and naming it.**
It is a **short-authenticated-string exchange (Vaudenay SAS), and we say so** — no PAKE, no CPace, no Argon2. Commit-then-reveal X25519, SAS = 6 digits derived from the full transcript. Two changes that make it real: (1) the digits are **typed, not compared** — A's new device displays them, the partner's device requires them to be typed and does the comparison in software, so there is no "yes they match" button to tap through; (2) the attempt limit lives in **local storage on the approving device, keyed to the requesting device's `x25519_pub`**, so deleting and re-inserting the request row does not reset it, and it sits on the only party whose state an attacker with A's session does not control. The `attempts int` column is deleted; there is no server-side guess counter anywhere, consistent with research/e2ee.md:210.
Cannot regress: the counter has no server representation to be restored from a backup. The residual — a voice-channel impersonation attack — is stated as an accepted limit rather than claimed closed.

**Serious flaws closed:** 7 (verification gate moved to the approval sheet where key material actually crosses; the inert send-side gate deleted; cross-signing binds the requesting device's x25519_pub at approval). 8 (PK_u loss rate stated alongside CRK; Recovery Key made a hard precondition for PK_u-backed features only; Stage 2 before Stage 4). 9 (client-side thumbnails as first-class objects with their own DEK and ledger row; egress re-priced on views, not uploads; the cost argument for the public bucket dropped, the security argument kept). 10 (Stage 0 split into five independently revertible pieces, per-topic remote flags, live storage policies dumped and committed verbatim before any DDL is written, `setAuth()` on token refresh in the same change). 11 (cost re-cited to supabase.md:271/:279/:282; crypto restated as a percentage of the real total). 12 (fantasy tag key derived from the *current epoch key*, not the immortal CRK, and rebuilt on rotation; "remove device" forces rotation in the stolen case). 13 (named as four separate migrations, each with its own server-side completion predicate; fantasy is explicitly *not* migrated; Stage 8 reordered to upload-then-single-statement with the ledger row in the same transaction). 14 (`invalidated` device state for `KeyPermanentlyInvalidatedException`, which does not consume a device slot; hardware matrix extended to seven events).
**Minor flaws closed:** 15 (two wrap tables, `'ik'` kind added, `epoch_id uuid`, no sentinels). 16 (`devices` RLS specified, `last_seen_at` dropped, `label` encrypted under the epoch key, CI gate widened to every client-readable table). 17 (property split by key kind, with the PK_u case asserted as a *negative*; `has_column_privilege` replaces the unworkable `information_schema` check; ciphertext enforced at a grep-enforced choke point instead of sampled). 18 (correlated-loss sensitivity given, mutual-pending deadlock added to the state machine, breakup case stated in setup copy).

**Accepted, not closed:** flaw 6 (backups resurrect wrap rows). The "destroying the wrap IS the delete, independent of backups" claim was false and is withdrawn. See accepted_limits.

## Target architecture
## What is broken today, in one paragraph

`E:/LDR/mobile/lib/core/crypto_core.dart:98-107` derives one couple key live: `X25519.sharedSecretKey(myKeyPair, partnerPub)` → `HKDF-SHA256(info='miles-closer-v1')` → 32 bytes in the static `CryptoCore._sharedKey`. The private half is a single X25519 seed under the fixed, non-user-scoped key `'miles_x25519_priv_v1'` in `flutter_secure_storage`. `android:allowBackup="false"` means reinstall or a new phone destroys it; `publishMyPublicKey()` then upserts a new public key over the old row in `public.partner_keys`, and because content is `f(A_priv, B_priv)`, the innocent partner's next `ensureSharedKey()` derives a different key and **every Closer row ever written becomes permanently undecryptable for both people**. There is no re-encryption path. It fails at n=2, not at scale. Everything else — `clearCache()` with zero callers, one keystore entry per device rather than per account, three incompatible envelope layouts, `hmacTag()` documented as HMAC-SHA256 but actually keyless 32-bit FNV-1a over a public 12-item taxonomy, fantasy "privacy" as `.eq('author', myId)` in Dart, cleartext body-map `x, y` — descends from that one decision or from the absence of any key that is not it.

## The mechanism: content keys are WRAPPED, never DERIVED

Content is encrypted under a random key that exists on the server only as N independently sealed copies. Losing a device removes one copy. The number of things that must survive for a couple's data to survive is one, and it is never a *specific* one.

## Key hierarchy

- **DK — Device Key.** Per (device, account). X25519 for wrap/unwrap plus Ed25519 for signing. The X25519 seed is generated with `Random.secure`, sealed under an Android Keystore AES-GCM key (StrongBox where available), sealed blob on disk. Never leaves the device, never wrapped to anything, never backed up. `setUserAuthenticationRequired` and `setInvalidatedByBiometricEnrollment` are **not** set — but Keystore keys can still be invalidated by a lock-screen credential change, so the state machine has an `invalidated` state (below). Replaces `'miles_x25519_priv_v1'`, which is keyed per device rather than per account, so two accounts on one phone currently share one identity.
- **IK — Identity Key.** Ed25519, per user. Signs that user's device list. The only input to the safety number. Wrapped into recovery envelopes, so a recovered user keeps their identity and the safety number does not change. A user who re-bootstraps with no recovery path gets a new IK — that is the loud event.
- **CRK — Couple Root Key.** 32 bytes, one per couple. `EK_1` for legacy couples is `HKDF(legacy_derived_shared_key, "miles-crk-bootstrap-v1")` — deterministic, so both devices converge without an exchange. For couples formed after Stage 1 it is `Random.secure(32)` minted under the election RPC. Never transmitted in the clear.
- **EK_n — Epoch Key.** `EK_1` as above; `EK_{n+1} = HKDF(EK_n || fresh_entropy, "epoch-" || epoch_id_{n+1})`. The new root needs the previous root *and* new entropy, so a device holding only `EK_{n+1}` cannot walk backwards. Rotation happens only on explicit user action ("reset shared history", breakup, stolen phone). Old epochs are never re-encrypted; surviving devices keep old epoch keys in their keyring.
- **PK_u — Personal Key.** 32 bytes per user. Wrapped **only** to that user's own DKs and own recovery credentials — never to the partner, and there is no table into which the partner can write such a wrap. Encrypts fantasy-jar text and personal-vault content. This is what makes "private from your partner" a key-possession fact instead of a Dart filter.
- **DEK — Data Encryption Key.** 32 bytes per item and per storage object (thumbnails get their own). Wrapped under `EK_n` or `PK_u`; the wrap lives in the row next to the ciphertext, or in the storage ledger row for objects.

**Epoch identity.** `epoch_id uuid` is minted with the key and is what appears in AEAD associated data and on every ciphertext row. The ordinal is only for ordering and uniqueness. This is the difference between "a wrap cannot move between slots" (which the ordinal gave) and "a reader knows which key opens which row" (which it did not).

## Data model

All tables hold ciphertext or public material only. No combination of rows the server can read produces a key.

- `devices(device_id uuid pk, user_id, x25519_pub bytea, ed25519_pub bytea, ik_sig bytea, state, label_cipher bytea, created_at)` — `state ∈ {pending, active, invalidated, retired, revoked}`. **No `last_seen_at`** (it was a global presence oracle). `label` is encrypted under the current epoch key so the partner can read it in the approval sheet and the server cannot. RLS SELECT: `user_id = auth.uid()` OR the requester's couple partner. INSERT/UPDATE: `user_id = auth.uid()`, with state transitions constrained by a SECURITY INVOKER trigger in the shape `hardening_2026_08.sql:56-70` already uses.
- `couple_epochs(couple_id, epoch_ordinal int, epoch_id uuid unique, mode, created_at, created_by_device, unique(couple_id, epoch_ordinal))` — INSERT only through `claim_epoch()`. No UPDATE or DELETE grant to any client role.
- `couple_key_wraps(couple_id, epoch_id, recipient_kind, recipient_id, wrapped_blob bytea, wrapped_by_device, created_at, pk(epoch_id, recipient_id))` — wraps of `EK_n`. **Append-only at the privilege level**: `revoke all ... from authenticated, anon; grant select, insert ...`. SELECT: `recipient_id` is one of my non-tombstoned devices or credentials. INSERT: `recipient_id` belongs to `auth.uid()` — plus the one narrow RPC below.
- `user_key_wraps(user_id, key_kind ∈ {'pk','ik'}, recipient_kind, recipient_id, wrapped_blob, wrapped_by_device, created_at, pk(user_id, key_kind, recipient_id))` — same append-only posture. SELECT and INSERT both require `user_id = auth.uid()` AND recipient owned by `auth.uid()`. **The partner has no write path here at all**, which is what makes PK_u privacy structural rather than policy-shaped.
- `key_revocations(id, owner_user, subject_kind ∈ {'device','recovery'}, subject_id, revoked_at server-default now(), revoked_by_device, sig)` — append-only; INSERT only where the subject belongs to `auth.uid()`. Readers ask "is this recipient tombstoned", never "which tombstone came first", so transaction-start `now()` is never load-bearing for ordering.
- `recovery_credentials(id, user_id, kind ∈ {'code','platform_vault','partner'}, pub_x25519, label, enrolled_at)` — append-only; revoked via tombstone.
- `key_requests(id, couple_id, requester_user, requester_device, commitment bytea, ephemeral_pub bytea, state ∈ {open, approved, refused, cancelled}, created_at, expires_at default now()+30 days, resolved_at)` — **no `attempts` column**. State changes only through RPCs.
- `storage_ledger(object_path pk, couple_id, item_id, role ∈ {'full','thumb'}, epoch_id, wrapped_dek bytea, padded_size int, created_at, purge_at)` — the object's key and lifetime. Partitioned monthly so the orphan sweeper reads one partition.

`wrapped_blob` is a sealed box: ephemeral X25519 → HKDF → XChaCha20-Poly1305 over the 32-byte key, with **AD = `(couple_id_or_user_id, epoch_id, key_kind, recipient_id)`**. A wrap copied or replayed into another slot fails to open. The server can withhold a wrap — a detectable denial of service — but can never redirect one.

**Key material is fetched as a whole set, never with a cursor.** A couple has at most a few dozen wrap rows. Clients read the full set on app open and on a broadcast hint. There is no `WHERE seq > cursor` anywhere in this domain, and no `postgres_changes` subscription on any key table — which is why the global-sequence out-of-order-visibility problem and the 30-changes/s project-wide ceiling do not touch it.

## Server-enforced write paths (SECURITY DEFINER)

- `register_device(pubkeys, sig)` — enforces the cap of 3 by counting `active` + `pending` devices for that user. `invalidated` and `retired` devices do **not** consume a slot. The 4th registration is refused with "remove a device first", never silently dropped.
- `claim_epoch(couple_id, epoch_ordinal, proposed_epoch_id, wraps[])` — one `INSERT ... ON CONFLICT DO NOTHING`, then RETURNS the committed row. For `mode='rotate'` it commits **only if** the submitted wraps cover exactly the set of currently active, non-tombstoned recipients of *both* users, counted in the same transaction. The server cannot verify a blob decrypts, but it can verify coverage, and a garbage blob is indistinguishable from withholding, which is already an acknowledged residual. `mode='separate'` (breakup) requires coverage of the caller's own recipients only and writes a loud, couple-visible record.
- `deliver_partner_wrap(request_id, wrapped_blob)` — the only path by which one user writes into another's slot. Validates: the request is `open`, the caller is the couple partner of `requester_user`, the target `recipient_id` equals `key_requests.requester_device`, and that device is still `pending` and un-tombstoned. Inserts exactly one row per epoch.
- `closer_migration_status(couple_id)` — returns `legacy_rows_remaining` as `count(*) where epoch_id is null` and `offline_credential_count` per user. This is the gate for Stage 7. There is no client counter.
- `purge_expired()` — hourly on `pg_cron`, plus a 5-minute cycle for user-initiated deletes. Drives off server `now()` only, inside SECURITY DEFINER, and is **forbidden from touching `key_requests`**.

Every expiry timestamp is server-set. The client-writable path is removed the way this repo already removes it: drop the table-level UPDATE grant, re-grant UPDATE only on the columns clients may write. `hardening_2026_08.sql:33` records the reason — a column-level revoke is a no-op while the table grant stands.

## Device state machine

`absent → pending → active`, with `active → invalidated` (Keystore key destroyed by a lock-screen or biometric change, `KeyPermanentlyInvalidatedException`), `active → retired` (user removed it), `active → revoked` (stolen). `invalidated` is distinct from `absent`: it re-enters recovery **without consuming a device slot**, and the copy names the cause ("your screen lock changed") rather than showing "items couldn't be opened" — the exact misleading state this design exists to kill.

A new install generates DK, inserts a `pending` device row, and tries in order: (1) platform vault entry, (2) Recovery Key, (3) partner-assisted, (4) stop and say so.

| Path | IK | Safety number | Couple history | Personal content (PK_u) |
|---|---|---|---|---|
| Platform vault | restored | unchanged | readable | readable |
| Recovery Key | restored | unchanged | readable | readable |
| Partner-assisted | **new** | **changes** | readable | **lost** |
| Nothing | new | changes | empty | empty |

Partner-assisted loses PK_u because the partner was never given a wrap of it and has no table to write one into. That is the design working — and it is precisely why Recovery Key enrolment is a hard precondition for the PK_u-backed features (fantasy jar, personal vault) and why it ships two stages before partner-assisted.

**Mutual-pending deadlock is an explicit state.** If both devices are `pending`, neither can approve the other. The app says so and the only exit is a Recovery Key. **Breakup** is stated in setup copy before the fact: partner-assisted recovery requires a cooperative partner, and it is unavailable exactly when a person most wants their shared memories back.

## Partner-assisted re-wrap — a SAS exchange, named as such

This is a Vaudenay short-authenticated-string exchange, **not a PAKE**. No CPace, no Argon2, no low-entropy secret used as key material.

1. A's new device inserts a `key_requests` row carrying its `x25519_pub` and a commitment `H(ephemeral_pub || nonce)`. `expires_at` is server-set to `now() + 30 days`.
2. B is hinted by a payload-free FCM data message and by the private couple channel. **Both are hints.** The row is the truth and is read on app open. The flow is designed to complete when the socket is dead, the app is backgrounded, and the OEM has force-stopped it for a week.
3. B's device fetches the request, contributes its ephemeral, A reveals. Both compute the SAS from the full transcript (both pubkeys, both ephemerals, request id, couple id).
4. **A's device displays 6 digits. B's device requires them to be typed** and compares in software. There is no "yes, they match" button. The couple speaks over their own call. The code is never sent to the server, so a malicious server or an injected rogue device row produces a mismatch, not a silent success.
5. The attempt limit — **3** — lives in local storage on **B's device, keyed to the requesting device's `x25519_pub`**. Deleting and re-inserting the request row does not reset it. There is no server-side guess counter anywhere in this design.
6. The approval sheet shows the safety number and the device label. On approval, B cross-signs the requesting device's `x25519_pub`, wraps `EK_n` for every epoch it holds via `deliver_partner_wrap()`, and a permanent transcript event is written on both sides. B's own rows are untouched throughout.

## Key-change events — the gate is at approval, not at send

Closer has no send path keyed to a peer's identity key; items are encrypted under `EK_n`. A send-side gate would fire *after* the escrow had already crossed, and would train users to dismiss the one warning that matters. So: **the verification moment is the approval sheet in step 6**, which is the only moment key material crosses and the only moment a human is present. The permanent transcript event is kept — it is honest and cheap. Safety number is the WhatsApp/Signal construction verbatim (sort the peer's device identity keys, iterate SHA-512 over `sorted_keys || user_id` 5,200 times, 30 bytes, six 5-byte big-endian chunks mod 100000, per-conversation 60-digit as sorted concatenation), under 1 ms on the IN2015 per research/e2ee.md:192. Two distinct events, neither of which the app has today: "Sam added a device" (IK unchanged, signature chain valid — routine, non-blocking) and "Sam's safety number changed" (new IK — permanent, in-thread).

## Storage

Object bytes are XChaCha20-Poly1305 under a per-object DEK, always. The path is 32 random bytes — no couple id, no user id, no date, no extension (today it is `<coupleId>/body/<uid>_<ms>.jpg`, which is why `hardening_2026_08.sql:24-25` had to record that couple UUIDs are not secret). The couple → object mapping and the wrapped DEK live in `storage_ledger` under RLS. A public bucket, a leaked signed URL, a CDN entry outliving its token, and a stolen service-role key are then all equivalent to holding random bytes. Sizes are padded to PADMÉ buckets (~12% overhead, priced). Media leaves `bytea` entirely; `bytea` holds text and metadata only, ≤4 KB.

**Thumbnails are first-class objects.** Encrypted objects cannot be transformed server-side, so there is no 200px variant to serve and a grid view would otherwise pull full-resolution bytes per tile. The client generates a 256px-long-edge thumbnail at write time; it gets its own DEK, its own object, its own ledger row. This doubles object count and is stated in the cost model. Poly1305 also forbids range requests and progressive decode — the whole object must land before any byte is trusted — which is a memory constraint on the IN2015 as much as a bill.

**A URL is never a capability.** Broadcast and push payloads carry an opaque object id; the receiver resolves the row under RLS and downloads. Every channel is created `private: true` with an RLS policy on `realtime.messages` scoped to couple membership, and `realtime.setAuth()` is wired on every token refresh — private channels disconnect on JWT expiry, which is the app's existing "joined but dead channel" bug class.

## Deletion and retention

Deleting an item deletes its row, which destroys the wrapped DEK. For objects, the delete flow is: set `storage_ledger.purge_at = now()`, have the client **overwrite the object with random bytes of the same padded length** (best effort — Storage overwrites are not carried in Postgres backups), then let the 5-minute purge cycle delete object and ledger row in one transaction. A monthly-partitioned orphan sweeper reaps objects with no ledger row — which is what finally collects `<coupleId>/reactions/*`, accumulating forever today.

The honest claim is: **unreadable to every live reader immediately; irrecoverable once the object is purged and the Postgres backup window has rolled past.** The original "independent of backups" claim was false and is withdrawn (see accepted_limits).

`clear_conversation_everyone()` hard-deletes message rows. Whatever the analogous Closer bulk-delete does, it deletes item rows and enqueues ledger purges — and it must **never** touch `couple_key_wraps` or `user_key_wraps`, which is guaranteed by the absence of a DELETE grant rather than by the function's good behaviour.

Every retention timer is a server-set `expires_at`; the 14-day mutual-delete window currently computed on the device clock becomes a server predicate.

## What is encrypted, and what leaks

Encrypted: vault note text, photo bytes and filename; fantasy text (under PK_u, new entries only); **body-map `x, y`** moved inside the ciphertext with the `real` columns dropped after backfill; memory title/note/photo and exact date; afterglow gratitude and photo; **capsule item text and media**, wholly plaintext today; device labels. Fantasy tags become `HMAC-SHA256(HKDF(EK_current, "fantasy-tags-v3"), normalized_tag)` truncated to 16 bytes — **derived from the current epoch key, not from the immortal CRK**, and rebuilt as part of any rotation, so "remove this stolen device" actually removes the thief's ability to enumerate future tags. Matching works within an epoch, which is correct: "reset shared history" should reset matching too.

Published leak list: row existence and count, `couple_id`, `author`, `created_at`, item `kind`, padded ciphertext length, storage object size and access time, thumbnail existence (i.e. "this item is an image"), realtime topic names and join timing, push timing, IP, per-user device count and recovery-credential count (to the server, not to strangers). Two deliberate leaks with a stated reason: a coarse cleartext `happened_month` for timeline ordering and pagination, and the `retention` class in cleartext, because the server enforces purge and cannot act on a value it cannot read. `E:/LDR/docs/architecture/metadata-exposure.md` enumerates every field the server can read for **every client-readable table**, including the six key tables, and CI fails if any such table gains a non-encrypted column with no entry.

## What this deliberately does not copy

No prekey pools, no X3DH/PQXDH, no Sesame — those establish an asynchronous session with a stranger, and this product has no strangers; skipping them also skips the Prekey Pogo drain-and-oracle surface (research/e2ee.md:19, :166) and a Kyber pool priced at 1.6 GB per 10k users (:223). No Double Ratchet for Closer: Closer is a shared mutable store, and forward secrecy per message is a deletion mechanism dressed as a security property for content whose purpose is to be re-read in three years. No key transparency (:216, :235) — two people who share a bed can compare a safety number, and cross-signing at approval is strictly stronger locally than KT is for users who never compare. No server-side escrow, no PIN, no Postgres guess counter (:210) — every escrow design in the corpus reduces to a tamper-evident device that destroys a secret after N guesses and cannot be rolled back, and we have none of those. No pgsodium / Transparent Column Encryption (:273), which is not end-to-end and which Supabase advises against on their own platform.

The launcher disguise is preserved throughout: no notification carries content, key-request hints are data-only FCM with no body, and `allowBackup` stays `false` — the platform-vault tier is Block Store, not an app-wide backup.

## Invariants
- Content keys are wrapped, never derived. No Closer plaintext is encrypted under a key that is a function of two live device private keys. Enforced by construction after Stage 7: the schema has no column holding such a key, and a CI check asserts `partner_keys` has zero readers in `lib/`. Consequence: the number of devices that must survive for the couple's data to survive is one, and never a specific one.
- `couple_key_wraps` and `user_key_wraps` are append-only. Enforced by Postgres privilege, not RLS: `revoke all ... from authenticated, anon` followed by `grant select, insert ...`. A future policy mistake cannot restore DELETE because DELETE was never granted. This repo already documents the failure mode this avoids — `hardening_2026_08.sql:33` records that a column-level revoke is a no-op while a table-level grant survives. Consequence: no client request, from either partner, can remove the other's key access.
- A partner has no write path into your personal key slots. `user_key_wraps` INSERT requires `user_id = auth.uid()` AND `recipient_id` owned by `auth.uid()`. There is no policy, RPC, or server role that inserts a wrap of PK_u for a recipient belonging to the other user. Consequence: 'private from your partner' is key possession, not `.eq('author', myId)` in Dart.
- Exactly one epoch may exist per (couple, ordinal). Enforced by `unique(couple_id, epoch_ordinal)` and by `claim_epoch()` doing a single `INSERT ... ON CONFLICT DO NOTHING ... RETURNING`. The losing device reads back an epoch_id it did not propose and is structurally unable to write, because it holds no key for the committed epoch.
- Every ciphertext row names the key that opens it. `epoch_id uuid` is stamped on the row with a FOREIGN KEY to `couple_epochs`, so a client cannot stamp an uncommitted epoch, and readers select a key rather than trial-decrypting. Combined with the next invariant, a mislabeled row fails to open rather than opening under the wrong key.
- Every wrap and every item ciphertext is bound to its slot by AEAD associated data `(couple_id_or_user_id, epoch_id, key_kind, recipient_id)`. A wrap copied, replayed, or moved into another slot by a malicious server or a compromised client fails to open. The server can withhold a wrap — a detectable denial of service — but can never redirect one.
- Epoch rotation cannot silently strand a recipient. `claim_epoch(mode='rotate')` commits only if the submitted wraps cover exactly the set of currently active, non-tombstoned recipients of both users, counted server-side in the same transaction. Excluding the partner requires `mode='separate'`, which writes a loud, couple-visible record. The server cannot verify a blob decrypts, but withholding and garbage are the same detectable failure.
- Every expiry, consent window, and retention timer is evaluated against `now()` inside a SECURITY DEFINER function, and no expiry timestamp is client-writable. Enforced by dropping the table-level UPDATE grant and re-granting UPDATE only on client-owned columns — the technique `hardening_2026_08.sql:43-45` already uses on `profiles`. No ordering decision anywhere in this domain depends on comparing two `now()` values, because Postgres `now()` is transaction-start time and is not monotonic across overlapping transactions; epochs order by `epoch_ordinal`, and revocations are set membership, not sequence.
- No destructive migration step is gated on client-reported progress. 'Legacy remaining' is `count(*) where epoch_id is null`, computed server-side per couple. Re-wrap is `UPDATE ... WHERE id = ? AND epoch_id IS NULL`, so a concurrent second writer is a no-op. There is no counter column to double-decrement.
- No read path is removed before the credential that replaces it exists. Stage 7 is the only removal in the migration, and it is gated per user on a server predicate: zero rows with `epoch_id is null` for that couple AND at least one non-device wrap of the current epoch for that user. A user with no offline credential keeps the legacy fallback indefinitely.
- There is no server-side guess counter anywhere. The partner-assisted attempt limit lives in local storage on the approving device, keyed to the requesting device's `x25519_pub`, so deleting and re-inserting the request row does not reset it. A Postgres row holding `attempts_remaining` is restorable from a nightly backup and provides zero cryptographic guarantee (research/e2ee.md:210).
- Recovery is a set of enrolled, independently revocable objects, and the server holds no oracle for any of them. Revoking one is appending a tombstone that removes it from the RLS SELECT predicate on `couple_key_wraps`; it does not affect the others and none is an implicit backdoor.
- Devices per user are capped at three, enforced inside `register_device()`. The fourth registration is refused with 'remove a device first', never silently ignored. `invalidated` and `retired` devices do not consume a slot, so a lock-screen change cannot burn one.
- Every byte at rest outside Postgres is ciphertext under a key that is not in the storage service's trust domain, and the object path carries no identifiers. Enforced by a single choke-point upload function with a CI grep asserting no other call site reaches `storage.from(...).upload`, plus an unauthenticated fetch test asserting the first bytes are not a JPEG magic number.
- A URL is never a capability. Nothing granting read access to bytes appears on a realtime payload, a push payload, or any row a non-member can read; references are opaque object ids resolved under RLS. Every channel is `private: true` with an RLS policy on `realtime.messages` scoped to couple membership, asserted by a CI grep over every `.channel(` call site plus a stranger-JWT join test. Knowing a couple UUID grants nothing.
- Tag tokens are keyed by the CURRENT epoch key, not by an immortal root. `HMAC-SHA256(HKDF(EK_current, 'fantasy-tags-v3'), tag)` cannot be enumerated without that epoch key, and rotating the epoch after a device is stolen rebuilds the tokens. The residual — a partner can enumerate, because overlap computation needs a shared key — is a published limitation, not a claim.
- The verification gate sits at the moment key material crosses, not at send. Closer has no send path keyed to a peer identity key, so a send-side gate would fire after the escrow had already been handed over. Approval of a partner-assisted re-wrap shows the safety number, requires the partner to TYPE the six digits (software compares; there is no match-confirm button), and cross-signs the requesting device's `x25519_pub`. A permanent transcript event is written on both sides and VERIFIED collapses to UNVERIFIED, which is monotonically downgradable and restored only by a human comparison.
- Key state is fetched as a whole set, never through a cursor, and never through `postgres_changes`. A couple has at most a few dozen wrap rows; clients read all of them on app open and on a payload-free broadcast hint. There is no `WHERE seq > cursor` in this domain, so out-of-order sequence visibility and rows vanishing beneath a cursor are structurally irrelevant here.

## Scale ceiling
**Key material is O(devices × epochs), never O(messages), and is never the bottleneck.** Per couple: ≤6 devices + ≤6 recovery credentials = ≤12 recipients, times a handful of epochs, at ~120 B/row → ~4 KB of `couple_key_wraps`. Per user: 2 key kinds × ≤6 recipients ≈ 1.4 KB of `user_key_wraps`, plus ~300 B of device rows. At 100k users / 50k couples that is roughly **350 MB, under 1 GB with indexes** — about $0.13/mo of Pro disk at $0.125/GB. (The original document's "~150 MB ≈ $19/mo" was arithmetically wrong by two orders of magnitude.) Contrast the prekey path rejected: research/e2ee.md:223 prices Kyber pubkeys alone at ~1.6 GB per 10k users, enough to blow the free-tier database on prekeys.

**1k users (500 couples).** No crypto-attributable ceiling. The only server work is inserting wrap rows. Failure mode: none.

**10k users (5k couples).** First pressure is the hourly `purge_expired()` and the storage orphan sweeper. Deleting ~10k rows/hour with a partial index on `(expires_at) where not deleted` is nothing; the sweeper comparing `storage.objects` against the ledger is what degrades. **Failure mode at the ceiling: the sweeper's scan overlaps its next invocation and piles up, holding locks on `storage.objects`.** Designed in before it bites: the ledger is partitioned by month and the sweeper reads one partition. Thumbnails double the object count, which pulls this ceiling closer — sweep cost is the term to watch, not key count.

**100k users (50k couples).** The ceiling is **media egress driven by views, and it is a bill, not a correctness break.** Encrypting objects removes server-side image transformation, so a grid view has no 200px variant to fetch. Without client-side thumbnails, 40k Closer users opening a 30-tile grid ten times a month pulls ~10.8 TB/mo of full-resolution bytes — roughly **$970/mo** at the uncached rate, and an out-of-memory problem on the IN2015 long before that. With client-side thumbnails at ~15 KB, the same browsing is ~180 GB/mo, and full-resolution opens add ~700 GB/mo. Blended egress lands in the **$20–60/mo** band depending on cache hit rate, and thumbnail hit rate is the single number to measure — with roughly two readers per object, full-resolution content will not approach the cached rate, so do not assume $0.03/GB across the board. PADMÉ padding adds ~12% to both storage and egress.

**The one genuine cryptographic ceiling.** Wrap fan-out is `recipients × epochs` per couple. A couple with many devices across many epochs needs a device holding `EK_n` online to mint `EK_{n+1}`, and an epoch whose only surviving wrap sits on a dead phone becomes an unreadable *slice* of history — partial loss, which is more confusing to a user than total loss. Two structural mitigations: three devices per user, server-enforced in `register_device()`; and epochs rotated only on explicit user action. Maximum realistic case is ~12 recipients × a handful of epochs — tens of unwraps at first unlock, milliseconds.

**Survivability, with the assumption labelled as an assumption.**

Today: research/e2ee.md:231 estimates 2% of couples per month replace a phone with no backup. At 50k couples that is **~1,000 destroyed couple histories per month**, each destroying it for both people.

Under this design a couple history is lost only when both users' devices die inside the same window AND no offline credential survives for either. Write it as `D × (1−E) × (1−V)` where D is dual-loss rate, E is Recovery Key enrolment, V is platform-vault coverage.
- **D = 0.05%/couple/mo (independent loss), E = 40%, V = 85% → ~2/mo.** This is the headline the original document quoted, and it rests entirely on an unsourced independence assumption.
- **D = 0.5% (correlated — couples upgrade on shared plans, travel together, are burgled together) → ~22/mo.**
- **V = 0 (Block Store does not ship or does not fit) → 15/mo at D=0.05%, 150/mo at D=0.5%.**
D is an assumption to be measured, not a result. State it that way in any budget or roadmap that cites it.

**PK_u loss, which the original headline silently excluded.** Personal content is wrapped only to the user's own devices and own credentials, so partner-assisted recovery loses it by construction. At 50k couples, ~1,000 users/month replace a phone. Without Recovery Key as a precondition, PK_u loss is `1,000 × (1−E) × (1−V)`: **~90/mo at E=40%, V=85%; ~600/mo if the platform-vault tier does not ship.** Those users recover through their partner, see "your history is back", and find their fantasy jar and personal vault empty with no explanation — which reads as a bug because the shared timeline is intact. Making the Recovery Key a hard precondition for PK_u-backed features drives this to approximately zero and puts the friction only on the content that cannot otherwise survive.

**Stated ceiling that is not a bug:** total loss of every authenticator is terminal by design, and the setup screen must say so before the fact rather than a support reply saying it after.

## Cost
**Correcting the source citations first.** The original document cited "research/supabase.md:267 puts [10k] at ~$70–110/mo" — line 267 is about connection overage, not a total. The actual totals in the research are **supabase.md:271 → $500–560/mo at 10k users** and **supabase.md:279 → $5,000–6,500/mo at 100k**, and supabase.md:282 states cost is **~85–90% Realtime messages at every scale past 1,000 users**. supabase.md:276 further notes the 100k configuration is ~5x past the 2,500 msg/s Team ceiling — a hard stop requiring Enterprise or a self-hosted Elixir Realtime cluster, not an overage. Restating crypto cost as a fraction of the real totals makes the argument stronger, not weaker.

**Assumptions, stated so they can be argued with:** 2 users per couple; 40% of couples enable Closer; per active Closer couple 15 photos/month at 900 KB after a client-side resize to 1600px long edge, plus a 15 KB thumbnail each, plus 40 text items; browsing at 10 grid opens and 20 full-resolution opens per user per month. Supabase Pro $25/mo base, 8 GB disk then $0.125/GB, 100 GB storage then $0.0213/GB, 250 GB egress then $0.09/GB uncached and $0.03/GB cached. PADMÉ padding ~12% on both storage and egress.

**1,000 users (500 couples, 200 Closer).** New media ~2.7 GB/mo + ~45 MB thumbnails → ~34 GB in year one with padding. Storage inside the 100 GB allowance: **$0**. Egress from browsing ~4 GB/mo, inside 250 GB: **$0**. Key rows ~1.5 MB. **Crypto-attributable: $0/mo**, against a total supabase.md:264 puts at ~$58/mo. The migration is cost-*negative*: those same 34 GB currently sit in Postgres `bytea`, which exceeds Pro's 8 GB disk in about three months and then bills $0.125/GB while riding in every database backup.

**10,000 users (5k couples, 2k Closer).** New media ~30 GB/mo with padding → ~360 GB year one. Storage overage at year end (360−100) × $0.0213 = **~$5.50/mo**. Egress: thumbnails ~18 GB/mo, full-resolution ~72 GB/mo → ~90 GB/mo, inside 250 GB: **$0**. Key rows ~20 MB. **Crypto-attributable ≈ $6/mo — roughly 1% of the $500–560/mo total.**

**100,000 users (50k couples, 20k Closer).** New media ~300 GB/mo with padding → ~3.6 TB year one. Storage (3,600−100) × $0.0213 = **~$75/mo**, rising ~$6.50 each month. Egress ~900 GB/mo (180 GB thumbnails + 720 GB full-resolution), 650 GB over allowance → **$20/mo if fully cached, $58/mo if fully uncached; budget $40–60** because full-resolution objects with ~2 readers each will not cache well. Key rows ≈ 1 GB ≈ **$0.13/mo**. **Crypto-attributable ≈ $120–140/mo — roughly 2% of the $5,000–6,500/mo total.**

**The term the encryption decision creates, priced.** Encrypted objects cannot be transformed server-side. Without client-side thumbnails, grid browsing at 100k users pulls ~10.8 TB/mo instead of 180 GB/mo — **~$970/mo instead of ~$20/mo**. That single decision is worth more than the entire rest of the crypto bill, and it is the reason thumbnails are specified as first-class objects with their own DEK and ledger row rather than left as an implementation detail.

**Dropped: the cost argument for the public bucket.** The original document argued encryption pays for itself by moving media to a public bucket at the cached rate (supabase.md:155, :318 — private buckets check permissions per object per user, so their traffic bills as uncached at $0.09/GB). The saving is real but small and depends on a cache hit rate this workload will not achieve. The public bucket stands on the **security** argument alone: with random paths and per-object DEKs, a leaked URL, a stale CDN entry, and a stolen service-role key are all equivalent to random bytes.

**Two terms added that the original omitted.** (1) "A URL is never a capability" replaces one signed-URL fetch with a broadcast id, a REST resolve, and a Storage GET — one additional round trip per media view, negligible in egress but real in Realtime-adjacent request count, which is the 85–90% term. (2) PADMÉ padding at ~12% on storage and egress, included above.

**Client CPU.** Per-item XChaCha20-Poly1305 on a 32-byte DEK, one sealed-box unwrap per key at unlock, ≤ a few dozen unwraps for a couple's full keyring, and 5,200 SHA-512 iterations for a safety number — under a millisecond on the IN2015 (research/e2ee.md:192). No Argon2, because there is no PIN and no low-entropy secret is ever used as key material. **$0.** The real client cost is memory: Poly1305 forbids range reads and progressive decode, so a full-resolution object must land entirely before any byte is trusted.

**The counterfactual.** The escrow designs this rejects are not expensive at scale — they are expensive at *any* scale, because the cost is fixed. One enclave-capable instance is ~$140/mo; SVR3's security claim needs three across separate vendors, so $400–1,500/mo minimum. At 1,000 users that exceeds the entire Supabase bill. research/e2ee.md:233: "There is no scaled-down version of this design: the fixed cost is the fixed cost."

## Migration
**Nothing is re-encrypted in a batch, and no read path is ever removed before the credential that replaces it exists.** That second rule is the one the previous plan broke — its Stage 2 dropped the legacy path before any recovery credential shipped, reconstructing the total-loss bug it was written to remove. The rule is now structural: Stage 7 is the only removal in the whole plan, and its gate is a server predicate, per user.

**Stage 0 — stop the bleeding. Five independently revertible pieces, not one.** The original Stage 0 was described as "no crypto change, ships alone" while being the largest change to Realtime authorization the app has ever had.
- **0a.** `private: true` per topic, **highest risk first** — touch, touch_trace, capsule_proximity, mood_lamp — each behind a remote flag, measuring joins/sec and error rate between each. Private channels run a database authorization query at join through Realtime's small connection pool, and supabase.md names rapid reconnection loops from failed authentication as a top cause of project suspension. Ship `realtime.setAuth()` on every token refresh **in the same change**, because private channels disconnect on JWT expiry and that is the app's existing "joined but dead channel" bug.
- **0b.** Stop putting signed URLs on broadcast payloads (`touch_map_screen.dart:601`); broadcast the opaque object id.
- **0c.** **Dump the live policies first.** `couple_media`, `couple_intimate` and `chat-bg` have no DDL anywhere in `E:/LDR/supabase` — their policies exist only in the dashboard. Commit `storage.buckets` and `pg_policies`/`storage.policies` verbatim as a baseline in one commit; change them in a separate one. "Revertible" does not restore a policy nobody wrote down.
- **0d.** Fix the missing `ON DELETE` on `vault_items.created_by/delete_requested_by/deleted_by`, `memory_threads.accepted_by`, `memory_revisits.initiated_by`, so `delete_my_account()` stops raising a foreign_key_violation for exactly the couples that used Closer. **This is a source-read inference — run the 60-second repro against a local `supabase start` before writing the fix.**
- **0e.** Proximity-unlock authorization gap (`capsules.sql:91-95` validates the date only for modes `date` and `both`, so a proximity capsule opens from anywhere).

**Stage 1 — key tables, pure addition, nothing depends on them yet.** `devices`, `couple_epochs`, `couple_key_wraps`, `user_key_wraps`, `key_revocations`, `recovery_credentials`, `key_requests`, `storage_ledger`. Append-only grants, RLS, `register_device()`, `claim_epoch()`. Each device computes `EK_1 = HKDF(legacy_derived_shared_key, "miles-crk-bootstrap-v1")` — deterministic, so both devices converge with no exchange and no race — and wraps it to its own DK. Reads and writes are unchanged. If this stage is entirely wrong, nothing is lost, because nothing reads from it.

**Stage 2 — Recovery Key.** 40 characters (1 version, 1 identifier, 34 entropy, 4 ECC over GF(32), B/G/I/O folded to 8/C/1/0 — research/e2ee.md:212's explicit recommendation), shown once, confirmed by typing back four randomly chosen positions. Enrolls as a credential; `EK_1`, `PK_u` and `IK` are wrapped to it. **This ships before partner-assisted**, reversing the original order, because it is the only tier that restores PK_u.

**Stage 3 — platform vault credential.** Android Block Store / iOS Keychain, its own independent secret, its own revocable credential. Covers uninstall-and-reinstall on the same phone, the largest real cohort (research/e2ee.md:181). Note: on Android, unlike iOS, app data including EncryptedSharedPreferences *is* deleted on uninstall, so Labyrinth's "persists across uninstalls" keychain property does not transfer for free. **Verify Block Store's current entry-size and count limits and whether cloud-backed entries require a screen lock before committing.** Do not solve it by re-enabling `allowBackup` — that undoes the disguise posture.

**Stage 4 — partner-assisted re-wrap.** `key_requests` with a 30-day server-set expiry, the SAS exchange, the typed six digits, the local attempt limit keyed to the requesting device's pubkey, cross-signing at approval, the transcript event. Depends on Stage 1 only.

**Stage 5 — content writes move to epoch keys.** New writes are encrypted under `EK_1` and stamped `epoch_id`; reads select by stamp and fall back to `CryptoCore._sharedKey` when the stamp is null. The existing all-zero-nonce legacy plaintext detection is untouched, so pre-2026-08 rows keep reading. This is safe precisely because Stage 1's bootstrap is deterministic: both devices already hold `EK_1` without any wrap having to arrive. Old partner builds are unaffected — nothing about `partner_keys` changes.

**Stage 6 — lazy re-wrap.** Any device re-encrypts old rows under `EK_1`, oldest-first, as `UPDATE ... WHERE id = ? AND epoch_id IS NULL`. Concurrent devices are no-ops for each other. Progress is a server predicate; there is no counter and no cliff. Couples where one side already lost their key: those rows are unrecoverable *today* — mark them `undecryptable` with honest copy and delete `closer_load_result.dart:39-42`'s "your partner may need to open Closer", which is false.

**Stage 7 — the only removal, gated per user.** Disable the legacy read fallback for user U when `closer_migration_status()` reports zero rows with `epoch_id is null` for that couple **and** U holds at least one non-device wrap of the current epoch. A user with no offline credential keeps the fallback indefinitely; the legacy code itself is deleted only in a much later release when the fleet-wide predicate is zero.

**Stage 8 — media out of `bytea`.** Order reversed from the original to remove the two orphan windows: upload the encrypted object **and its thumbnail** first, then **one** statement that sets `object_id`, `thumb_id` and nulls `bytea`, with both ledger rows inserted in the **same transaction** as that write — so the sweeper can never observe an object without the ledger row it is about to gain. Simultaneously add column projection and pagination to every Closer fetch; `fetchItems()` and `fetchThreads()` currently do a bare `.select()` that downloads every photo the couple has ever saved on screen open.

**Stage 9 — body-map coordinates.** `x, y` move inside the ciphertext. The `real` columns stay until a server-side backfill predicate reports zero unmigrated rows, then drop.

**Stage 10 — fantasy jar. Do not migrate.** Entries written before PK_u were encrypted under a key the partner has held all along and may have cached locally; re-encrypting them is an unenforceable retroactive privacy claim. PK_u applies to **new entries only**, old entries are marked in the UI as written before private mode, and the copy says so. Tag tokens move to `HMAC-SHA256(HKDF(EK_current, "fantasy-tags-v3"), tag)`, rebuilt at write and at every rotation — not "during the Stage-2 re-wrap", which by then no longer exists.

**Stage 11 — capsule item text and media encrypted** (wholly plaintext today).

**Stage 12 — retention becomes real.** Server-set `expires_at` via table-grant removal plus column re-grant; `purge_expired()` hourly on `pg_cron` plus a 5-minute cycle for user-initiated deletes; the object random-overwrite on delete; the monthly-partitioned ledger and orphan sweeper. `purge_expired()` is explicitly forbidden from touching `key_requests`.

**Stage 13 — safety numbers, transcript, cross-signing.** Last, because it hashes over a device list that only exists after Stage 1 and only matters after Stage 4. **No send-side gate** — Closer has no send keyed to a peer identity key, and the gate would fire after the escrow had crossed.

**Dependencies, stated:** 4 needs 1. 5 needs 1. 6 needs 5. 7 needs 6 AND (2 or 3). 8, 9, 10, 11 need 5. 12 and 13 need 1. Everything in Stage 0 is independent of everything else. **This is four separate content migrations (6, 8, 9, 11), each with its own server-side completion predicate**, plus one explicit non-migration (10) — not one migration described as none.

## Verification
**The premise: make the crypto a pure function of state, then test the state machine instead of the devices.** Every previous fix passed on two NTP-synced phones on one wifi, because that configuration exercises one path through a state machine with dozens.

**1. Deterministic key-lifecycle simulator in `test/`, property-based, 10,000 seeds in CI.** Devices are plain objects; inject a fake keystore and a fake Supabase whose in-memory tables enforce the same RLS predicates and the same *privilege* set as the real schema — including the absence of DELETE on the wrap tables. Event alphabet: `{addDevice, loseDevice, reinstall, keystoreInvalidated, recoverByPartner, recoverByCode, recoverByPlatform, rotateIdentity, revokeDevice, rotateEpoch, separateEpoch, concurrentMint, mutualPending, partnerRefuses, writeItem, readItem, deleteItem, purge, pitrRestore}`.
Properties, **split by key kind** because the original single property was false under the design's own recovery matrix and would have failed a correct implementation:
- **P1 (couple content).** For every item written under `EK_n` at time t, and every device d that is a couple member at t' > t holding at least one surviving credential of any kind, `read(d, item)` succeeds.
- **P2 (personal content, asserted as a negative).** For every item under `PK_u`, `read(d, item)` succeeds **only if** d holds a credential of kind `code` or `platform_vault` belonging to the same user. The sequence `{writeItem(A, personal), loseDevice(A), recoverByPartner(A), readItem(A)}` must **fail** — a passing read here means someone wrapped PK_u to the partner and deleted the product's only key-enforced privacy guarantee.
- **P3 (append-only).** No reachable sequence produces an UPDATE or DELETE against `couple_key_wraps` or `user_key_wraps`.
- **P4 (no divergence).** At most one epoch per (couple, ordinal) ever exists; every item's `epoch_id` references a committed epoch; no two distinct keys are ever both valid for one stamp.
- **P5 (no premature removal).** No sequence reaches a state where the legacy fallback is disabled for a user who holds zero non-device wraps.
P1 fails on seed 1 against today's code — `{reinstall(A), readItem(B)}` violates it — which is exactly the evidence never gathered.

**2. Golden vectors, checked in.** `(EK_n, device keys, plaintext) → expected wrap bytes and envelope bytes`. There are three mutually incompatible packing layouts in the codebase today (`mac||ct` in `packMacAndCiphertext`, `ct||mac` hand-rolled in `fantasy_jar_repository._pack` and `body_map_repository._pack`, `nonce||mac||ct` in `packFull`), plus a fourth private copy of the derivation preamble in `body_map_repository.dart:36-60`. Golden vectors make a fifth impossible to add silently. Plus a compat gate that decrypts vectors generated by the **previous release binary** — that is what catches a refactor changing the format for existing users.

**3. Two isolates, one process, for "two phones".** The partner-assisted SAS exchange is two state machines exchanging rows. Run both in one test over a channel the test fully controls: drop, reorder, duplicate, delay; advance each side's clock independently. Scripted scenarios covering every dependency the brief forbids — partner offline for three days, app killed mid-exchange, socket dead but HTTP alive, clocks eight hours apart, the same approval delivered twice, request row deleted and re-inserted (assert the attempt counter does **not** reset), and an attacker-substituted `x25519_pub` (assert SAS mismatch, assert the wrap is refused).

**4. Clock-skew testing is free, because the invariant forbids client clocks — so assert the invariant mechanically.** For every column on a checked-in list of server-owned timestamps, assert `has_column_privilege('authenticated', table, column, 'UPDATE')` is false **and** `has_table_privilege('authenticated', table, 'UPDATE')` is false where the table has no client-writable columns. The table-level check is not optional: `hardening_2026_08.sql:33` records that a column-level revoke is a no-op while the table grant survives. (The original plan's `information_schema.column_privileges` check cannot detect "used in an expiry predicate" and would have passed vacuously.)

**5. Append-only, asserted as a privilege fact.** `has_table_privilege('authenticated'|'anon', 'public.couple_key_wraps'|'public.user_key_wraps'|'public.couple_epochs'|'public.key_revocations', 'UPDATE'|'DELETE')` is false for every combination. This is the mechanical form of the invariant that closes the remote-wipe weapon, and no future policy change can regress it without failing this query.

**6. RLS tests in SQL against a local `supabase start`,** as three roles: user A, partner B, and stranger C holding a valid JWT **and knowing the couple UUID** (hardening_2026_08.sql:24-25 records that couple UUIDs are not secret). Assert: C reads zero rows from every key table and every Closer table. B reads zero rows from `user_key_wraps where user_id = A`. B reads zero plaintext from post-Stage-10 `fantasy_jar_entries` and from `personal_vault_items`. B cannot INSERT into `couple_key_wraps` for a recipient of A's except through `deliver_partner_wrap()` with an open request. That last set is what the current implementation cannot pass and is the whole product promise of the Fantasy Jar.

**7. Storage posture as executable assertions.** (a) `select id, public from storage.buckets` matches a checked-in map — which fails today, because three live buckets have no DDL. (b) Ciphertext is enforced **by construction at a single choke-point upload function**, with a CI grep asserting no other call site reaches `storage.from(...).upload` — not by sampling one object, which a plaintext path introduced by the Stage-8 migration or by thumbnails would pass. (c) An unauthenticated fetch of a public URL asserts the first bytes are not a JPEG magic number, run against both a full object and a thumbnail.

**8. Channel privacy.** CI grep asserting every `.channel(` call site passes `private: true`, plus an integration test where a stranger JWT joins `touch:<known-uuid>` and the join is rejected. Plus a joins/sec measurement gate between each Stage-0a topic flip.

**9. Delete honesty.** A test that deletes an item, asserts the ledger row carries `purge_at`, asserts the object bytes differ from the original after the overwrite step, and asserts the item is unreadable to a client that still holds `EK_n`. Then a test that restores the wrap row from a snapshot and asserts the item is **still** unreadable because the bytes were overwritten — that is the test that makes the honest deletion claim checkable rather than rhetorical.

**10. `delete_my_account()` repro, executed, not inferred.** Against a local `supabase start`: create a couple, write vault items and a memory thread from both users, delete one account with the partner remaining, and record whether it raises `foreign_key_violation`. This is 60 seconds and it converts the one source-read inference in this design into a fact.

**What still needs hardware — one phone at a time, never two networks.** Does the Keystore-sealed device key survive, on the IN2015, the Vivo and the OnePlus 7, across **seven** events: app upgrade, force-stop, reboot, **lock-screen credential change**, **biometric re-enrolment**, **uninstall/reinstall**, and **Android device-to-device transfer**. The original plan tested the first three — omitting the two that trigger `KeyPermanentlyInvalidatedException` and the two the entire recovery design exists for. Three phones, seven events, one afternoon, and it is the only claim here a simulator cannot make.

## Accepted limits
**1. Deletion is not backup-proof, and the original claim to the contrary is withdrawn.** The wrap is a Postgres row; Supabase daily backups and PITR restore Postgres rows. The original document rejected server-side guess counters because a row is "restorable from a nightly backup" and then relied on the identical mechanism for its deletion guarantee. Honest statement: **an item is unreadable to every live reader the instant its wrap is destroyed, and irrecoverable once the object is purged (≤5 minutes for user-initiated deletes) and the backup retention window has rolled past.** The random-overwrite of the object before purge is a real mitigation — Storage overwrites are not carried in Postgres backups — but it is best-effort: it requires the client to be online at delete time, and a CDN entry can survive up to 60 seconds. **Residual risk: an operator-initiated PITR restore inside the retention window, executed before the object purge ran and before the overwrite succeeded, restores readability of a deleted item, and no user is told.** Publish the retention window rather than claiming immediacy.

**2. A malicious or compromised server can withhold wraps and truncate the epoch list.** AEAD associated data prevents redirecting a wrap into another slot, but nothing prevents the server serving a device an incomplete set. Meta publishes the same limitation for Labyrinth (research/e2ee.md:125). **Residual risk: denial of service and a partial view of history, detectable as missing data, never as silently wrong plaintext.**

**3. Revocation is forward-only.** A revoked device keeps every epoch key it already downloaded, forever. Tombstoning removes it from future wrap delivery; epoch rotation limits it to content written before the rotation. **Residual risk: a stolen unlocked phone reads all existing content until the rotation completes, and the UI must say `retired`/`revoked` means "no future access", not "no access".**

**4. Partner-assisted recovery is authenticated by the human voice channel.** The six digits are read from a screen and typed by the partner. An attacker holding A's session (borrowed unlocked phone, stolen refresh token) can register a pending device, see the digits, and telephone B. **Residual risk: a social-engineering attack succeeds if the attacker can convincingly impersonate the partner on a call.** Bounded, not eliminated, by: it delivers CRK only and never PK_u; a permanent transcript event fires on both sides; the new device appears in the device list with a label and timestamp; and three wrong entries against a given requesting pubkey lock that pubkey out permanently on B's device. That local counter is also erased if B factory-resets — trivially true and not worth defending against.

**5. Fantasy tag matching leaks your full tag set to your partner.** Overlap computation requires a shared key, so any scheme short of a Private Set Intersection lets the holder enumerate. PSI is disproportionate here. **The copy must change to what is true: "your partner sees which themes you both picked; never your words."** Separately, **fantasy entries written before Stage 10 are permanently readable by the partner** — they were encrypted under a couple key the partner has held all along and may have cached locally. They are marked in the UI and not migrated, because migrating them would be an unenforceable retroactive privacy claim.

**6. Total loss of every authenticator is terminal.** Both users' devices dead, no Recovery Key, no platform-vault entry — the data is gone and no one can recover it. This must appear on the setup screen before the fact, not in a support reply after it (research/e2ee.md:144's wording is the model).

**7. Two structural gaps in partner-assisted coverage.** (a) **Mutual pending:** if both partners replace phones in the same window, neither can approve the other; the only exit is a Recovery Key. (b) **Breakup:** the moment a person most urgently wants their shared memories back is the moment the ex-partner will not approve — and the ex can also `mode='separate'` them out of future content while holding the only approval that would restore the past. Both are stated in setup copy. Neither is fixable without a server-side escrow this stack cannot host.

**8. The dual-loss rate is an assumption, not a result.** The "~2/mo residual" figure rests on 0.05% independent dual loss per couple per month, which is unsourced. Couples upgrade on shared plans, travel together, and are burgled together. At 0.5% correlated loss the residual is ~22/mo. Measure it; do not cite it as established.

**9. No forward secrecy for content.** Compromise of `EK_n` exposes every item in that epoch, permanently. This is deliberate — Closer is a store whose purpose is re-reading in three years, and a ratchet is a deletion mechanism dressed as a security property — but it is a real property and should not be misread as an oversight.

**10. Metadata the server sees, published rather than assumed away.** Row existence and count, `couple_id`, `author`, `created_at`, item `kind`, padded ciphertext length, storage object size and access time, thumbnail existence (i.e. "this item is an image"), realtime topic names and join timing, push timing, IP, per-user device count and recovery-credential count, coarse `happened_month`, and the `retention` class in cleartext. The last two are deliberate: ordering and pagination need a coarse date, and the server enforces purge and cannot act on a value it cannot read.

**11. Padding hides size imperfectly.** PADMÉ buckets, ~12% overhead, bucketed not hidden. A 40 MB video and a 40 KB note remain distinguishable.

**12. Encrypted objects forbid server-side transformation and range reads.** No server-side thumbnails (hence client-side ones), no HTTP range requests, no progressive decode — the whole object must land before any byte is trusted. **Residual risk: memory pressure on the IN2015 for large photos, and a slower first paint than a plaintext CDN image.**

**13. The platform-vault tier is unverified.** Android Block Store's current entry-size and count limits, and whether cloud-backed entries require a device screen lock for E2EE, have **not** been checked against live documentation. The survivability arithmetic is materially sensitive to whether this tier ships: without it, PK_u loss rises from ~90/mo to ~600/mo at 50k couples.

**14. Server-enforced wrap *coverage* is not server-enforced wrap *correctness*.** `claim_epoch(mode='rotate')` can count that a wrap row exists for every active recipient; it cannot verify the blob decrypts. A client that submits garbage produces the same observable outcome as a server that withholds — a detectable failure, not a silent one — but the recipient discovers it at unlock time, not at rotation time.

**15. One claim in the current-state analysis is still an inference.** The `delete_my_account()` foreign-key breakage (`account_deletion.sql:57` versus the missing `ON DELETE` on `vault_items.created_by/delete_requested_by/deleted_by`, `memory_threads.accepted_by`, `memory_revisits.initiated_by`) was read from source, **not executed**. Stage 0d must run the 60-second repro against a local `supabase start` before the fix is written.

## Open decisions
**1. Is Recovery Key enrolment mandatory?** *Recommend: mandatory to enable the PK_u-backed features (fantasy jar, personal vault); strongly prompted but optional for couple-shared Closer.* The numbers decide it: without it, ~90/mo (or ~600/mo if Block Store does not ship) users lose personal content silently at 50k couples, recovering through their partner, seeing the shared timeline intact, and finding their private content empty — which reads as a bug because it looks like one. Scoping the friction to PK_u content rather than to Closer as a whole puts it exactly where it is load-bearing and leaves the shared surface frictionless. You have no key, so "I lost everything" has no reply; the friction is cheaper than the support queue you cannot serve.

**2. Ship the platform-vault tier?** *Recommend: yes, but verify first.* It covers uninstall-and-reinstall on the same phone, the largest real cohort (research/e2ee.md:181). But Labyrinth's "persists across uninstalls" is an iOS Keychain property; on Android app data is removed on uninstall, so Block Store is the analogue. **Verify Block Store's entry-size and count limits and its screen-lock requirement for cloud-backed E2EE entries before committing.** If it does not fit, the Recovery Key alone is sufficient and this tier is convenience. Do **not** solve it by re-enabling app-wide `allowBackup` — that undoes the deliberate launcher-disguise posture.

**3. Does the partner get a wrap of your Personal Key — a "legacy contact"?** *Recommend: no by default, offered as an explicit, individually revocable enrolment with unambiguous copy.* This is the most emotionally loaded switch in the design and the only decision here a user would experience as a betrayal if defaulted wrong. Note that the schema makes the safe default structural: there is no path by which the partner writes into `user_key_wraps`, so enabling this must be an act by *you*, wrapping *your* PK_u to a credential of kind `partner`.

**4. Retention default for Closer items.** Today `keep` for the vault and `ephemeral` for afterglow, and neither is enforced by anything — `retention='ephemeral'` writes `reconfirm_due` that nothing reads, and `deleted=true` never hard-purges. *Recommend: default `keep`, plus a server-enforced 24-month dormancy purge for couples with no session in 24 months, announced by push and email 30 days ahead.* That bounds both the storage bill and the breach blast radius for abandoned accounts — the population most likely to be breached and least likely to notice.

**5. When does the legacy dual-read path go away?** *Recommend: not on a calendar. Gate it on the server predicate, per user, and publish each couple's state in-app.* The original "two releases or 90 days" is a date-based cliff, which is the shape of the bug that made the previous plan fatal. Delete the legacy *code* only when fleet-wide telemetry shows zero couples with `epoch_id is null` rows and zero users without an offline credential.

**6. Encrypt `happened_on` and body-map `x, y`?** *Recommend: encrypt both, keep a coarse cleartext `happened_month` for ordering and pagination.* The body-map coordinate leak is the single sharpest contradiction of the E2EE claim in the suite — `intimacy_tables.sql:99-104` stores `x` and `y` as cleartext `real` columns, so the server sees exactly where on the body each pin sits and only the caption is hidden. The coordinates are the sensitive part.

**7. Does "remove device" force an epoch rotation?** *Recommend: forced for `state='revoked'` (stolen), offered for `state='retired'` (user replaced it), never for `invalidated`.* A couple always has a second epoch-key holder, so rotation is always possible. Without it the state transition is cosmetic — the removed device keeps every key it holds, including the fantasy tag key. If the product does not want forced rotation, then the UI copy must say plainly that removing a device does not revoke access to existing content.

**8. SAS digit direction — the one protocol decision to lock before any code is written.** *Recommend: A's new device displays, the partner types.* The alternative — the partner's existing device generates and A types (Labyrinth's shape) — is better if you ever replace the SAS with a real PAKE, because a PAKE needs the secret as input on both sides. Choosing now avoids a rewrite later. What is **not** negotiable either way: the digits are typed and compared in software, never confirmed by a "yes, they match" button, and the attempt counter lives on the approving device keyed to the requesting device's `x25519_pub`.

**9. Are `key_requests` rows ever deleted?** *Recommend: no. State transitions only, plus a 90-day archival sweep of `refused` and `cancelled` rows.* A repeated pattern of refused requests against one partner is the signature of the phishing attack this flow manufactures, and it is only visible if the rows survive. `purge_expired()` must never touch this table.

**10. Fantasy Jar copy.** *Recommend: change the promise to what is true* — "your partner sees which themes you both picked; never your words" — and delete the doc comment in `crypto_core.dart` claiming HMAC-SHA256 protection that `hmacTag()` does not implement (it is keyless 32-bit FNV-1a over a fixed public 12-item taxonomy, computable by anyone with DB read in about a second).

**11. Repair/retry window.** *Recommend: none for Closer.* A wrap is idempotent and re-openable rather than a consumed ratchet step, so there is nothing to repair. This matters because research/e2ee.md:237 notes the trade nobody warns about — a repair loop needs a local plaintext outbox, which is a plaintext store on disk, a genuine risk for an app where device seizure is plausible. If chat later wants one, pick the window deliberately and write the number down; do not inherit Signal's 14 days by default.
